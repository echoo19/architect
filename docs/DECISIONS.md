# Decisions

Short records of choices that aren't obvious from the code. Newest last. Each has the context, the decision, and what follows from it.

## 001. Electron, Vite and React for the desktop shell

**Context.** The spec allows Tauri or Electron with a Next.js UI. The engine, adapters and UI are all TypeScript, and end-to-end tests need to drive the real app.
**Decision.** Electron with electron-vite, React and Tailwind. No Next.js: there is no server to render, and Vite keeps main, preload and renderer builds in one tool.
**Consequences.** One language across the stack; Playwright's Electron support drives end-to-end tests. Larger installers than Tauri would give.

## 002. TypeScript 6.0, not 7.0

**Context.** TypeScript 7.0 (the native compiler) is current, but typescript-eslint 8 supports TypeScript below 6.1.
**Decision.** Pin TypeScript 6.0.x across the workspace.
**Consequences.** Revisit when typescript-eslint supports 7.x.

## 003. Engine and agent hosts run in separate utility processes

**Context.** Training runs for hours and must survive renderer reloads and app restarts. Graduates must never reach the network, while training must reach the mentor.
**Decision.** Training, evaluation and storage run in an engine host (Electron `utilityProcess`). Workspace sessions run in a separate agent host that never imports mentor adapters and installs a loopback-only network guard at startup. Both are plain Node modules wrapped by thin Electron entries.
**Consequences.** Clear process boundary for the offline guarantee; the full loop is testable under Vitest without Electron. Events cross processes over MessagePorts, so event payloads are schema-checked.

## 004. Mentor-written tools run in QuickJS inside a child process

**Context.** The mentor writes helper tools that the student calls. They must not touch the network, the file system outside the job's declared data, or other processes.
**Decision.** Each tool call runs in a fresh QuickJS VM (quickjs-emscripten) inside a sandbox child process. The VM gets only a data API for the job's declared files and permissions, plus time and memory limits. Tools are read-only; writes go through built-in write tools that need approval in the workspace.
**Consequences.** No native modules, same behavior on Windows and macOS, deterministic execution (no clock or randomness inside the VM). Tools are plain JavaScript functions, so the mentor can't use npm packages.

## 005. Sample job: the closing routine of a home-services office

**Context.** The sample job must show the product end to end, be deterministic to check, leave room for a learning curve, and stay clear of medical, education, basic RAG and political topics.
**Decision.** Ferncliff Home Services, a fictional plumbing, heating and electrical company with about 12 technicians and 400 customers. A seeded generator writes its records as CSV files plus a short policy document (pricing, tax, payment terms, scheduling rules). The agent, named "Service desk", handles three workflows:
- **Invoices.** Price a completed job: labor by technician tier, parts at markup, trip fee, after-hours multiplier, plan-member discount, city tax, all in integer cents with the rounding rules stated in the policy. Checked by end state: the created invoice's line items and total.
- **Overdue balances.** Find invoices past terms after partial payments, totals per customer, oldest balance. Checked by exact structured answer (ids and cents).
- **Scheduling.** Find the earliest start for a job that needs a skill or license in a zone, given working hours, existing bookings and a fixed zone travel matrix, with fixed-duration slots. Checked by end state: the booking is feasible and starts at the global earliest time; ties between technicians are all accepted.

The bare student gets the same policy document and the same primitive tools as every other method. What the mentor can improve is orchestration: reading the policy, applying rules in order, writing tools for steps it keeps getting wrong. Answers are structured, not free prose. Inventory and plan renewals wait as a possible second task family.
GPT-6 Astra reviewed the first draft (five task types) and recommended cutting to these three, bounding scheduling, using integer cents and avoiding fact-matching on prose. Adopted.
**Consequences.** One coherent story ("close out today: invoices, overdue balances, tomorrow's urgent call"). Fixtures get hand-audited against independently calculated answers before any training run, because a bug shared by the generator and the checker would be invisible otherwise.

## 006. What the mentor can see

**Context.** Keep-or-revert decisions use dev, and showing the mentor dev traces would let it tune to dev the same way it tunes to train.
**Decision.** The mentor sees train traces with checker reasons, per-type train results, the overall dev pass count, and its earlier hypotheses with their keep or revert decision and overall dev change. A round rejected before dev saw it (a reply that isn't a hypothesis, or a change set the harness refuses) is listed too, with the runner's reason, which is about the mentor's own reply and files. It never sees per-type dev counts, dev traces, dev task ids or dev checker reasons, and never anything from the test split. (Per-type dev counts were in the first version of this decision; GPT-6 Astra pointed out they are an extra channel for tuning to dev, and train results already show which types fail.)
**Consequences.** Dev still leaks a little through the overall score and the decisions (adaptive overfitting), so rounds per run are capped in advance and the report shows the dev to test gap.

## 007. One hypothesis per round, kept on a margin

**Context.** The spec allows "one or a few" changes per round. Measuring each change separately costs a full dev evaluation each, and a slow local student makes that expensive.
**Decision.** Each round the mentor proposes one hypothesis: a change set that may touch several files but serves one diagnosis, with a predicted effect. Dev evaluation uses Meta's recommended sampling for Glimmer (temperature 1.0, top_p 0.95, top_k 64; greedy decoding makes it repetitive). The runner, not the harness, owns the sampler seed. Each round draws its dev seeds from the run's panel seed and evaluates both the candidate and the incumbent on them, so the incumbent is measured again instead of being judged by the score that got it kept, which was the luckier of its draws. Sharing seeds does little against noise: at temperature 1 any change to the prompt re-samples every dev task, so the two results are close to independent draws. What shared seeds do is stop a change from choosing its own seeds and make every number reproducible. The guard against noise is repetition and the margin. With `devRepeats` (1 to 3, default 1) every dev task runs under that many seeds and passes add up across them. The change set is kept only if net dev passes rise by at least the job's margin times the repeat count (default margin: 2 tasks, or 5% of dev if larger) and no task type loses more than one pass per repeat; otherwise it is reverted and logged as a failed hypothesis. Before main runs, the noise pilot (`devNoisePilot`) evaluates one harness on dev under three student seeds and reports how far the score moves; if noise alone moves it by the margin or more, raise `devRepeats`, the margin or the dev set.
**Consequences.** Clean attribution in the lineage. A round evaluates dev twice per repeat, once for the candidate and once for the incumbent, so it costs 2 × `devRepeats` × the dev tasks in attempts, on top of the train batch. Kept changes are an engineering gate, not a significance test, and the README says so.

## 008. Answers end with a structured line

**Context.** The checker must parse answers deterministically, and free-text fact matching is fragile.
**Decision.** Task prompts ask the agent to finish with one line `ANSWER: <json>`, where the JSON shape is stated per task type. Write tasks are checked on the end state of the job's scratch data instead.
**Consequences.** Format failures count as failures (the policy and task text state the format, so formatting is part of the job). The workspace uses the same harness without the answer line requirement.

## 009. Where training and the locked test run

**Context.** On this machine the local student needs 2 to 3 minutes per task (measured 2026-10-27), so a full comparison (four methods, three seeds) can't be optimized locally in the time available. A hosted copy of Glimmer is much faster.
**Decision.** Training rounds and dev evaluations may run on a hosted copy of the student. Every graduate is frozen before any test runs, and test results never trigger another round. The graduate the app ships, and one predeclared seed of every method, are locked-tested on the local student after the mentor is released: its gate closed, so no call can start, and its adapter dropped. Hosted locked tests cover every seed as supplementary results. GPT-6 Astra reviewed this and preferred local tests for every seed; that stays the goal if GPU time allows.
**Consequences.** The report card of a shipped graduate describes the agent the user actually runs. The README states, for every number, the provider, precision, runtime and seed it came from, and says plainly that optimization happened on a hosted copy.

## 010. Job setup follows the design's conversation, with every field editable

**Context.** The design starts a job as a conversation (Describe, then the mentor's clarifying questions, then a review screen). The spec lists the job fields as one setup form.
**Decision.** Follow the design: describe the job and attach files, answer a few clarifying questions from the mentor, then review the drafted job on the Define screen. Every spec field (tasks, checker, requirements, budget, mentor, student, starting harness, permissions) is editable there under Advanced, and a job file can be imported directly.
**Consequences.** Drafting a job costs a few mentor calls. The saved job file is the same either way.

## 011. Where the design shows more than this version builds

**Context.** The design includes exporting a fine-tuned adapter (`.safetensors`) and training on a "Cloud GPU".
**Decision.** No weight training in this version, so the export offers the graduate folder and the report instead of an adapter. "Cloud GPU" means a hosted endpoint for the student during training.
**Consequences.** The LoRA comparison stays on the stretch list in the spec.

## 012. MIT licence

**Context.** The repository is public and should be reusable.
**Decision.** MIT.
**Consequences.** None beyond the licence text.

## 013. SQLite through `node:sqlite`, not better-sqlite3

**Context.** The brief's default is better-sqlite3, a native module that must be rebuilt for Electron's ABI, which also breaks running the same code under plain Node for tests.
**Decision.** Use the built-in `node:sqlite` (`DatabaseSync`). Electron 45 ships Node 24.22, and a check on 2026-10-27 confirmed `node:sqlite` works inside Electron and in Node 24.
**Consequences.** No native modules in the app, no rebuild step, and tests use the same storage code as the app. The module is still marked experimental in Node, so storage stays behind a small interface in `packages/engine/src/store`.

## 014. Mentor tier for the sample job's runs

**Context.** The Meta Model API has a standard tier ($1.25 in, $4.25 out per million tokens) and a contributor tier ($0.10 in, $0.20 out) whose content Meta may use for training and which must not carry sensitive or personal data. The app defaults to the standard tier and shows the tier as a setting.
**Decision.** Development and debugging runs on the sample job use the contributor tier: its data is generated and fictional. The comparison runs reported in the README all use one tier, the standard one, so the reported cost matches what a user with real data would pay.
**Consequences.** Spend stays small (a mentor round costs well under a cent on the contributor tier and a few cents on the standard tier). The README says which tier produced each number.

## 015. Glimmer runs with low reasoning strength

**Context.** Glimmer always reasons; Ollama's `think: false` hides the reasoning but may not stop it. Meta measured 1,811 completion tokens for one agent decision at the default `high` strength and 256 at `low`. On this machine the 30B model generates only a few tokens per second.
**Decision.** Harnesses default to `thinking: low`, and the mentor may raise it per harness through `decoding.yaml` like any other decoding setting.
**Consequences.** Several times fewer tokens per step. If low reasoning caps what the student can do, a kept change that raises it will show up in the lineage with its measured cost in latency.

## 016. Harness files are strict

**Context.** Harness folders are written by a model and read back by the runner, the workspace and other people's tools. A silently ignored typo (`max_step` instead of `max_steps`) would make a change do nothing while the lineage claims it was tested.
**Decision.** Unknown or misspelled keys in any harness or graduate file are validation errors with a "did you mean" hint. On-disk keys are snake_case everywhere (YAML, `lineage.jsonl`, `report.json`). Skills, tools and examples are ordered by slug; a tool's file name must equal its `name`; Windows device names (`con`, `nul`, `com1`...) are refused as names; symlinks and OS clutter files are ignored when reading. A version folder only counts once its `harness.yaml`, written last, exists, and loading fails if the files no longer match the saved hash. Graduate folders carry the report card twice: `report.json` for the app and `report.md` for people.
**Consequences.** A mentor edit with a typo is rejected and logged as a failed round instead of being kept as a no-op. Folders written on one platform read identically on another.

## 017. Small departures from the design for accessibility and robustness

**Context.** Matching the design exactly occasionally conflicts with readable contrast or Electron's behaviour.
**Decision.** Muted text is `#7F7F87` instead of the design's `#7E7E86`, which reached only 4.48:1 on the composer; a test keeps every readable text color at 4.5:1 or better in both themes. The theme setting drives Electron's `nativeTheme`, and the page copies the resulting `prefers-color-scheme` onto `<html data-theme>`, so there is one source of truth and no flash on launch. IPC handlers reply with `{ ok, value }` or `{ ok: false, error }` because Electron mangles errors thrown across IPC; the preload turns a failure back into an `Error` with the original message. Settings rows from the design that have no setting behind them yet (open at login, privacy toggles) are replaced by real ones: mentor tier, mentor reasoning, comparison mode, and read-only privacy facts.
**Consequences.** The look is unchanged to the eye; every visible control does something.

## 018. How the sample job's data avoids shortcuts

**Context.** The mentor sees train tasks with their expected answers. Any answer value shared by many tasks (train and test alike) would let it hard-code that value and look like it taught something.
**Decision.** Every id in an answer follows from the task's own record: invoices take their job's number (job W-2482 gets INV-2482) and bookings take their request's number (R-3042 gets B-3042). The first draft numbered invoices after the highest existing one, which made all 60 invoice tasks expect the same id; it was changed before any training run. The records are a snapshot as of Thursday 2026-11-05 (`businessDate` on the job), with the office closed on Wednesday 2026-11-11. The checker works out the earliest scheduling slot itself from the original tables, an implementation independent of the generator's reference code. Values that repeat by rule (the issue date, a few due dates and trip fees) remain, and so do some scheduling slots (27 distinct slots across 60 tasks, the most common one answering 7); none of them passes a task on its own, because the checker validates feasibility and every field.
**Consequences.** A harness that memorizes answers scores close to nothing on unseen tasks. The README notes the repeated scheduling slots as a limitation of one task family.

## 019. How a graduate behaves in the workspace

**Context.** The workspace is where people use a graduate every day; its rules for writes, refusals and interruptions need to be predictable.
**Decision.** A graduate's write mode is its saved setting, falling back to the job's `permissions.writes`. "Always allow" saves `allow`; in `allow` mode the diff still appears in the chat, marked approved, so every change stays visible. A refusal is decided before the student is called and shows the reason from the guardrails. Stopping a reply marks running steps stopped and pending writes denied; a reply interrupted by a restart comes back as an error when the graduate is reopened. History sent to the student is the last 12 messages that fit in a quarter of its context. The workspace's data lives in its own folder per graduate (`<userData>/workspace/<graduateId>/`), seeded from a copy of the job's data, so workspace writes never touch training data. The agent host runs behind a loopback-only network guard and refuses any student endpoint that isn't on this machine; the tool sandbox's child process has no network APIs at all (QuickJS), so it needs no guard of its own.
**Consequences.** Every write a graduate makes is visible and reversible at the moment it happens, and the offline guarantee is enforced by the process, not by convention.

## 020. Sixteen model turns per request by default

**Context.** The first calibration on local Glimmer (15 calibration tasks, blank harness, 2026-10-27) passed every overdue task (5/5) and failed every invoice and scheduling task (0/10). The traces showed why: Glimmer makes one tool call per turn, and the write tasks need about ten reads (job, customer, technician, rate, parts, prices, tax, policy; or the request, technicians, three pages of bookings, travel) before they can compute and write. Every write attempt hit the 8-turn limit while still reading. Its tool use up to that point was sound.
**Decision.** The default `max_steps` is 16. The mentor can still change it in a harness like any decoding setting.
**Consequences.** Bare failures now come from what the student gets wrong, not from a cap it can't see. Write attempts take longer on a local student (each turn is about 17 seconds), which makes a hosted student more important for training runs.

## 021. One bounded revision of the sample job, then a freeze

**Context.** On hosted Glimmer with a blank harness, the first version of the sample job scored 34/45 on dev (76%: invoices 9/15, overdue 13/15, scheduling 12/15) against an 85% requirement. That leaves little room for any method, and a mentor that only reads the policy would likely write the same invoice tool Architect found in its first round, so the comparison could show nothing about the value of watching attempts. GPT-6 Astra advised one bounded revision with realistic complications and no hidden rules, then a freeze, keeping the first version as a secondary benchmark.
**Decision.** Version 2 (`examples/home-services/job/`, the sample the app ships) adds overdue questions over groups of customers (a city, or a zone narrowed to plan members or one payment term; 5 to 60 customers), which a careful agent answers in a few filtered reads while a lazy 50-row read silently truncates; morning and afternoon windows for scheduling requests; and paired boundary cases inside the existing rules (labor minutes on and just past a quarter hour, invoices due today versus yesterday, payments dated today versus tomorrow, a slot that travel to the next booking invalidates). Every rule is in the policy with a worked example, the reference answers use only the student's own tool operations and limits (at most 4 reads for any overdue question), and no answer value is right for more than three tasks of a type. Version 1 stays byte for byte in `job-v1/`. Both are frozen from here: no further changes before the comparison runs.
Measured after the revision, same student and blank harness: dev 36/45 (80%: invoices 9/15, overdue 14/15, scheduling 13/15) and calibration 11/15. The estimate had been about 52%; Glimmer handled the group questions and the windows well, and invoices still fail mostly by running out of turns while pricing line by line. Following the same advice (don't keep hardening until a method wins), the tasks stay as they are.
The readiness bar is raised from 85% to 95% for both versions, before any comparison ran. These tasks write invoices and bookings into a business's records; one wrong row in seven is more than an office would accept from an assistant, and one in twenty is about the most it would.
**Consequences.** Comparison results are reported on version 2, with version 1 as a secondary result. Changing the tasks after seeing how the methods do would bias the comparison, so it doesn't happen. With the bare student near 80%, the room for any method is the last 15 points and the time per answer, so the README reports latency and turns per task alongside pass rates.

## 022. A change that clears the keep check is measured again before it's kept

**Context.** Before the comparison runs, a noise pilot ran the sample job's starting harness on all 45 dev tasks three times under different student seeds (hosted Glimmer, its recommended temperature 1): 39, 33 and 36 passes, with 14 tasks changing outcome between runs. A second pilot at temperature 0.6 gave 37, 38 and 34 with 15 tasks flipping, so lower temperature brought no clear benefit and decoding stays at the model's recommended settings. Pooled over the six runs, 21 of the 45 tasks are unstable and one dev run's score has a standard deviation of about 2.3 tasks; invoices carry most of it (11 of 15 unstable). Simulating the keep check with those per-task pass rates, a change that does nothing cleared the old rule (+2 net dev passes, no type down more than one, one run each) about 28% of the time.
**Decision.** A change that clears the limits on its first measurement has both versions measured again on dev under new seeds, the round's next `devRepeats` seeds, and is kept only if the totals over both measurements clear the limits for twice the runs (+4 net, no type down more than two, with one repeat). The second measurement needn't clear the limits alone. Changes that miss on the first measurement are reverted without the second, so the extra cost falls only on promising changes. The per-type limit stays at one per run: loosening it to two raised the share of kept trade-offs (one type up, another down) from about 9% to 22% in the same simulation. Patience for the sample job rises from three to four reverts in a row, since a real three-task gain now clears the check only about half the time. The same rule serves Architect and self-reflection.
In simulation with the pilot's task pass rates, a do-nothing change is kept 11 to 15% of the time (depending on whether rates come from one pilot or both and whether they are smoothed), a change worth about 4.5 tasks 78 to 83%, and one worth about 2 tasks 43 to 47%; each round runs 2 to 4 dev measurements of 45 tasks instead of 2. GPT-6 Astra reviewed the rule before it was built and agreed, with three conditions this follows: store both measurements (lineage and rounds keep `firstMeasurement` beside the pooled scores), call kept effects selection-conditioned dev estimates, and plot pass rates rather than mixed totals.
**Consequences.** The 13% figure is a per-proposal estimate from a small pilot, not an experiment-wide error rate; kept changes' measured effects still lean upward because the same measurements decided to keep them, and dev curves reflect repeated use of one dev set. Claims about methods rest on the locked test. Dev scores can now have different totals within a run (45 or 90 with one repeat), so anything that compares them uses rates or per-run counts.

## 023. One fix for a reply the runner can't use

**Context.** The first comparison run of the one-shot baseline lost its only reply to a format slip: Spark wrote its worked examples with `args` where the harness format says `arguments`, and left out `tool_call_id` on tool turns. The change set was refused, so the "one-shot" result would have been the blank starting harness: a measure of one formatting mistake, not of writing a harness without watching the student. Architect and self-reflection lose a whole round to the same kind of slip, and two refused rounds in a row end training.
**Decision.** When the runner can't use a reply (it isn't a hypothesis, or the harness refuses its change set), the round's author gets the same request again followed by its own reply and the runner's reason, and one more answer. If that can't be used either, the round is rejected as before. The fix adds nothing but the refusal reason, so the one-shot author still never sees an attempt, and every method gets exactly the same chance. The fix call is charged to its round and saved beside the first (`mentor/round-<n>-fix-1.json`); the stored reply records whether it is a fix, so a restart never asks twice. The mentor's guide to the harness now shows the exact shape of each example message.
**Consequences.** A round can cost two author calls. Comparison runs started before this was in place are discarded and run again.

## 024. A tool may name a data file without its extension

**Context.** In the restarted seed 1, Spark's one-shot harness called `ctx.readTable("jobs")` in its pricing tool, and the file is `jobs.csv`. The mentor's guide said `ctx.readTable(name, ...)` without saying the name keeps its extension, so the tool failed on every call and the student spent its steps retrying it: dev fell from 38/45 to 15/45. The student can correct a wrong file name after the error message; a tool's code can't, and one-shot never sees an attempt.
**Decision.** In the sandbox, a name that isn't a file but is exactly one file's name without its extension refers to that file. The mentor's guide now describes `ctx` precisely: file names as listed, rows as objects keyed by column with text values and null for empty cells, every matching row unless a limit is passed, and the same filters as `read_table`. The student's own tools still take exact names.
**Consequences.** The runs of that start were discarded and seed 1 began again with this in place.

## 025. A change set's tools must load before it is measured

**Context.** The same one-shot harness had a second tool, `find_slot`, with a typo (`var start Day=null;`) that no JavaScript engine parses. Every scheduling task called it, got a syntax error back, and ran out of steps. A tool that doesn't load is as detectable before any task runs as a malformed example file, and it costs Architect a whole measured round to find out from traces.
**Decision.** When a change set adds or edits a tool, the runner loads the tool's code in the sandbox before measuring anything: only the code's top level runs, the tool isn't called and sees no data. A tool that doesn't load (a syntax error, no `run`, a top level that throws or runs too long) makes the change set unusable, with the reason and line, so the author gets its one fix (decision 023). The sandbox now reports the line of a syntax error too.
**Consequences.** All methods get the same check. A tool that loads but computes the wrong thing is still found only by attempts, which is what the comparison is about.

## 026. A blank start begins with a whole draft, and the comparison shares it

**Context.** The one-shot baseline is there to test whether watching the student adds anything (SPEC). Architect started from the job's starting harness, which is blank for the sample job, and made one change per round, so within eight rounds it built a whole harness piece by piece while one-shot wrote one in a single reply. In seed 1, with decisions 023 to 025 in place, Spark's one-shot draft took dev from 35/45 to 45/45. A loss to that baseline would then say "writing piece by piece is slower" as much as "watching adds nothing". No Architect or self-reflection run had been made in any start of the comparison. This is a change to the protocol made after seeing that one-shot score, and it is reported as one.
**Decision.** In the product, a run that starts from a blank harness begins with a draft round: the author writes a whole harness from the job setup and the train examples with their expected answers, with no attempts, as one-shot does, and the draft is kept as the starting point. Every later round is one watched change under the keep rule. A run that starts from a template or an imported harness refines it directly. In the comparison, each seed's draft is written once and shared: one-shot stops there, while Architect and self-reflection start from that exact draft with the seven rounds left and the draft's mentor spend taken off their cap. Self-reflection is then the student refining the mentor's draft, which compares the two refiners from the same starting point. GPT-6 Astra reviewed this and advised keeping the draft unconditionally and forking one draft per seed.
**Consequences.** A draft is measured once, against the run's baseline, since it is kept whatever it scores; a draft refused even after its fix is followed by another draft rather than by building piece by piece; and a seed whose one-shot draft was refused has nothing to share, so its Architect and self-reflection runs draft for themselves (all three settled after a second independent review). What the comparison can test is "watched refinement adds value over stopping after the draft". When a draft already meets the 95% bar on dev, refinement stops at once (target met) and Architect tests the same harness one-shot did; the README says so plainly where it happens, and reports each draft's dev score, every kept change, paired test outcomes, costs, and every earlier start of seed 1 with its fixes and cost.

## 027. Five seeds for the comparison

**Context.** With the shared draft (decision 026), a seed whose draft meets the bar costs about $2.50 of hosted student time: bare and one-shot, plus two refining runs that stop at once. Seed 1's draft passed 60/60 on the locked test, so the question three seeds can barely answer is how often a draft falls short, which is the only place watched refinement can show anything on this job.
**Decision.** Seeds 1 to 5 for all four methods, decided after seed 1's one-shot result and before any later seed ran. The order is fixed: seeds 2 to 5 run in sequence, and if the $50 cap on the hosted student key comes within $8, the remaining seeds are dropped and the README says which.
**Consequences.** Every seed is reported, including any that fail, with each draft's dev and test scores. The limit that matters turned out to be the account's prepaid credit ($10), not the key's $50 cap; it ran out minutes into seeds 2 to 5, which wait for more credit.

## 028. A second task family, where the data is messier than its samples

**Context.** On the home-services job the policy states every rule with an example, and Spark's first draft passed every check task before it saw an attempt, so the comparison can't show what watching adds (README, Results). The mentor sees each data file through its columns, row count and a few sample rows; only the student's attempts touch every row. Real office files are rarely as clean as their first rows.
**Decision.** Build a second job in a different domain whose policy, like the first, states every rule with a worked example and hides nothing, but whose data files are messy the way exported spreadsheets are (several date formats, money written with symbols and separators, stray spaces and letter case, a few legacy codes), with the messy rows spread through each file rather than in the first rows. The reference answers and checker handle every variant. Its difficulty is calibrated on the bare student like the first job's, before any method runs on it, and its comparison uses the same protocol (decisions 022 to 027). Decided after seeing seed 1 of the first job; the rationale is that samples are what a mentor sees and attempts are what watching adds, and the result is reported whichever method it favors.
**Consequences.** If Spark's first draft handles the messy rows anyway, this job ends at the ceiling too, and the README says so. Running it needs hosted credit, which waits on the owner.


## 029. A model call that fails in passing is tried again before the run pauses

**Context.** Hosted models sometimes drop a reply partway: on 2026-10-28 OpenRouter cut three runs' replies within the same minute, and each run paused until someone resumed it. In the app that means a training run left overnight stops for good at the first hiccup, though a minute later the same call works.
**Decision.** When a step fails with an adapter error that usually passes on its own (a busy or rate-limited server, a dropped connection, a reply cut off partway, but not a 504), the run logs it, waits 30 seconds, and plans its next step again, which redoes only the attempts that hadn't finished. A second failure waits 90 seconds. A third with no attempt finished since the one before pauses the run with the reason, as before. Errors that waiting won't fix (a refused key, no credit, a bad request) pause at once.
**Consequences.** The run stays active while it waits, so the wall clock keeps counting and a pause or stop takes effect once the wait ends. A local runtime that isn't running gets two minutes to come back before the run pauses.

## 030. Graduates run on a coding-agent harness built on Architect's own loop

**Context.** The expanded spec assumed Pi was already the graduates' agent harness. It isn't: task evaluation and the workspace share Architect's own loop, and the student's tools were table tools written for one kind of job (`read_table`, `append_rows`, `calculate`). The owner (Oct 28): "Pi is a good base to start off. if you think a custom version is better thats fine but it should be a classic coding-agent-like harness since those are the most versatile."
**Decision.** Keep the loop and make the harness a coding agent's: built-in `read`, `ls`, `glob`, `grep`, `write`, `edit`, `append` and `run`, where `run` executes JavaScript in the QuickJS sandbox in place of a shell; standing instructions in `AGENTS.md`; skills as `skills/<name>/SKILL.md`, listed by name and read on demand; helpers as typed sandboxed tools; paths are logical (`data/`, `output/`) and each installation binds them. Pi itself isn't embedded: its bash tool can't be kept offline and sandboxed on Windows, and the loop already owns replay, approvals, budgets and the network guard.
**Consequences.** Results measured with the table tools (the first comparison, seed 1) describe the old runtime and are labeled so. The sample jobs' reference solutions move to the new tools.

**As built (Oct 28).** Where the build differs from the plan above, or settles something it left open:
- Skills are read with `read` on `skills/<name>/SKILL.md`; there is no `load_skill`. Retrieval rules can still put a skill's steps in the system prompt up front. A skill folder holds only its `SKILL.md`, whose front matter is `name` (the folder) and `description`.
- `output/` exists only when the job's `data.output` says so. Training gives each attempt an empty scratch one, which the checker's validators don't read yet; the workspace keeps it as a folder inside the graduate's data folder until installations get their own bindings.
- `grep` runs in the sandbox child like `run`, so a pattern that backtracks without end is stopped instead of hanging the engine. Both get 5 seconds a call; helpers keep 2. `glob` matches in one pass per part of its pattern, so no pattern can stall the engine either, and a pattern it can't read is an error the agent sees.
- `run`'s `csv.parse` gives every cell as text and an empty cell as `""`, the usual JavaScript habit; helpers' `ctx.readTable` keeps `null` for an empty cell, as it always did. Helpers may also name a data file by its path, `data/jobs.csv`.
- A write may not break a table: the new text must parse as CSV and keep the header line, or nothing changes and the agent is told why. Every change is diffed by line, and a change to a table also by row; the workspace's approval card shows the rows for a table and the lines for any other file. A change too large to diff quickly (thousands of rows rewritten) is recorded as the whole file replaced. In a live `output/`, a new file never replaces one the folder holds but didn't open (a file over 1 MB, say), never goes through a link, and can't differ from an existing name only in capitals.
- Tools accept `file_path` or `file` for `path`, and counts written as text ("10"), because small models send both. A call to one of the table tools gets an error that names the tool to use instead, so a harness written for them can recover; a format 1 harness's skills and examples are not rewritten and still mention those tools.
- Harness format 2 is migrated in code when a format 1 folder is read: `system.md` becomes `AGENTS.md`, each `skills/<slug>.md` becomes `skills/<slug>/SKILL.md` with its summary as the description and its old title as a heading, and a helper named like one of the new built-in tools (`grep`, `run`) becomes `<name>_helper`. The folder is checked against the hash it was saved with, then gets a new hash over its format 2 files. So an older graduate opens and runs on the new tools in the workspace, but a run frozen before this change can't take or repeat its locked test, and its graduate can't be rewritten on acceptance: its record belongs to the table tools.
- Every attempt's trace records what it started from: a sha256 of each data file as its bytes stood at the start, the harness hash, the tools' version (`architect-tools/2`), the sampler seed, the decoding settings and the business date. Each write records its diff and whether it was applied, and the trace ends with every file's change since the start. Locked-test traces are still not kept.
- The sample jobs' reference solutions read the policy, send `run` code that fetches the rows a task needs and adds up its numbers, and append the new row; the TypeScript policy code still decides. Their tests replay every call of every task through the engine's own tools, compare the text the agent gets back, and grade the end state with the real checker. The worst cases are 5 tool calls and 12,341 characters of results on the returns desk, and 3 calls and 21,028 characters on home services, against 16 turns and 24,000 characters; no limit changed. The task files didn't change: the generators still write them byte for byte.

## 034. Any mentor by key, sign-in or a local runtime, and no guessed prices

**Context.** The owner asked on 2026-10-28 for Architect to be truly model agnostic: mentors from other providers by API key or sign-in, or a model running on the same computer, and any local model as the student, with Meta's models kept as the defaults. Three parts of that aren't settled by the code alone: where a key may be sent, how a desktop app signs in without a server of its own, and what the dollar cap does when nobody knows a model's price. The same day the owner asked for the student to run on the GPU; Glimmer's 4-bit build needs about 19.5 GB and doesn't fit a 12 GB card.
**Decision.**
- *Keys.* A provider's key is stored encrypted under the provider's name and goes only to that provider's hosts, over HTTPS. A key for an endpoint added by address is stored under that exact host and port and goes nowhere else; plain HTTP is allowed only to this computer. Main checks a key with its provider before storing it, so a refused key never lands in the store. Ollama and LM Studio on this computer are found without any setup and need no key.
- *Sign-in.* OpenRouter documents a sign-in that hands any desktop app its own API key, with no app to register: PKCE with a callback on localhost or 127.0.0.1 on any port. Main opens OpenRouter's page in the system browser through the same checked link route as every other external page, waits once on 127.0.0.1 for the callback, matches its `state`, and exchanges the code for a key, which is stored like a pasted one. It stops on cancel, on a decline, after 10 minutes (when OpenRouter's codes expire), or if no port can be opened. No other sign-in is built. Hugging Face documents one that would fit (a public OAuth app with PKCE, a loopback redirect on any port, and an `inference-api` scope for its Inference Providers), but it needs an app registered with Hugging Face first, so it is a proposal for the owner. Google's OAuth for the Gemini API needs a client in the developer's own Cloud project and scope verification for outside users, and OpenAI and Anthropic document no sign-in for other apps.
- *Prices.* A mentor's price comes from its preset, from OpenRouter's listing (saved with the mentor and sent as `provider.max_price`, so OpenRouter can't route to a provider that charges more), from a price the user enters, or is zero for a model on this computer. Otherwise the price is unknown, and Architect doesn't guess: Define asks for the price before training can start, and the budget gate refuses any mentor call it can't price. When OpenRouter reports what a call cost, that amount is what counts against the cap.
- *GPU.* Architect reads the GPU (nvidia-smi, or Apple silicon's shared memory), shows for each local model whether it runs entirely on the GPU, and recommends the largest Glimmer build that fits. For a 12 GB card that is a 2-bit build, which Architect installs itself: it pulls Unsloth's UD-IQ2_XXS file and makes a text-only Ollama model from its weights with Glimmer's own renderer and parser, so tools and thinking work as they do with the library build. The 4-bit build stays the default wherever it fits.
**Consequences.** Every invariant holds as before: the graduate and the workspace still never construct a mentor, and a graduate's student must be on a loopback address. A mentor with no known price costs one extra step instead of a cap that can't be kept. Mentors on generic OpenAI-compatible services get the schema in the prompt and one repair call, so they may need a repair more often than Meta, OpenAI, Anthropic or Gemini, which hold replies to the schema. Live checks and what wasn't checked are listed in `docs/MODELS.md`; the OpenRouter sign-in and the GPU build's install are tested against fakes, since the account has no credit and GPU work is paused.

## 035. How the adapter runtime and the training worker are built, and where they differ from 031 and 033

**Context.** Decisions 031 and 033 set the direction on Oct 28. Building them settled details they left open, and three points differ from them: llama-server is found but not installed, the compute cap lives with the training records for now, and a job's inputs and outputs share one private repository. The real training run itself still waits on the owner's Hugging Face token.
**Decision.**
- *Finding llama-server.* The path set in Settings, else the first `llama-server` on PATH, and nothing else, so no developer's install is assumed. Builds older than 10358, the first with Muse Glimmer, are refused. Installing one for the user is deferred (031 said "finds or installs").
- *Base weights.* The GGUF comes from Ollama's store through the model's manifest, in either layout Ollama writes (`docs/MODELS.md`). Its size must match the manifest and it must be GGUF. A model whose Ollama copy carries an adapter layer, or isn't stored as GGUF, is refused rather than served without it.
- *Adapters.* Each adapter is checked against the base before anything loads: same architecture, every adapted weight in the base, pairs shaped [n_in, r] and [r, n_out], tensor types the converter writes, no embedding adapters. They load unapplied (`--lora` with `--lora-init-without-apply`) and every request names every loaded adapter with its scale, so one server measures a candidate with and without its adapter. A change of scales between requests clears the server's prompt cache, so measurements should group requests by adapter.
- *The server process.* 127.0.0.1 on a free port, with a fresh key per start read from a file, so a web page on the same computer can't use it; `--jinja`, `--no-webui`, `--offline`, one slot, the context size and GPU layers, and the quiet-mode thread cap as `--threads` and `--threads-batch`. Before it starts, Ollama is asked to unload every model and the start waits until it has. A request's hold on the server is taken in the same step that hands the server over, and a server whose launch changes (other adapters, another thread cap) restarts only when no request holds it; one caller giving up on a start doesn't call it off for the others, while a stop calls it off at any stage. It stops after 10 idle minutes; `--sleep-idle-seconds` makes a server the app lost track of unload its model by itself, and the next start stops such a server if it answers to the saved key. Failures are named from the server's own log lines (the model, memory, an adapter, a port, a timeout) and reach a student as an `AdapterError`, so an evaluation stops on them instead of scoring a wrong answer.
- *Students.* A llama.cpp student in `packages/adapters` is bound to one adapter selection through a small `LlamaServerAccess` contract in `packages/shared`; students on the same base and adapter set share one server and one copy of the weights, and a student that lets go stops the server only once no other student has a request in flight. Graduates without an adapter keep running on Ollama, as 031 says.
- *Training on Hugging Face Jobs.* Each job gets one private model repository: the app commits the job's inputs there (job file, dataset, recipe scripts; at most 10 MB per file, since the app doesn't speak LFS), and the job reads them at that commit and uploads its outputs beside them, where the app downloads them at a fixed commit and checks each against the job's manifest of hashes. The job runs the recipe's image pinned by digest, its token as an encrypted job secret, Architect's job id as an environment tag (how a job is found again after a crash), and a timeout equal to the compute the budget allowed, so the Hub stops it there even if the app is closed. Jobs run on any Hugging Face account or organization with a positive credit balance (the Hub's Jobs guide, checked Oct 28).
- *Durable jobs.* A job's record is written before the backend hears of it, keyed by dataset, base revision, recipe, backend and hardware, so the same job is never sent twice; a failed or cancelled one may be sent again. Changes to one job (its submission, checks, cancels, downloads) run one at a time, each from the record as stored. When the provider's answer to a submission is lost and the provider can't be asked whether it has the job, the job stays as sent and is asked about again on the next check, rather than risk sending it twice. After a restart, unfinished jobs are picked up where they were: a submission cut off is found by its tag (or marked as never received), running jobs are polled, finished ones are downloaded. Outputs that are missing or don't check out fail the job; a dropped connection is tried again. Records are files under `<data>/training/jobs/<id>/` behind a store interface, ready to move into the database.
- *Compute cap.* A budget line beside mentor dollars, per scope (a job or run id): jobs that stopped running count at what they cost and running ones at their whole authorization. New jobs are made one at a time per scope, so two can't be paid from the same dollars. A new job is cut to what is left at the hardware's price and refused when that is under 35 minutes (10 for setup, 15 to convert and upload, at least 10 to train) or when the price isn't known; the worker also cancels a job it sees running two minutes past its limit. Compute time runs from when the job began (bounded by when it was last seen waiting for hardware, or else made) to the end the worker observes, capped at the authorization, since the provider stops the job there: an upper bound on what is billed, and time spent waiting for hardware counts toward neither cost nor the worker's stop. The one priced flavor is the L40S (`l40sx1`, 48 GB) at $1.80 an hour, as the Hub's Jobs hardware table listed it on Oct 28. The cap sits with the training records until versioned job contracts can carry it in the job's budget (033 put it beside mentor dollars without saying where it is kept).
- *The recipe.* PEFT with bitsandbytes QLoRA, not Unsloth: Unsloth patches transformers at import and changes fast, and the L40S has room for plain QLoRA. Pinned in `trainer/recipe.json`: the PyTorch 2.11 CUDA 12.8 runtime image by digest; transformers 5.19.0, peft 0.20.0, bitsandbytes 0.50.1, accelerate 1.14.0, tokenizers 0.23.3, safetensors 0.8.0 and huggingface_hub 1.33.0, the versions in this PC's package cache; NF4 with double quantization and bf16 compute; LoRA r 16, alpha 32, dropout 0.05 on the text decoder's q, k, v, o and attention-gate projections and the MLP's gate, up and down, never the vision tower, the embeddings or the head; plain alpha / r scaling with no rsLoRA or DoRA, which llama.cpp applies as trained; 2 epochs at 1e-4 with a cosine schedule, batch 1 with 8 accumulation steps, up to 16,384 tokens, seed 1234. The conversion is llama.cpp's `convert_lora_to_gguf.py` at commit 60eeeb6 (b10472, the build that loaded the probe adapter here) in its own environment with that commit's requirements, writing f16.
- *Targets.* Only assistant turns flagged for training are labels, found by rendering the conversation with the model's own chat template. A template that renders a turn differently further on is refused, and an example longer than the limit is skipped and listed, never cut. Checked on Oct 28 with Glimmer's own template (from the 2-bit build's metadata, rendered as transformers renders it) on an example from the dataset builder: the targets were exactly the read call (` to=read<|message|><atem:function_calls>...<|eot|>`) and the answer with its reasoning (` to=self<|message|>...<|eom|><|start|>assistant to=user<|message|>ANSWER: ...<|eot|>`), each from just after `<|start|>assistant`, with the user's words and the tool's output left as context.
- *What may be trained on.* Episodes from train tasks and accepted workspace corrections. An episode from another split, or one the vault's leak detector flags, stops the dataset build. Episodes whose data may not leave the computer are left out of remote datasets, and the worker refuses a dataset that holds any.
- *Stand-in.* As 033 says. Its label is in the record, its manifest, the adapter's GGUF metadata and every line the app writes about the job; its adapter is a no-op (lora_b is zero), and `countsAsRealTraining` is false for it whatever else its record says.
**Consequences.** A01 stays blocked until the owner adds a Hugging Face token with Jobs access. Everything up to a real job is tested against fakes (a stand-in llama-server process, a fake Hub with a separate download host) and against this PC's real files without loading a model. The first real job will show whether the pins and the converter work on Glimmer; a wrong pin costs the setup minutes, not a full job, since the recipe checks its inputs before installing anything. The desktop app is not wired yet: Settings needs llama-server's path and a Hugging Face key service (`huggingface` isn't in the secret store's services), the `trainer/` folder must ship as an app resource, and the engine host must call `resume` when it starts.

## 036. A task that asks only for an answer must leave the data as it found it

**Context.** With the coding-agent tools an attempt can change any writable table. The built-in comparator graded answer and facts tasks without looking at the files, and the returns desk's validators checked only the table each task writes (order questions only the ANSWER line). So an attempt could book an unasked pickup while recording a return, or add a row while answering a question, and still pass. A second opinion on the evaluation plan found this before any measurement on the new runtime.
**Decision.** The engine fails an answer or facts task when the attempt changed any table, comparing rows and columns, so a rewrite that kept every row counts as unchanged. The returns desk's validators fail an attempt that changed a writable table other than its own: a return adds its row to `returns.csv` only, a pickup to `pickups.csv` only, and an order question changes neither. The reason names the table, the way other reasons name a field. Text files and `output/` are outside the check: the sample jobs' text files are read-only, and neither job enables `output/`.
**Consequences.** The tasks didn't change, and the reference solutions still pass. Results from before this change, including the Oct 27 calibration on the old tools, aren't comparable with measurements on the new runtime, which all start after it.

## 038. A graduate version is a portable package

**Context.** A graduate was a folder written once after its locked test (`graduate.yaml`, the harness files, the report card, the lineage), and it opened only on the computer that trained it: the workspace read its job and copied the job's data from the run's folders, `graduate.yaml` held the student's endpoint, the hash covered only the harness files, and accepting it rewrote the folder. The expanded spec (sections 10 and 11) asks for one portable, immutable artifact that the desktop app, the CLI, export, import and the Hub all use.
**Decision.** A version is a folder with `graduate.json` (schema 2, snake_case keys like every other file), `harness/` (the harness folder exactly as `@architect/harness` writes it, so the coding-agent format of decision 030 drops in), `evidence/` (the author's report card and a change history), `adapter/` when there is one, and `resources/<name>/` only when the author chooses to share a resource. The manifest has the sections of the spec's table: identity (agent id, version, parent, when and how it was made), the job contract it was tested against, the model (a base model named the way runtimes name it, with its digest, and the adapter's path, format and sha256), the harness (format, hash, the round that made it), logical resources (`data`, `output`, named ones; required or not, accepted types, the files and columns the contract names, the access it asks for), requirements (where it was tested, measured latency, estimated memory, limitations), evidence (labelled "Evaluated on the author's configuration", with its status: ready, experimental or unevaluated), verification (the checks an installation can run, never the locked test), the sha256 and size of every other file, and terms. Nothing in it belongs to one computer: no endpoint, folder, chat or key. The change history keeps each round's title, files, predicted and measured effect and decision; the mentor's diagnosis, the reasoning behind its prediction and the task ids are left out, since they quote attempts on the author's data, and the full lineage stays with the run.
The transport is `<name>-v<n>.architect.zip`: stored or deflated entries, UTF-8 names, fixed timestamps, so the same files always make the same archive. A version's identity is the sha256 of its `graduate.json`, recorded when it is installed and checked, with every file's checksum, each time it opens. Files that file managers drop into folders and archives (`.DS_Store`, `._` files, `__MACOSX`, `Thumbs.db`, `desktop.ini`) are passed over, never counted as part of a package.
An import (a folder or a zip) is checked in a staging folder before anything in it runs: every entry name is a portable relative path (no `..`, drive letters, backslashes, hidden files, device names, or two names for one file on Windows or macOS); links, junctions and special files are refused whatever system made the archive; no more than 2,000 files, 2 GB a file and 4 GB in all, a directory no larger than its entries need, inflation stops at each entry's declared size, and an entry that expands more than 200 times is refused as a bomb; entries must not overlap and their headers must agree; the manifest's schema number is read before its fields; the files must be exactly the ones listed, byte for byte; it must run on a runtime an installation here can serve (an adapter needs one that loads adapters); its harness format must be one this build reads; and its `data/` resource must name the files its contract does. A format 1 folder's files are weighed before they are parsed, and a harness larger than any harness may be is refused before it is read. Only then is the harness parsed (read, never run) and compared with its hash. Tools first load in the sandbox in the installation checks, after the version is installed.
An import never replaces a version. The same package installed twice is found by its digest. A package continues an agent here only when this computer has the version its manifest names as parent, matched by digest; otherwise it becomes a new agent, under its own id when that is free and a new one when not, since anyone holding an export knows an agent's id.
What a computer gives a graduate is its installation, kept in SQLite and never exported: the local model endpoint, a folder for each logical resource, and grants (the write mode and each resource's access). A package's requested access is not a grant: an import grants only what the request names, capped at what the package asks for, and an import that names nothing grants nothing, on any computer. A graduate made here gets its job's model endpoint, its own copy of the job's data for `data/` and the job's write mode, so the same computer never needs an export. Installation checks (platform, memory, runtime and adapter fit; the harness hash; tools load; folders bound with the files and columns named; the base model served, and the same build when the runtime can tell; a short request, timed, with the model unloaded afterwards) are labelled "Installation checks on this computer" and stored apart from the author's evidence, which never changes. Ready means every check passed; needs attention means something the user can fix (a folder to bind, a model to download, a computer the author didn't test on); blocked means it can't run here, and the workspace won't open it. With no folder bound to `data/` a graduate opens no files at all.
An export writes exactly what its review scanned: the version's folder byte for byte unless the user opts into a resource, and then the resource's named files and a manifest that lists them. The best-effort scan (stored key values, common key shapes, user and app folders, also as JSON escapes them) masks everything it finds in every excerpt, and an export with findings goes ahead only when the request names the digest of the findings the user reviewed. The archive is written before the folder moves into place, so a failure leaves nothing behind. Graduates in format 1 are converted in code: when the engine starts, for those already here (their endpoint becomes the installation, their workspace folder and write mode are kept, and their old files stay where they are), and on import.
An adapter is named the way the adapter runtime of decision 035 checks and loads it. In the manifest's words: `model.base.name` is the base's name in Ollama's store (the runtime's `ServeRequest.model`); `model.adapter.base_digest` is the digest of the GGUF file that store holds for it (`OllamaModelFile.digest`, `sha256:<hex>`, which the llama.cpp student reports), and installation checks block a version whose served base has another; `model.adapter.sha256` and `size_bytes` are the GGUF LoRA's, as the training job's `gguf_lora` artifact records them and as the integrity section must list them, or the manifest is refused; `model.adapter.scale` is the scale every request applies (`ServeRequest.scales`); `model.adapter.training_job_id` is the `TrainingJobRecord.id` that made it, when one did, and `stand_in` marks an adapter from the stand-in backend (its `artifacts.standIn`, or a record that isn't `real`), which also adds a limitation saying so. `model.base.digest` stays the digest the runtime that tested the version reported. A version opens with the runtime's request ready (`ActiveVersion.adapter`: the installation's name for the base, the version's own adapter file, its scale), so a rollback hands the runtime the earlier version's harness and adapter together. Only GGUF LoRA adapters go into packages; PEFT files stay with the training job.
**Consequences.** A graduate opens anywhere a compatible runtime serves its base, and the same computer needs no setup to use a new one. Until an installation can serve a version with llama.cpp (decision 035), a package with an adapter exports byte for byte but is refused at import, and a version with one is never opened on Ollama, which would run it without its adapter. The ZIP reading and writing are written here and tested with archives built byte by byte. Hugging Face publishing will upload the same folder; its table exists and is unused so far.

## 039. Every graduate is an agent with immutable versions

**Context.** A graduate had one version: accepting it rewrote its folder, importing refused an id already present, chats didn't record what answered, and a job's contract was overwritten whenever the job was saved. Teach this and Improve agent (spec section 8) need versions that never change, candidates kept apart from what the user runs, and the version recorded with every answer.
**Decision.** A `graduates` row is the agent; `graduate_versions` holds its versions (v1, v2 and on), each an immutable package folder under `graduates/<id>/versions/`. Only a version's state changes: candidate, accepted or rejected. The agent's active version is a pointer, and accepting and promoting are separate events, logged with rejections and rollbacks in `graduate_events`. An agent's first version is active from the start, since nothing else could be; any later one (an improvement, or an imported newer version) waits as a candidate until it is accepted and then promoted. Promotion and rollback move the pointer in one transaction, a rollback only to an earlier accepted version, and because a version's folder holds its harness and adapter together and is verified whenever it opens, they always switch together. A version imported from elsewhere never inherits permission to write without asking: promoting one turns "allow" back to "ask".
A chat records the version that was active when it started, and each reply the version that wrote it. A reply runs on one version, with one set of folders and grants, from start to finish; after a promotion, a rollback or a new binding, the workspace opens the graduate again before its next reply.
Job contracts have versions in `job_contracts`. Saving a job whose scope or success criteria differ from every recorded version adds a new one; renaming it doesn't. A graduate carries the contract version it was tested against, and a package refuses a locked-test result measured against another bar or other task types, so a new contract version never inherits an old graduation result.
An ask-mode write can fail instead of waiting: a message sent with `approvals: 'fail'` ends at the first write that needs approval, nothing is written, the model gets no further turn, and the reply's `failure` holds the change it wanted (`approval_required`). The CLI will use this.
**Consequences.** Migrations 9 to 13 add the tables and backfill chats and replies as version 1, which every earlier graduate becomes. Rejected and superseded versions stay on disk and in the records, so the history across versions stays complete. The screens still read a format 1 shaped view of the active version (`GraduateSummary.manifest`); the versions, import and export screens come next.

## 040. A migrated harness is known by its new hash, and keeps the hash it was tested with

**Context.** Harness format 2 (decision 030) reads a format 1 folder by checking it against the hash it was saved with, then migrating it in memory, which gives it a new hash. As built, that left graduates and runs from before the change stuck: a run frozen with the old hash couldn't take or repeat its locked test, and a graduate couldn't be accepted, since accepting rewrote its folder and the hash no longer matched.
**Decision.** A migrated harness is identified by its migrated hash from then on, and the old one stays as its provenance: `harness.meta.migrated_from` (in memory, never written to `harness.yaml`) and, in a package, `harness.migrated_from` name the format and the hash of the files as they were saved. A graduate made before versions becomes version 1 with the migrated harness's files and hash, and its package keeps the format 1 hash. A version's harness is always checked against its manifest as stored, so a package that keeps a format 1 harness is checked against the old hash and runs migrated. A run frozen in format 1 takes or repeats its locked test when its version's files still have the frozen hash; it is tested as it runs now, on the coding agent's tools, and its graduate's package records the old hash. Accepting never rewrites a version, so it can't fail on a hash.
**Consequences.** What was tested stays traceable to the files it was tested with, and every version opens, is accepted and rolls back like any other. The package says which kind of result it carries: a graduate made before the change lists that its locked test ran on the older format and its tools, and one frozen before and tested after lists that it was trained in the older format and migrated before its test. This replaces the part of 030's as-built notes that kept such runs from their locked test and such graduates from acceptance.

## 041. llama.cpp serves a version with an adapter on the base in Ollama's store, and its installation stays bound to Ollama

**Context.** Decisions 031 and 035 built the adapter runtime, and 038 named an adapter the way that runtime loads it, but nothing served one: a package with an adapter was refused at import, a version with one never opened, and the installation checks compared the adapter's `base_digest` with the digest Ollama's API reports, which Ollama derives from the model's manifest, not from its GGUF weights. The CLI will run graduates through the same agent host as the workspace. This refines 035 and 038.
**Decision.**
- *Which runtime.* The version decides it, not the installation. A version with an adapter runs on llama.cpp, with the base from Ollama's store under the name its installation gives it; a version without one runs on the installation's runtime, as before. So the installation of a version with an adapter stays bound to Ollama (`runtime: 'ollama'`, the base's name in Ollama's store), `llama.cpp` stays out of `BINDABLE_RUNTIMES`, and one agent rolls back from a version with an adapter to one without, or the other way, with nothing rebound. A version with an adapter whose installation names another runtime needs attention and isn't opened. This replaces 038's reading that such an installation would serve its model with llama.cpp.
- *Before serving.* The runtime's request carries the adapter's `base_digest` and its sha256, and the version's context length. Before any start, the runtime refuses a base whose GGUF in Ollama's store has another digest and an adapter file whose sha256 differs (worked out again only when the file's size or time changes). The agent host checks both when it opens a version, and a mismatch blocks it with the reason and the way out, which never replaces the model under its name, since other versions may use it: add the exact build under a name of its own and set the agent's model to it. A missing llama-server or a base not yet downloaded lets the version open; a reply then says what is missing, so installing it needs no reopening.
- *One server, the right files.* A launch names what each adapter file holds (its sha256, else its size and time), so an adapter replaced at the same path, as when an agent is removed and imported again under its id, restarts the server instead of being answered by the one it loaded before. The server runs with the version's context, which its chats' history is sized to. Closing a graduate with an adapter lets go of the server, and the engine's checks that load a model through it take turns, so one never finds it busy with another agent's adapter.
- *Checks and import.* `assertUsable` accepts a package with an adapter whenever it names an adapter runtime this build serves. Whether this computer can serve it is for the installation checks to say, never a refusal at import. The checks ask the runtime for every problem at once: no llama-server, a build older than 10358 and a base not in the store need attention, each with its fix (set its path or install llama.cpp; update it; download the base, with its size and the exact weights it must have); a base of another build or an adapter that isn't the file installed blocks. A new `adapter-runtime` check names the build found, and the model check's short request goes through llama.cpp with the adapter applied, its server stopped afterwards.
- *Two runtimes, one set of settings.* The agent host serves and the engine host checks, each with its own llama-server and its own folder (`local-runtime/workspace`, `local-runtime/engine`), since each stops a server it finds in its folder answering to its key. Both read the same settings at every start: the llama-server path, quiet mode's thread cap, and the Ollama whose models are unloaded first (the default student's, when it is on this computer), and both stop after 10 idle minutes, as 035 says. Main sends the agent host its settings with `host.configure` before any graduate opens and again on every change; the engine gets them in its start and settings messages. `createAgentHost` requires a runtime, so the CLI passes its own (`hostAdapterRuntime`, folder `local-runtime/cli`) and serves adapters the same way.
- *Quitting.* Main asks the agent host to stop instead of killing it, so it stops its llama-server before it exits. A server left behind by a crash is still stopped by the next start (035).
- *The setting.* The renderer can read `llamaServerPath` but not write it: Architect runs that program, so only a file the user picked in a dialog becomes it (`connections.chooseLlamaServer`). Settings › Models lists llama.cpp with its build, as too old with how to update it, or with what is missing, and checks it again on demand. The workspace's status line says "LoRA adapter", or "Stand-in adapter" for one from the stand-in backend.
- *Tests.* The runtime's `command`, the stand-in llama-server, now has its build checked like any other, so a test can make it too old. In the app, the stand-in runs through `ARCHITECT_LLAMA_SERVER_COMMAND`, a launch switch for tests only.
**Consequences.** A graduate with an adapter imports, opens and answers wherever llama-server 10358 or newer and the exact base are, in the workspace and through the agent host the CLI will share; A01 still waits on a real adapter. Not handled yet: an installation check that loads the model starts the engine's llama-server while the workspace's may be running, and after an adapter reply llama-server keeps the GPU for up to 10 idle minutes, which an Ollama graduate's next replies would share.

## 042. Failure-specific mentoring: verified lessons, one intervention per round, an experiment for every round

**Context.** The expanded spec (sections 6, 7, 8, 16 and 17) asks the mentor to point at the failure in a trace, show the right behavior from that point, prove the correction with the checker, teach with related practice, choose one bounded intervention, and leave a record of every attempt with its budget. As built before this, a round was one harness hypothesis judged on dev: nothing was replayed, no lesson was kept, adapters existed only as a runtime, and the workspace couldn't tell the mentor what went wrong in a reply. Two second opinions (GPT 6 Astra) set the requirements used here: answer-blind continuations in a fresh context, verified fixtures and clocks, whole-batch resume points, a bounded fallback that is labeled, an audit of intermediate writes, the student's prefix masked from training, stable category ids, the four-configuration comparison, and durable stages before any teaching call.

**Decision.**
- *Durable stages.* A round now moves through attempting, diagnosing, teaching, training or clarifying, then evaluating, each persisted, so a restart resumes at the stage it left without a second lesson, charge, training job or record. Lessons and experiments have ids derived from the run, round and item (`lsn_` and `exp_` plus a sha256 prefix), so writing one again replaces it. An attempt's identity includes its configuration: who acted (the student, or the mentor as a reference), the backend, and any adapter with its scale (`student`, `student/llama.cpp/<adapter>@<scale>`, `reference/<provider>/none`); older attempts read as `student`.
- *Diagnosis.* The mentor's reply names up to three findings on this round's failed train attempts, each with the model turn it suspects, step-referenced evidence, the cause, a category and the task type, and one intervention from the menu: procedure, retrieval, helper, weights or clarification, with its hypothesis, worked examples, practice per finding, estimated cost and verification plan. The runner checks every finding (a failed train attempt of this round, a turn inside it) and sets aside the rest with the reason. The menu offers only what this run can do (weights needs training compute and a local adapter runtime, clarification needs someone there to answer), and an intervention whose estimate exceeds what is left is refused and recorded, never silently trimmed. Categories belong to the job, keep their id forever, and are matched by id, then by slug, then created; a new slug can't reset a cap.
- *Teaching.* For each finding the runner rebuilds the attempt up to the turn before the suspected failure, at a whole tool batch: same harness hash, tool runtime, business date and data file hashes, replaying each call and comparing what it returned and wrote. If anything differs the replay fails; the environment is never repaired. The mentor's model then continues as the agent, in a fresh context that holds only the task's prompt, the harness and that prefix, with no expected value. If a try doesn't verify (the replay doesn't hold, or the continuation fails the checker or the audit), the runner tries one turn earlier, then a full demonstration of the task from the start, and the lesson records which (`fallback: none | earlier | full_task`). The checker grades the end state, and a mutation audit rejects corrections that pass while doing harm on the way: a declined write, an answer task that changed a table, a table changed and then restored, an original row removed. A verified lesson keeps a training episode whose targets are only the mentor's own turns; the student's prefix is context, never a target. Related practice takes other train tasks of the same task type (never the same family), ranked by how many findings share their category, and verifies each the same way. Caps: 6 lessons per category per run, 12 per task type; a category stops after 2 measured rounds without a dev gain, a type after 4 (a round refused before it taught or measured anything doesn't count). Every mentor turn as the agent passes the same gate as a mentor call (not released, no locked-test content, within the dollar cap) and is charged to the mentor budget, at the most it was allowed to cost when its reply doesn't say what it used; a refusal ends the round's teaching and, for budget or a leak, the run. A pause, a stop or the wall clock ends teaching between corrections, and the next session resumes at the next try. An error the mentor's model can't get past by waiting (a bad request, a content filter) rejects that try with the reason instead of stalling the run, and a mentor whose model can't act as the agent here (Anthropic's API, for now) keeps teaching off the menu.
- *Candidates.* A procedure, retrieval or helper intervention is a harness change; worked examples (at most two, from verified lessons) become `examples/lesson-<round>-<n>.json` with a retrieval rule that loads them for the finding's task type. A change that writes train answers into the harness (a tool holding any train answer, or a file holding the values of two or more train tasks) is refused as a lookup table; worked examples may show a train answer. A draft is measured as a whole harness, whatever intervention its reply names. A weights intervention builds a dataset from the round's verified lessons plus at most 8 earlier ones as seeded rehearsal, submits it to the training worker under the run's id with an idempotency key from the dataset, and waits in 30 second steps on the run's clock. A clarification asks the person one question; the run waits until they answer, the answer reaches the mentor in later rounds, and an answer that changes what counts as success stops the run, since only a new job contract can change it.
- *Evaluation.* The keep rule is unchanged (decisions 007 and 022: a margin on paired dev measurements, then a confirming measurement), and hard gates come after it: every dev write within the job's writable files, p95 latency within the job's limit, and never an adapter from the stand-in backend. A weights round is measured in four configurations with the same backend, base, decoding and seeds: H0/A0, H1/A0, H0/A1, H1/A1, where H1 is the round's harness and A1 its adapter; a measurement reused from earlier says where it came from. Every round that tries a change ends in one experiment record with its kind, inputs (lessons, findings, intervention), measurements, gates, budget (mentor dollars and tokens, student dollars and tokens, compute dollars and minutes, examples, trained tokens, attempts, minutes) and a disposition: kept, reverted, rejected (harmful, or a gate failed), invalid (refused before measurement) or stopped. A failed hard gate always rejects. A clarification round tries no change, so it records its question and answer on its intervention and no experiment; the progress view counts clarifications apart. Progress and the capability breakdown are computed from these records only. Weights are offered only where they can work: a training worker, an adapter runtime, a locked test on the local student (the hosted copy can't load an adapter), and a real backend; the stand-in, which trains nothing, is offered only to tests.
- *Freezing and the locked test.* The frozen graduate records its whole configuration: backend, adapter (id, file, sha256, scale, the base's digest) and decoding. The locked test runs exactly that, refuses an adapter whose file changed, and repeats on the seeds the job declares in advance (`evaluation.lockedTestSeeds`, 101 and 102 in decision 037). Each repeat is stored with its seed and shown on the card, and a scenario passes only if every repeat passes: repeats are never counted as more scenarios.
- *Spark as a reference.* On a finished run, Spark can act as the agent on the run's dev tasks or its locked test, with the frozen harness, as a comparison. It has its own disclosed dollar cap, its own gate and its own configuration key, its costs are filed under `reference` and never as the student's, and nothing it does reaches mentoring, the run's totals, its card, its capability numbers or its list of recent attempts. On dev every request passes the leak check. On the locked test the mentor is released first and the vault opens only on that proof; the leak check is off there because the test's content is the request.
- *Teach this and Improve agent (spec section 8).* Each settled workspace reply keeps its work: every model turn, every call with its arguments, every result as the model saw it. A person corrects one reply by saying what was wrong, what they wanted and their evidence. It goes to the mentor only when the job shares corrections (`sharing.corrections`) and the person consents to that exchange, behind the leak check and a $0.25 cap. The mentor classifies it (procedure, source, weakness, ambiguous, invalid) and proposes a lesson; nothing is queued until the person queues it, and an ambiguous or invalid one can't be. A procedure or source lesson can take effect at once as an instruction-only candidate version: the active version's harness with one line added under "From the person's corrections", unevaluated, its parent recorded. Improve agent runs every queued lesson through the usual rounds as a run that starts from the active version's harness and adapter, shows the lessons to the mentor beside the train evidence, keeps to the budget the person was shown, and ends in a candidate version of the same agent measured on dev. It never takes the locked test again, not by a re-test and not with Spark as a reference: the earlier result isn't reused as guidance, and the candidate says no locked test measured it. It needs the job to still share corrections, and it takes, in the transaction that writes its run, only the lessons still queued. The active version never changes; accepting and promoting stay the person's. Another run holding the student makes it wait, and it says so. Version writes for one agent take the graduate library's lock, so an instruction lesson and an improvement can't race for a number.
- *Wiring.* The engine host resumes the training worker before it recovers runs, scopes jobs by run id, reads the recipe from `trainer/` (packaged under `resources/trainer`), and uses Hugging Face Jobs only when a token resolves, the stand-in otherwise. The engine has one llama-server (decision 041): the utility process makes the adapter runtime once and gives it to the loop's adapter students and to the installation checks, and an evaluation through it takes the same turn the checks take. The mentor acts as the agent through the existing provider code.

**Consequences.** A02 (a failure becomes a replayed or full-task correction that passes the checker), A03 (harness and weights measured apart, a harmful change rejected, the prior version still running), A04 (a correction enters the queue under the sharing setting and becomes a candidate without touching the active version), A05 (progress and capability reconcile with the stored experiments, rejected and stopped included) and the records A14 asks for are covered by tests on fakes, and one whole chain runs on the returns desk with the real tools, sandbox, checker, vault and loop and scripted models; no model, Ollama, llama.cpp, OpenRouter, Meta or Hugging Face call was made. The stand-in backend proves the plumbing and is never kept. Limits as built: the Hugging Face token isn't yet passed to the engine's utility process, so the desktop app trains only with the stand-in; the stand-in's base header is read from the default student in Ollama's store; graduating with an adapter needs the llama.cpp student to report the base's digest; the screens for lessons, experiments and Teach this aren't built; an imported agent can't be taught here, since its job isn't on this computer. Known gaps from the independent review, not fixed yet: a draft's harness isn't checked for train answers; with no business date, a computer at UTC+12 or later records attempts a day ahead, so every replay falls back to a full demonstration; a crash between a refused lesson and the round's end lets teaching go on after restart; closing the app can wait for an adapter download; after a confirmation, the four configurations don't all cover the same seeds, and once an adapter is kept A0 is that adapter, not the bare base; a round stopped during training records compute as of the stop; an adapter's file is hashed as found rather than checked against its job's artifact record; a backend that changes between submit and restart sends a second job; and an improvement that keeps failing while it writes its candidate can't be stopped.

## 043. The architect command runs graduates through the workspace's own agent host

**Context.** Spec section 12 asks for a terminal command over the same package loader, runtime, bindings, permissions and event stream as the desktop app, with no second execution path, versioned JSON in and out, stable exit codes, and no approval that hangs or approves itself. The app's agent host is a plain Node module (decision 003) and already ends an ask-mode write as `approval_required` when nobody can answer (decision 039).
**Decision.**
- *One runtime.* `apps/cli` is a plain Node program. It opens the app's own data folder (Electron's `userData` for "Architect", or `ARCHITECT_USER_DATA`), the same SQLite store, and runs a graduate through `createAgentHost` over `workspaceStore`, in its own process: the same loader, active version check, bindings, grants, write approvals, tools, sandbox and `message.updated` events as a chat in the app. Install, inspect, verify, export and publish call the engine's graduate library, importer, exporter and publisher, opened outside the engine host through `openLocalLibrary`, which converts and clears nothing (that stays the engine host's job at start).
- *Local models.* It reads the app's own `settings.json` for local models the way the app gives its hosts theirs (`runtimeSettingsOf`, `quietThreadCap`): quiet mode's thread cap for a local student and for llama-server, the llama-server chosen in Settings, and the default student's Ollama only when it is on this computer. A version with an adapter runs on a llama-server of the command's own (`local-runtime/cli`, decision 041), which stops when the command ends.
- *Offline.* Before a graduate loads (run, verify, and an install's import step), the command installs the workspace's loopback-only network guard in its process. It never constructs a mentor; lint keeps mentor and vault code out of `apps/cli`. A Hub download happens before the guard goes up, and the import after.
- *Sessions.* A conversation is kept in memory unless `--save` asks for a chat in the app, and either way the session only sees its own chats, so it never settles a conversation the app has running.
- *Batch.* `architect.run-request/1` in, `architect.run-result/1` out, both zod schemas in `packages/shared`, keys snake_case. The request is checked before the agent opens; input references must be files the contract names, in folders bound and granted here. A result is written for every run past its command line, whole or not at all. Steps and messages go to stderr; stdout carries only results.
- *Approvals.* Asked on a terminal, line by line; with `--non-interactive`, a request on stdin, or no terminal, the reply ends `approval_required` with the change it wanted, and nothing is written.
- *Exit codes.* 0 succeeded, 1 runtime error, 2 invalid input, 3 not permitted (approval, binding, grant, blocked or attention-needing installation, token, unaccepted findings), 4 task failed (refused, no answer, an unusable reply), 130 cancelled. A runtime failure is told from a task failure by whether the agent host reported an error for the reply, as it does for adapter errors the loop treats as the runtime's.
- *Getting it.* `pnpm architect` in development, through tsx. The desktop build bundles the same sources (`out/cli/architect.mjs`, about 1 MB) beside the sandbox, packaging leaves it out of the archive, and each installer carries a launcher that runs it on the app's own binary with `ELECTRON_RUN_AS_NODE=1`: `architect.cmd` beside `Architect.exe`, `Contents/Resources/architect` on macOS. Nothing adds it to `PATH`.
**Consequences.** What the command does is what the app does, so tests compare them directly (A10). The command can't read keys saved in the desktop app (the system encrypts them for the app), so its export scan knows only the Hugging Face token it would use, and it doesn't follow the app's quiet mode for local models. An import from the command and one from the app for the same agent at the same moment aren't coordinated: version numbers are taken in each process. Checked on Windows with the unpacked installer build; the macOS launcher is untested.

## 044. Hugging Face publishing and installation, by commit

**Context.** Spec section 13: publish the same package to the Hub, private by default, never widening a repository's visibility, with a generated model card; install by an immutable revision; never show a failed or partial upload as a release, and let a retry finish without duplicate records. Training already had a Hub client with small commits only (decision 035), and an adapter is about 200 MB. No Hugging Face token exists on this PC yet.
**Decision.**
- *One client, one fake.* The training client moves to `packages/engine/src/hub` and gains what publishing needs, through the Hub's documented HTTP API rather than a new dependency: repository visibility, public or private creation, preupload, the LFS batch API with basic and multipart transfers, LFS verification, commits that add LFS files and delete files and can name their parent commit, file listings by revision across pages, and capped downloads. The token goes only to the Hub's own API for calls that need it: never to an upload or download host, a signed completion address or a redirect. The fake Hub in `test/support` serves all of it, with a second host for uploads and downloads that records whether a token ever reached it.
- *Public repositories.* Reading one needs no token: a read goes without one when there is none, and only a change requires it. Plain HTTP is allowed only to a Hub on this computer (tests), never for an address a Hub on the internet hands out.
- *The token.* One resolver for publishing and the training backend: the key saved in the app first (the new `huggingface` service, bound to `huggingface.co`, and only when the token goes there), then `HF_TOKEN` or `HUGGING_FACE_HUB_TOKEN`, then the token file `hf auth login` writes. The command uses the last two. It reports where a token came from, never its value.
- *What a repository holds.* The package at its root, exactly as an export would write it, and `README.md` beside it. The package goes up in one commit (LFS for whatever the Hub asks), and is checked file by file against the Hub's own listing at that commit; a second commit adds the model card, which names that commit in its install command. Files an earlier version left in the package's folders are deleted in the same commit as the new package; the rest of the repository is left alone.
- *Privacy.* A new repository is private unless the request says public. An existing private repository stays private (the publication records it as private and says so); a public one is refused for a private publication. Publishing runs the export's review and scan over the package and the card, and stops on findings until the request names the digest of the ones reviewed.
- *Records.* One `publications` row per version and repository (a unique index): `staged`, `uploading`, then `complete` with the package's commit and the repository's URL, or `failed` with the reason. Trying again reuses the row. When the Hub already holds exactly the package at the branch's head (an attempt that failed after its commit), no new commit is made, and only the card is added if missing. A complete publication of the same package is returned as it is; one of other files (other shared resources) to the same repository is refused.
- *Installing.* `hf://owner/name` resolves the commit once (the one named, or the one `main` points at) and records it with the version (`graduate_versions.source`, migration 15). Only `graduate.json` (at most 1 MB) and the files it lists are downloaded, within a package's limits, each checked by sha256 and size as it arrives; then the folder goes through `importPackage` like any package. A newer publication never changes an installed version; installing again without a commit adds the newer one beside it, as a candidate.
- *The package format* doesn't change. The model card and the records are outside the package.
**Consequences.** Live Hub validation waits on a token: everything is tested against the fake Hub, including LFS uploads, multipart, failed uploads and retries, and A12 stays partly done until one real publish and install. The Hub now stores new files with Xet; huggingface_hub without its Xet extension still uploads through the LFS API this client speaks, and whether the Hub takes that for every repository is the main thing a live run must confirm. Publishing over IPC has no progress events yet, and the desktop screens for it are the UI's work.
