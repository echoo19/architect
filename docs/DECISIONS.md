# Decisions

Short records of choices that aren't obvious from the code. Newest last. Each has the context, the decision, and what follows from it.

## 001. Electron, Vite and React for the desktop shell

**Context.** The spec allows Tauri or Electron with a Next.js UI. The engine, adapters and UI are all TypeScript, and end-to-end tests need to drive the real app.
**Decision.** Electron with electron-vite, React and Tailwind. No Next.js: there is no server to render, and Vite keeps main, preload and renderer builds in one tool.
**Consequences.** One language across the stack; Playwright's Electron support drives end-to-end tests. Larger installers than Tauri would give.

## 002. TypeScript 6.0, not 7.0

**Context.** TypeScript 7.0 (the native compiler) is current, but typescript-eslint 8 supports TypeScript below 6.1.
**Decision.** Pin TypeScript 6.0.x across the workspace.
**Consequences.** Revisit when typescript-eslint supports 7.x.

## 003. Engine and agent hosts run in separate utility processes

**Context.** Training runs for hours and must survive renderer reloads and app restarts. Graduates must never reach the network, while training must reach the mentor.
**Decision.** Training, evaluation and storage run in an engine host (Electron `utilityProcess`). Workspace sessions run in a separate agent host that never imports mentor adapters and installs a loopback-only network guard at startup. Both are plain Node modules wrapped by thin Electron entries.
**Consequences.** Clear process boundary for the offline guarantee; the full loop is testable under Vitest without Electron. Events cross processes over MessagePorts, so event payloads are schema-checked.

## 004. Mentor-written tools run in QuickJS inside a child process

**Context.** The mentor writes helper tools that the student calls. They must not touch the network, the file system outside the job's declared data, or other processes.
**Decision.** Each tool call runs in a fresh QuickJS VM (quickjs-emscripten) inside a sandbox child process. The VM gets only a data API for the job's declared files and permissions, plus time and memory limits. Tools are read-only; writes go through built-in write tools that need approval in the workspace.
**Consequences.** No native modules, same behavior on Windows and macOS, deterministic execution (no clock or randomness inside the VM). Tools are plain JavaScript functions, so the mentor can't use npm packages.

## 005. Sample job: the closing routine of a home-services office

**Context.** The sample job must show the product end to end, be deterministic to check, leave room for a learning curve, and stay clear of medical, education, basic RAG and political topics.
**Decision.** Ferncliff Home Services, a fictional plumbing, heating and electrical company with about 12 technicians and 400 customers. A seeded generator writes its records as CSV files plus a short policy document (pricing, tax, payment terms, scheduling rules). The agent, named "Service desk", handles three workflows:
- **Invoices.** Price a completed job: labor by technician tier, parts at markup, trip fee, after-hours multiplier, plan-member discount, city tax, all in integer cents with the rounding rules stated in the policy. Checked by end state: the created invoice's line items and total.
- **Overdue balances.** Find invoices past terms after partial payments, totals per customer, oldest balance. Checked by exact structured answer (ids and cents).
- **Scheduling.** Find the earliest start for a job that needs a skill or license in a zone, given working hours, existing bookings and a fixed zone travel matrix, with fixed-duration slots. Checked by end state: the booking is feasible and starts at the global earliest time; ties between technicians are all accepted.

The bare student gets the same policy document and the same primitive tools as every other method. What the mentor can improve is orchestration: reading the policy, applying rules in order, writing tools for steps it keeps getting wrong. Answers are structured, not free prose. Inventory and plan renewals wait as a possible second task family.
GPT-6 Astra reviewed the first draft (five task types) and recommended cutting to these three, bounding scheduling, using integer cents and avoiding fact-matching on prose. Adopted.
**Consequences.** One coherent story ("close out today: invoices, overdue balances, tomorrow's urgent call"). Fixtures get hand-audited against independently calculated answers before any training run, because a bug shared by the generator and the checker would be invisible otherwise.

## 006. What the mentor can see

**Context.** Keep-or-revert decisions use dev, and showing the mentor dev traces would let it tune to dev the same way it tunes to train.
**Decision.** The mentor sees train traces with checker reasons, per-type train results, the overall dev pass count, and its earlier hypotheses with their keep or revert decision and overall dev change. A round rejected before dev saw it (a reply that isn't a hypothesis, or a change set the harness refuses) is listed too, with the runner's reason, which is about the mentor's own reply and files. It never sees per-type dev counts, dev traces, dev task ids or dev checker reasons, and never anything from the test split. (Per-type dev counts were in the first version of this decision; GPT-6 Astra pointed out they are an extra channel for tuning to dev, and train results already show which types fail.)
**Consequences.** Dev still leaks a little through the overall score and the decisions (adaptive overfitting), so rounds per run are capped in advance and the report shows the dev to test gap.

## 007. One hypothesis per round, kept on a margin

**Context.** The spec allows "one or a few" changes per round. Measuring each change separately costs a full dev evaluation each, and a slow local student makes that expensive.
**Decision.** Each round the mentor proposes one hypothesis: a change set that may touch several files but serves one diagnosis, with a predicted effect. Dev evaluation uses Meta's recommended sampling for Glimmer (temperature 1.0, top_p 0.95, top_k 64; greedy decoding makes it repetitive). The runner, not the harness, owns the sampler seed. Each round draws its dev seeds from the run's panel seed and evaluates both the candidate and the incumbent on them, so the incumbent is measured again instead of being judged by the score that got it kept, which was the luckier of its draws. Sharing seeds does little against noise: at temperature 1 any change to the prompt re-samples every dev task, so the two results are close to independent draws. What shared seeds do is stop a change from choosing its own seeds and make every number reproducible. The guard against noise is repetition and the margin. With `devRepeats` (1 to 3, default 1) every dev task runs under that many seeds and passes add up across them. The change set is kept only if net dev passes rise by at least the job's margin times the repeat count (default margin: 2 tasks, or 5% of dev if larger) and no task type loses more than one pass per repeat; otherwise it is reverted and logged as a failed hypothesis. Before main runs, the noise pilot (`devNoisePilot`) evaluates one harness on dev under three student seeds and reports how far the score moves; if noise alone moves it by the margin or more, raise `devRepeats`, the margin or the dev set.
**Consequences.** Clean attribution in the lineage. A round evaluates dev twice per repeat, once for the candidate and once for the incumbent, so it costs 2 × `devRepeats` × the dev tasks in attempts, on top of the train batch. Kept changes are an engineering gate, not a significance test, and the README says so.

## 008. Answers end with a structured line

**Context.** The checker must parse answers deterministically, and free-text fact matching is fragile.
**Decision.** Task prompts ask the agent to finish with one line `ANSWER: <json>`, where the JSON shape is stated per task type. Write tasks are checked on the end state of the job's scratch data instead.
**Consequences.** Format failures count as failures (the policy and task text state the format, so formatting is part of the job). The workspace uses the same harness without the answer line requirement.

## 009. Where training and the locked test run

**Context.** On this machine the local student needs 2 to 3 minutes per task (measured 2026-10-27), so a full comparison (four methods, three seeds) can't be optimized locally in the time available. A hosted copy of Glimmer is much faster.
**Decision.** Training rounds and dev evaluations may run on a hosted copy of the student. Every graduate is frozen before any test runs, and test results never trigger another round. The graduate the app ships, and one predeclared seed of every method, are locked-tested on the local student after the mentor is released: its gate closed, so no call can start, and its adapter dropped. Hosted locked tests cover every seed as supplementary results. GPT-6 Astra reviewed this and preferred local tests for every seed; that stays the goal if GPU time allows.
**Consequences.** The report card of a shipped graduate describes the agent the user actually runs. The README states, for every number, the provider, precision, runtime and seed it came from, and says plainly that optimization happened on a hosted copy.

## 010. Job setup follows the design's conversation, with every field editable

**Context.** The design starts a job as a conversation (Describe, then the mentor's clarifying questions, then a review screen). The spec lists the job fields as one setup form.
**Decision.** Follow the design: describe the job and attach files, answer a few clarifying questions from the mentor, then review the drafted job on the Define screen. Every spec field (tasks, checker, requirements, budget, mentor, student, starting harness, permissions) is editable there under Advanced, and a job file can be imported directly.
**Consequences.** Drafting a job costs a few mentor calls. The saved job file is the same either way.

## 011. Where the design shows more than this version builds

**Context.** The design includes exporting a fine-tuned adapter (`.safetensors`) and training on a "Cloud GPU".
**Decision.** No weight training in this version, so the export offers the graduate folder and the report instead of an adapter. "Cloud GPU" means a hosted endpoint for the student during training.
**Consequences.** The LoRA comparison stays on the stretch list in the spec.

## 012. MIT licence

**Context.** The repository is public and should be reusable.
**Decision.** MIT.
**Consequences.** None beyond the licence text.

## 013. SQLite through `node:sqlite`, not better-sqlite3

**Context.** The brief's default is better-sqlite3, a native module that must be rebuilt for Electron's ABI, which also breaks running the same code under plain Node for tests.
**Decision.** Use the built-in `node:sqlite` (`DatabaseSync`). Electron 45 ships Node 24.22, and a check on 2026-10-27 confirmed `node:sqlite` works inside Electron and in Node 24.
**Consequences.** No native modules in the app, no rebuild step, and tests use the same storage code as the app. The module is still marked experimental in Node, so storage stays behind a small interface in `packages/engine/src/store`.

## 014. Mentor tier for the sample job's runs

**Context.** The Meta Model API has a standard tier ($1.25 in, $4.25 out per million tokens) and a contributor tier ($0.10 in, $0.20 out) whose content Meta may use for training and which must not carry sensitive or personal data. The app defaults to the standard tier and shows the tier as a setting.
**Decision.** Development and debugging runs on the sample job use the contributor tier: its data is generated and fictional. The comparison runs reported in the README all use one tier, the standard one, so the reported cost matches what a user with real data would pay.
**Consequences.** Spend stays small (a mentor round costs well under a cent on the contributor tier and a few cents on the standard tier). The README says which tier produced each number.

## 015. Glimmer runs with low reasoning strength

**Context.** Glimmer always reasons; Ollama's `think: false` hides the reasoning but may not stop it. Meta measured 1,811 completion tokens for one agent decision at the default `high` strength and 256 at `low`. On this machine the 30B model generates only a few tokens per second.
**Decision.** Harnesses default to `thinking: low`, and the mentor may raise it per harness through `decoding.yaml` like any other decoding setting.
**Consequences.** Several times fewer tokens per step. If low reasoning caps what the student can do, a kept change that raises it will show up in the lineage with its measured cost in latency.

## 016. Harness files are strict

**Context.** Harness folders are written by a model and read back by the runner, the workspace and other people's tools. A silently ignored typo (`max_step` instead of `max_steps`) would make a change do nothing while the lineage claims it was tested.
**Decision.** Unknown or misspelled keys in any harness or graduate file are validation errors with a "did you mean" hint. On-disk keys are snake_case everywhere (YAML, `lineage.jsonl`, `report.json`). Skills, tools and examples are ordered by slug; a tool's file name must equal its `name`; Windows device names (`con`, `nul`, `com1`...) are refused as names; symlinks and OS clutter files are ignored when reading. A version folder only counts once its `harness.yaml`, written last, exists, and loading fails if the files no longer match the saved hash. Graduate folders carry the report card twice: `report.json` for the app and `report.md` for people.
**Consequences.** A mentor edit with a typo is rejected and logged as a failed round instead of being kept as a no-op. Folders written on one platform read identically on another.

## 017. Small departures from the design for accessibility and robustness

**Context.** Matching the design exactly occasionally conflicts with readable contrast or Electron's behaviour.
**Decision.** Muted text is `#7F7F87` instead of the design's `#7E7E86`, which reached only 4.48:1 on the composer; a test keeps every readable text color at 4.5:1 or better in both themes. The theme setting drives Electron's `nativeTheme`, and the page copies the resulting `prefers-color-scheme` onto `<html data-theme>`, so there is one source of truth and no flash on launch. IPC handlers reply with `{ ok, value }` or `{ ok: false, error }` because Electron mangles errors thrown across IPC; the preload turns a failure back into an `Error` with the original message. Settings rows from the design that have no setting behind them yet (open at login, privacy toggles) are replaced by real ones: mentor tier, mentor reasoning, comparison mode, and read-only privacy facts.
**Consequences.** The look is unchanged to the eye; every visible control does something.

## 018. How the sample job's data avoids shortcuts

**Context.** The mentor sees train tasks with their expected answers. Any answer value shared by many tasks (train and test alike) would let it hard-code that value and look like it taught something.
**Decision.** Every id in an answer follows from the task's own record: invoices take their job's number (job W-2482 gets INV-2482) and bookings take their request's number (R-3042 gets B-3042). The first draft numbered invoices after the highest existing one, which made all 60 invoice tasks expect the same id; it was changed before any training run. The records are a snapshot as of Thursday 2026-11-05 (`businessDate` on the job), with the office closed on Wednesday 2026-11-11. The checker works out the earliest scheduling slot itself from the original tables, an implementation independent of the generator's reference code. Values that repeat by rule (the issue date, a few due dates and trip fees) remain, and so do some scheduling slots (27 distinct slots across 60 tasks, the most common one answering 7); none of them passes a task on its own, because the checker validates feasibility and every field.
**Consequences.** A harness that memorizes answers scores close to nothing on unseen tasks. The README notes the repeated scheduling slots as a limitation of one task family.

## 019. How a graduate behaves in the workspace

**Context.** The workspace is where people use a graduate every day; its rules for writes, refusals and interruptions need to be predictable.
**Decision.** A graduate's write mode is its saved setting, falling back to the job's `permissions.writes`. "Always allow" saves `allow`; in `allow` mode the diff still appears in the chat, marked approved, so every change stays visible. A refusal is decided before the student is called and shows the reason from the guardrails. Stopping a reply marks running steps stopped and pending writes denied; a reply interrupted by a restart comes back as an error when the graduate is reopened. History sent to the student is the last 12 messages that fit in a quarter of its context. The workspace's data lives in its own folder per graduate (`<userData>/workspace/<graduateId>/`), seeded from a copy of the job's data, so workspace writes never touch training data. The agent host runs behind a loopback-only network guard and refuses any student endpoint that isn't on this machine; the tool sandbox's child process has no network APIs at all (QuickJS), so it needs no guard of its own.
**Consequences.** Every write a graduate makes is visible and reversible at the moment it happens, and the offline guarantee is enforced by the process, not by convention.

## 020. Sixteen model turns per request by default

**Context.** The first calibration on local Glimmer (15 calibration tasks, blank harness, 2026-10-27) passed every overdue task (5/5) and failed every invoice and scheduling task (0/10). The traces showed why: Glimmer makes one tool call per turn, and the write tasks need about ten reads (job, customer, technician, rate, parts, prices, tax, policy; or the request, technicians, three pages of bookings, travel) before they can compute and write. Every write attempt hit the 8-turn limit while still reading. Its tool use up to that point was sound.
**Decision.** The default `max_steps` is 16. The mentor can still change it in a harness like any decoding setting.
**Consequences.** Bare failures now come from what the student gets wrong, not from a cap it can't see. Write attempts take longer on a local student (each turn is about 17 seconds), which makes a hosted student more important for training runs.

## 021. One bounded revision of the sample job, then a freeze

**Context.** On hosted Glimmer with a blank harness, the first version of the sample job scored 34/45 on dev (76%: invoices 9/15, overdue 13/15, scheduling 12/15) against an 85% requirement. That leaves little room for any method, and a mentor that only reads the policy would likely write the same invoice tool Architect found in its first round, so the comparison could show nothing about the value of watching attempts. GPT-6 Astra advised one bounded revision with realistic complications and no hidden rules, then a freeze, keeping the first version as a secondary benchmark.
**Decision.** Version 2 (`examples/home-services/job/`, the sample the app ships) adds overdue questions over groups of customers (a city, or a zone narrowed to plan members or one payment term; 5 to 60 customers), which a careful agent answers in a few filtered reads while a lazy 50-row read silently truncates; morning and afternoon windows for scheduling requests; and paired boundary cases inside the existing rules (labor minutes on and just past a quarter hour, invoices due today versus yesterday, payments dated today versus tomorrow, a slot that travel to the next booking invalidates). Every rule is in the policy with a worked example, the reference answers use only the student's own tool operations and limits (at most 4 reads for any overdue question), and no answer value is right for more than three tasks of a type. Version 1 stays byte for byte in `job-v1/`. Both are frozen from here: no further changes before the comparison runs.
Measured after the revision, same student and blank harness: dev 36/45 (80%: invoices 9/15, overdue 14/15, scheduling 13/15) and calibration 11/15. The estimate had been about 52%; Glimmer handled the group questions and the windows well, and invoices still fail mostly by running out of turns while pricing line by line. Following the same advice (don't keep hardening until a method wins), the tasks stay as they are.
The readiness bar is raised from 85% to 95% for both versions, before any comparison ran. These tasks write invoices and bookings into a business's records; one wrong row in seven is more than an office would accept from an assistant, and one in twenty is about the most it would.
**Consequences.** Comparison results are reported on version 2, with version 1 as a secondary result. Changing the tasks after seeing how the methods do would bias the comparison, so it doesn't happen. With the bare student near 80%, the room for any method is the last 15 points and the time per answer, so the README reports latency and turns per task alongside pass rates.

## 022. A change that clears the keep check is measured again before it's kept

**Context.** Before the comparison runs, a noise pilot ran the sample job's starting harness on all 45 dev tasks three times under different student seeds (hosted Glimmer, its recommended temperature 1): 39, 33 and 36 passes, with 14 tasks changing outcome between runs. A second pilot at temperature 0.6 gave 37, 38 and 34 with 15 tasks flipping, so lower temperature brought no clear benefit and decoding stays at the model's recommended settings. Pooled over the six runs, 21 of the 45 tasks are unstable and one dev run's score has a standard deviation of about 2.3 tasks; invoices carry most of it (11 of 15 unstable). Simulating the keep check with those per-task pass rates, a change that does nothing cleared the old rule (+2 net dev passes, no type down more than one, one run each) about 28% of the time.
**Decision.** A change that clears the limits on its first measurement has both versions measured again on dev under new seeds, the round's next `devRepeats` seeds, and is kept only if the totals over both measurements clear the limits for twice the runs (+4 net, no type down more than two, with one repeat). The second measurement needn't clear the limits alone. Changes that miss on the first measurement are reverted without the second, so the extra cost falls only on promising changes. The per-type limit stays at one per run: loosening it to two raised the share of kept trade-offs (one type up, another down) from about 9% to 22% in the same simulation. Patience for the sample job rises from three to four reverts in a row, since a real three-task gain now clears the check only about half the time. The same rule serves Architect and self-reflection.
In simulation with the pilot's task pass rates, a do-nothing change is kept 11 to 15% of the time (depending on whether rates come from one pilot or both and whether they are smoothed), a change worth about 4.5 tasks 78 to 83%, and one worth about 2 tasks 43 to 47%; each round runs 2 to 4 dev measurements of 45 tasks instead of 2. GPT-6 Astra reviewed the rule before it was built and agreed, with three conditions this follows: store both measurements (lineage and rounds keep `firstMeasurement` beside the pooled scores), call kept effects selection-conditioned dev estimates, and plot pass rates rather than mixed totals.
**Consequences.** The 13% figure is a per-proposal estimate from a small pilot, not an experiment-wide error rate; kept changes' measured effects still lean upward because the same measurements decided to keep them, and dev curves reflect repeated use of one dev set. Claims about methods rest on the locked test. Dev scores can now have different totals within a run (45 or 90 with one repeat), so anything that compares them uses rates or per-run counts.

## 023. One fix for a reply the runner can't use

**Context.** The first comparison run of the one-shot baseline lost its only reply to a format slip: Spark wrote its worked examples with `args` where the harness format says `arguments`, and left out `tool_call_id` on tool turns. The change set was refused, so the "one-shot" result would have been the blank starting harness: a measure of one formatting mistake, not of writing a harness without watching the student. Architect and self-reflection lose a whole round to the same kind of slip, and two refused rounds in a row end training.
**Decision.** When the runner can't use a reply (it isn't a hypothesis, or the harness refuses its change set), the round's author gets the same request again followed by its own reply and the runner's reason, and one more answer. If that can't be used either, the round is rejected as before. The fix adds nothing but the refusal reason, so the one-shot author still never sees an attempt, and every method gets exactly the same chance. The fix call is charged to its round and saved beside the first (`mentor/round-<n>-fix-1.json`); the stored reply records whether it is a fix, so a restart never asks twice. The mentor's guide to the harness now shows the exact shape of each example message.
**Consequences.** A round can cost two author calls. Comparison runs started before this was in place are discarded and run again.

## 024. A tool may name a data file without its extension

**Context.** In the restarted seed 1, Spark's one-shot harness called `ctx.readTable("jobs")` in its pricing tool, and the file is `jobs.csv`. The mentor's guide said `ctx.readTable(name, ...)` without saying the name keeps its extension, so the tool failed on every call and the student spent its steps retrying it: dev fell from 38/45 to 15/45. The student can correct a wrong file name after the error message; a tool's code can't, and one-shot never sees an attempt.
**Decision.** In the sandbox, a name that isn't a file but is exactly one file's name without its extension refers to that file. The mentor's guide now describes `ctx` precisely: file names as listed, rows as objects keyed by column with text values and null for empty cells, every matching row unless a limit is passed, and the same filters as `read_table`. The student's own tools still take exact names.
**Consequences.** The runs of that start were discarded and seed 1 began again with this in place.

## 025. A change set's tools must load before it is measured

**Context.** The same one-shot harness had a second tool, `find_slot`, with a typo (`var start Day=null;`) that no JavaScript engine parses. Every scheduling task called it, got a syntax error back, and ran out of steps. A tool that doesn't load is as detectable before any task runs as a malformed example file, and it costs Architect a whole measured round to find out from traces.
**Decision.** When a change set adds or edits a tool, the runner loads the tool's code in the sandbox before measuring anything: only the code's top level runs, the tool isn't called and sees no data. A tool that doesn't load (a syntax error, no `run`, a top level that throws or runs too long) makes the change set unusable, with the reason and line, so the author gets its one fix (decision 023). The sandbox now reports the line of a syntax error too.
**Consequences.** All methods get the same check. A tool that loads but computes the wrong thing is still found only by attempts, which is what the comparison is about.

## 026. A blank start begins with a whole draft, and the comparison shares it

**Context.** The one-shot baseline is there to test whether watching the student adds anything (SPEC). Architect started from the job's starting harness, which is blank for the sample job, and made one change per round, so within eight rounds it built a whole harness piece by piece while one-shot wrote one in a single reply. In seed 1, with decisions 023 to 025 in place, Spark's one-shot draft took dev from 35/45 to 45/45. A loss to that baseline would then say "writing piece by piece is slower" as much as "watching adds nothing". No Architect or self-reflection run had been made in any start of the comparison. This is a change to the protocol made after seeing that one-shot score, and it is reported as one.
**Decision.** In the product, a run that starts from a blank harness begins with a draft round: the author writes a whole harness from the job setup and the train examples with their expected answers, with no attempts, as one-shot does, and the draft is kept as the starting point. Every later round is one watched change under the keep rule. A run that starts from a template or an imported harness refines it directly. In the comparison, each seed's draft is written once and shared: one-shot stops there, while Architect and self-reflection start from that exact draft with the seven rounds left and the draft's mentor spend taken off their cap. Self-reflection is then the student refining the mentor's draft, which compares the two refiners from the same starting point. GPT-6 Astra reviewed this and advised keeping the draft unconditionally and forking one draft per seed.
**Consequences.** A draft is measured once, against the run's baseline, since it is kept whatever it scores; a draft refused even after its fix is followed by another draft rather than by building piece by piece; and a seed whose one-shot draft was refused has nothing to share, so its Architect and self-reflection runs draft for themselves (all three settled after a second independent review). What the comparison can test is "watched refinement adds value over stopping after the draft". When a draft already meets the 95% bar on dev, refinement stops at once (target met) and Architect tests the same harness one-shot did; the README says so plainly where it happens, and reports each draft's dev score, every kept change, paired test outcomes, costs, and every earlier start of seed 1 with its fixes and cost.

## 027. Five seeds for the comparison

**Context.** With the shared draft (decision 026), a seed whose draft meets the bar costs about $2.50 of hosted student time: bare and one-shot, plus two refining runs that stop at once. Seed 1's draft passed 60/60 on the locked test, so the question three seeds can barely answer is how often a draft falls short, which is the only place watched refinement can show anything on this job.
**Decision.** Seeds 1 to 5 for all four methods, decided after seed 1's one-shot result and before any later seed ran. The order is fixed: seeds 2 to 5 run in sequence, and if the $50 cap on the hosted student key comes within $8, the remaining seeds are dropped and the README says which.
**Consequences.** Every seed is reported, including any that fail, with each draft's dev and test scores. The limit that matters turned out to be the account's prepaid credit ($10), not the key's $50 cap; it ran out minutes into seeds 2 to 5, which wait for more credit.

## 028. A second task family, where the data is messier than its samples

**Context.** On the home-services job the policy states every rule with an example, and Spark's first draft passed every check task before it saw an attempt, so the comparison can't show what watching adds (README, Results). The mentor sees each data file through its columns, row count and a few sample rows; only the student's attempts touch every row. Real office files are rarely as clean as their first rows.
**Decision.** Build a second job in a different domain whose policy, like the first, states every rule with a worked example and hides nothing, but whose data files are messy the way exported spreadsheets are (several date formats, money written with symbols and separators, stray spaces and letter case, a few legacy codes), with the messy rows spread through each file rather than in the first rows. The reference answers and checker handle every variant. Its difficulty is calibrated on the bare student like the first job's, before any method runs on it, and its comparison uses the same protocol (decisions 022 to 027). Decided after seeing seed 1 of the first job; the rationale is that samples are what a mentor sees and attempts are what watching adds, and the result is reported whichever method it favors.
**Consequences.** If Spark's first draft handles the messy rows anyway, this job ends at the ceiling too, and the README says so. Running it needs hosted credit, which waits on the owner.


## 029. A model call that fails in passing is tried again before the run pauses

**Context.** Hosted models sometimes drop a reply partway: on 2026-10-28 OpenRouter cut three runs' replies within the same minute, and each run paused until someone resumed it. In the app that means a training run left overnight stops for good at the first hiccup, though a minute later the same call works.
**Decision.** When a step fails with an adapter error that usually passes on its own (a busy or rate-limited server, a dropped connection, a reply cut off partway, but not a 504), the run logs it, waits 30 seconds, and plans its next step again, which redoes only the attempts that hadn't finished. A second failure waits 90 seconds. A third with no attempt finished since the one before pauses the run with the reason, as before. Errors that waiting won't fix (a refused key, no credit, a bad request) pause at once.
**Consequences.** The run stays active while it waits, so the wall clock keeps counting and a pause or stop takes effect once the wait ends. A local runtime that isn't running gets two minutes to come back before the run pauses.

## 030. Graduates run on a coding-agent harness built on Architect's own loop

**Context.** The expanded spec assumed Pi was already the graduates' agent harness. It isn't: task evaluation and the workspace share Architect's own loop, and the student's tools were table tools written for one kind of job (`read_table`, `append_rows`, `calculate`). The owner (Oct 28): "Pi is a good base to start off. if you think a custom version is better thats fine but it should be a classic coding-agent-like harness since those are the most versatile."
**Decision.** Keep the loop and make the harness a coding agent's: built-in `read`, `ls`, `glob`, `grep`, `write`, `edit`, `append` and `run`, where `run` executes JavaScript in the QuickJS sandbox in place of a shell; standing instructions in `AGENTS.md`; skills as `skills/<name>/SKILL.md`, listed by name and read on demand; helpers as typed sandboxed tools; paths are logical (`data/`, `output/`) and each installation binds them. Pi itself isn't embedded: its bash tool can't be kept offline and sandboxed on Windows, and the loop already owns replay, approvals, budgets and the network guard.
**Consequences.** Results measured with the table tools (the first comparison, seed 1) describe the old runtime and are labeled so. The sample jobs' reference solutions move to the new tools.

**As built (Oct 28).** Where the build differs from the plan above, or settles something it left open:
- Skills are read with `read` on `skills/<name>/SKILL.md`; there is no `load_skill`. Retrieval rules can still put a skill's steps in the system prompt up front. A skill folder holds only its `SKILL.md`, whose front matter is `name` (the folder) and `description`.
- `output/` exists only when the job's `data.output` says so. Training gives each attempt an empty scratch one, which the checker's validators don't read yet; the workspace keeps it as a folder inside the graduate's data folder until installations get their own bindings.
- `grep` runs in the sandbox child like `run`, so a pattern that backtracks without end is stopped instead of hanging the engine. Both get 5 seconds a call; helpers keep 2. `glob` matches in one pass per part of its pattern, so no pattern can stall the engine either, and a pattern it can't read is an error the agent sees.
- `run`'s `csv.parse` gives every cell as text and an empty cell as `""`, the usual JavaScript habit; helpers' `ctx.readTable` keeps `null` for an empty cell, as it always did. Helpers may also name a data file by its path, `data/jobs.csv`.
- A write may not break a table: the new text must parse as CSV and keep the header line, or nothing changes and the agent is told why. Every change is diffed by line, and a change to a table also by row; the workspace's approval card shows the rows for a table and the lines for any other file. A change too large to diff quickly (thousands of rows rewritten) is recorded as the whole file replaced. In a live `output/`, a new file never replaces one the folder holds but didn't open (a file over 1 MB, say), never goes through a link, and can't differ from an existing name only in capitals.
- Tools accept `file_path` or `file` for `path`, and counts written as text ("10"), because small models send both. A call to one of the table tools gets an error that names the tool to use instead, so a harness written for them can recover; a format 1 harness's skills and examples are not rewritten and still mention those tools.
- Harness format 2 is migrated in code when a format 1 folder is read: `system.md` becomes `AGENTS.md`, each `skills/<slug>.md` becomes `skills/<slug>/SKILL.md` with its summary as the description and its old title as a heading, and a helper named like one of the new built-in tools (`grep`, `run`) becomes `<name>_helper`. The folder is checked against the hash it was saved with, then gets a new hash over its format 2 files. So an older graduate opens and runs on the new tools in the workspace, but a run frozen before this change can't take or repeat its locked test, and its graduate can't be rewritten on acceptance: its record belongs to the table tools.
- Every attempt's trace records what it started from: a sha256 of each data file as its bytes stood at the start, the harness hash, the tools' version (`architect-tools/2`), the sampler seed, the decoding settings and the business date. Each write records its diff and whether it was applied, and the trace ends with every file's change since the start. Locked-test traces are still not kept.
- The sample jobs' reference solutions read the policy, send `run` code that fetches the rows a task needs and adds up its numbers, and append the new row; the TypeScript policy code still decides. Their tests replay every call of every task through the engine's own tools, compare the text the agent gets back, and grade the end state with the real checker. The worst cases are 5 tool calls and 12,341 characters of results on the returns desk, and 3 calls and 21,028 characters on home services, against 16 turns and 24,000 characters; no limit changed. The task files didn't change: the generators still write them byte for byte.

## 034. Any mentor by key, sign-in or a local runtime, and no guessed prices

**Context.** The owner asked on 2026-10-28 for Architect to be truly model agnostic: mentors from other providers by API key or sign-in, or a model running on the same computer, and any local model as the student, with Meta's models kept as the defaults. Three parts of that aren't settled by the code alone: where a key may be sent, how a desktop app signs in without a server of its own, and what the dollar cap does when nobody knows a model's price. The same day the owner asked for the student to run on the GPU; Glimmer's 4-bit build needs about 19.5 GB and doesn't fit a 12 GB card.
**Decision.**
- *Keys.* A provider's key is stored encrypted under the provider's name and goes only to that provider's hosts, over HTTPS. A key for an endpoint added by address is stored under that exact host and port and goes nowhere else; plain HTTP is allowed only to this computer. Main checks a key with its provider before storing it, so a refused key never lands in the store. Ollama and LM Studio on this computer are found without any setup and need no key.
- *Sign-in.* OpenRouter documents a sign-in that hands any desktop app its own API key, with no app to register: PKCE with a callback on localhost or 127.0.0.1 on any port. Main opens OpenRouter's page in the system browser through the same checked link route as every other external page, waits once on 127.0.0.1 for the callback, matches its `state`, and exchanges the code for a key, which is stored like a pasted one. It stops on cancel, on a decline, after 10 minutes (when OpenRouter's codes expire), or if no port can be opened. No other sign-in is built. Hugging Face documents one that would fit (a public OAuth app with PKCE, a loopback redirect on any port, and an `inference-api` scope for its Inference Providers), but it needs an app registered with Hugging Face first, so it is a proposal for the owner. Google's OAuth for the Gemini API needs a client in the developer's own Cloud project and scope verification for outside users, and OpenAI and Anthropic document no sign-in for other apps.
- *Prices.* A mentor's price comes from its preset, from OpenRouter's listing (saved with the mentor and sent as `provider.max_price`, so OpenRouter can't route to a provider that charges more), from a price the user enters, or is zero for a model on this computer. Otherwise the price is unknown, and Architect doesn't guess: Define asks for the price before training can start, and the budget gate refuses any mentor call it can't price. When OpenRouter reports what a call cost, that amount is what counts against the cap.
- *GPU.* Architect reads the GPU (nvidia-smi, or Apple silicon's shared memory), shows for each local model whether it runs entirely on the GPU, and recommends the largest Glimmer build that fits. For a 12 GB card that is a 2-bit build, which Architect installs itself: it pulls Unsloth's UD-IQ2_XXS file and makes a text-only Ollama model from its weights with Glimmer's own renderer and parser, so tools and thinking work as they do with the library build. The 4-bit build stays the default wherever it fits.
**Consequences.** Every invariant holds as before: the graduate and the workspace still never construct a mentor, and a graduate's student must be on a loopback address. A mentor with no known price costs one extra step instead of a cap that can't be kept. Mentors on generic OpenAI-compatible services get the schema in the prompt and one repair call, so they may need a repair more often than Meta, OpenAI, Anthropic or Gemini, which hold replies to the schema. Live checks and what wasn't checked are listed in `docs/MODELS.md`; the OpenRouter sign-in and the GPU build's install are tested against fakes, since the account has no credit and GPU work is paused.

## 035. How the adapter runtime and the training worker are built, and where they differ from 031 and 033

**Context.** Decisions 031 and 033 set the direction on Oct 28. Building them settled details they left open, and three points differ from them: llama-server is found but not installed, the compute cap lives with the training records for now, and a job's inputs and outputs share one private repository. The real training run itself still waits on the owner's Hugging Face token.
**Decision.**
- *Finding llama-server.* The path set in Settings, else the first `llama-server` on PATH, and nothing else, so no developer's install is assumed. Builds older than 10358, the first with Muse Glimmer, are refused. Installing one for the user is deferred (031 said "finds or installs").
- *Base weights.* The GGUF comes from Ollama's store through the model's manifest, in either layout Ollama writes (`docs/MODELS.md`). Its size must match the manifest and it must be GGUF. A model whose Ollama copy carries an adapter layer, or isn't stored as GGUF, is refused rather than served without it.
- *Adapters.* Each adapter is checked against the base before anything loads: same architecture, every adapted weight in the base, pairs shaped [n_in, r] and [r, n_out], tensor types the converter writes, no embedding adapters. They load unapplied (`--lora` with `--lora-init-without-apply`) and every request names every loaded adapter with its scale, so one server measures a candidate with and without its adapter. A change of scales between requests clears the server's prompt cache, so measurements should group requests by adapter.
- *The server process.* 127.0.0.1 on a free port, with a fresh key per start read from a file, so a web page on the same computer can't use it; `--jinja`, `--no-webui`, `--offline`, one slot, the context size and GPU layers, and the quiet-mode thread cap as `--threads` and `--threads-batch`. Before it starts, Ollama is asked to unload every model and the start waits until it has. A request's hold on the server is taken in the same step that hands the server over, and a server whose launch changes (other adapters, another thread cap) restarts only when no request holds it; one caller giving up on a start doesn't call it off for the others, while a stop calls it off at any stage. It stops after 10 idle minutes; `--sleep-idle-seconds` makes a server the app lost track of unload its model by itself, and the next start stops such a server if it answers to the saved key. Failures are named from the server's own log lines (the model, memory, an adapter, a port, a timeout) and reach a student as an `AdapterError`, so an evaluation stops on them instead of scoring a wrong answer.
- *Students.* A llama.cpp student in `packages/adapters` is bound to one adapter selection through a small `LlamaServerAccess` contract in `packages/shared`; students on the same base and adapter set share one server and one copy of the weights, and a student that lets go stops the server only once no other student has a request in flight. Graduates without an adapter keep running on Ollama, as 031 says.
- *Training on Hugging Face Jobs.* Each job gets one private model repository: the app commits the job's inputs there (job file, dataset, recipe scripts; at most 10 MB per file, since the app doesn't speak LFS), and the job reads them at that commit and uploads its outputs beside them, where the app downloads them at a fixed commit and checks each against the job's manifest of hashes. The job runs the recipe's image pinned by digest, its token as an encrypted job secret, Architect's job id as an environment tag (how a job is found again after a crash), and a timeout equal to the compute the budget allowed, so the Hub stops it there even if the app is closed. Jobs run on any Hugging Face account or organization with a positive credit balance (the Hub's Jobs guide, checked Oct 28).
- *Durable jobs.* A job's record is written before the backend hears of it, keyed by dataset, base revision, recipe, backend and hardware, so the same job is never sent twice; a failed or cancelled one may be sent again. Changes to one job (its submission, checks, cancels, downloads) run one at a time, each from the record as stored. When the provider's answer to a submission is lost and the provider can't be asked whether it has the job, the job stays as sent and is asked about again on the next check, rather than risk sending it twice. After a restart, unfinished jobs are picked up where they were: a submission cut off is found by its tag (or marked as never received), running jobs are polled, finished ones are downloaded. Outputs that are missing or don't check out fail the job; a dropped connection is tried again. Records are files under `<data>/training/jobs/<id>/` behind a store interface, ready to move into the database.
- *Compute cap.* A budget line beside mentor dollars, per scope (a job or run id): jobs that stopped running count at what they cost and running ones at their whole authorization. New jobs are made one at a time per scope, so two can't be paid from the same dollars. A new job is cut to what is left at the hardware's price and refused when that is under 35 minutes (10 for setup, 15 to convert and upload, at least 10 to train) or when the price isn't known; the worker also cancels a job it sees running two minutes past its limit. Compute time runs from when the job began (bounded by when it was last seen waiting for hardware, or else made) to the end the worker observes, capped at the authorization, since the provider stops the job there: an upper bound on what is billed, and time spent waiting for hardware counts toward neither cost nor the worker's stop. The one priced flavor is the L40S (`l40sx1`, 48 GB) at $1.80 an hour, as the Hub's Jobs hardware table listed it on Oct 28. The cap sits with the training records until versioned job contracts can carry it in the job's budget (033 put it beside mentor dollars without saying where it is kept).
- *The recipe.* PEFT with bitsandbytes QLoRA, not Unsloth: Unsloth patches transformers at import and changes fast, and the L40S has room for plain QLoRA. Pinned in `trainer/recipe.json`: the PyTorch 2.11 CUDA 12.8 runtime image by digest; transformers 5.19.0, peft 0.20.0, bitsandbytes 0.50.1, accelerate 1.14.0, tokenizers 0.23.3, safetensors 0.8.0 and huggingface_hub 1.33.0, the versions in this PC's package cache; NF4 with double quantization and bf16 compute; LoRA r 16, alpha 32, dropout 0.05 on the text decoder's q, k, v, o and attention-gate projections and the MLP's gate, up and down, never the vision tower, the embeddings or the head; plain alpha / r scaling with no rsLoRA or DoRA, which llama.cpp applies as trained; 2 epochs at 1e-4 with a cosine schedule, batch 1 with 8 accumulation steps, up to 16,384 tokens, seed 1234. The conversion is llama.cpp's `convert_lora_to_gguf.py` at commit 60eeeb6 (b10472, the build that loaded the probe adapter here) in its own environment with that commit's requirements, writing f16.
- *Targets.* Only assistant turns flagged for training are labels, found by rendering the conversation with the model's own chat template. A template that renders a turn differently further on is refused, and an example longer than the limit is skipped and listed, never cut. Checked on Oct 28 with Glimmer's own template (from the 2-bit build's metadata, rendered as transformers renders it) on an example from the dataset builder: the targets were exactly the read call (` to=read<|message|><atem:function_calls>...<|eot|>`) and the answer with its reasoning (` to=self<|message|>...<|eom|><|start|>assistant to=user<|message|>ANSWER: ...<|eot|>`), each from just after `<|start|>assistant`, with the user's words and the tool's output left as context.
- *What may be trained on.* Episodes from train tasks and accepted workspace corrections. An episode from another split, or one the vault's leak detector flags, stops the dataset build. Episodes whose data may not leave the computer are left out of remote datasets, and the worker refuses a dataset that holds any.
- *Stand-in.* As 033 says. Its label is in the record, its manifest, the adapter's GGUF metadata and every line the app writes about the job; its adapter is a no-op (lora_b is zero), and `countsAsRealTraining` is false for it whatever else its record says.
**Consequences.** A01 stays blocked until the owner adds a Hugging Face token with Jobs access. Everything up to a real job is tested against fakes (a stand-in llama-server process, a fake Hub with a separate download host) and against this PC's real files without loading a model. The first real job will show whether the pins and the converter work on Glimmer; a wrong pin costs the setup minutes, not a full job, since the recipe checks its inputs before installing anything. The desktop app is not wired yet: Settings needs llama-server's path and a Hugging Face key service (`huggingface` isn't in the secret store's services), the `trainer/` folder must ship as an app resource, and the engine host must call `resume` when it starts.

## 036. A task that asks only for an answer must leave the data as it found it

**Context.** With the coding-agent tools an attempt can change any writable table. The built-in comparator graded answer and facts tasks without looking at the files, and the returns desk's validators checked only the table each task writes (order questions only the ANSWER line). So an attempt could book an unasked pickup while recording a return, or add a row while answering a question, and still pass. A second opinion on the evaluation plan found this before any measurement on the new runtime.
**Decision.** The engine fails an answer or facts task when the attempt changed any table, comparing rows and columns, so a rewrite that kept every row counts as unchanged. The returns desk's validators fail an attempt that changed a writable table other than its own: a return adds its row to `returns.csv` only, a pickup to `pickups.csv` only, and an order question changes neither. The reason names the table, the way other reasons name a field. Text files and `output/` are outside the check: the sample jobs' text files are read-only, and neither job enables `output/`.
**Consequences.** The tasks didn't change, and the reference solutions still pass. Results from before this change, including the Oct 27 calibration on the old tools, aren't comparable with measurements on the new runtime, which all start after it.

## 038. A graduate version is a portable package

**Context.** A graduate was a folder written once after its locked test (`graduate.yaml`, the harness files, the report card, the lineage), and it opened only on the computer that trained it: the workspace read its job and copied the job's data from the run's folders, `graduate.yaml` held the student's endpoint, the hash covered only the harness files, and accepting it rewrote the folder. The expanded spec (sections 10 and 11) asks for one portable, immutable artifact that the desktop app, the CLI, export, import and the Hub all use.
**Decision.** A version is a folder with `graduate.json` (schema 2, snake_case keys like every other file), `harness/` (the harness folder exactly as `@architect/harness` writes it, so the coding-agent format of decision 030 drops in), `evidence/` (the author's report card and a change history), `adapter/` when there is one, and `resources/<name>/` only when the author chooses to share a resource. The manifest has the sections of the spec's table: identity (agent id, version, parent, when and how it was made), the job contract it was tested against, the model (a base model named the way runtimes name it, with its digest, and the adapter's path, format and sha256), the harness (format, hash, the round that made it), logical resources (`data`, `output`, named ones; required or not, accepted types, the files and columns the contract names, the access it asks for), requirements (where it was tested, measured latency, estimated memory, limitations), evidence (labelled "Evaluated on the author's configuration", with its status: ready, experimental or unevaluated), verification (the checks an installation can run, never the locked test), the sha256 and size of every other file, and terms. Nothing in it belongs to one computer: no endpoint, folder, chat or key. The change history keeps each round's title, files, predicted and measured effect and decision; the mentor's diagnosis, the reasoning behind its prediction and the task ids are left out, since they quote attempts on the author's data, and the full lineage stays with the run.
The transport is `<name>-v<n>.architect.zip`: stored or deflated entries, UTF-8 names, fixed timestamps, so the same files always make the same archive. A version's identity is the sha256 of its `graduate.json`, recorded when it is installed and checked, with every file's checksum, each time it opens. Files that file managers drop into folders and archives (`.DS_Store`, `._` files, `__MACOSX`, `Thumbs.db`, `desktop.ini`) are passed over, never counted as part of a package.
An import (a folder or a zip) is checked in a staging folder before anything in it runs: every entry name is a portable relative path (no `..`, drive letters, backslashes, hidden files, device names, or two names for one file on Windows or macOS); links, junctions and special files are refused whatever system made the archive; no more than 2,000 files, 2 GB a file and 4 GB in all, a directory no larger than its entries need, inflation stops at each entry's declared size, and an entry that expands more than 200 times is refused as a bomb; entries must not overlap and their headers must agree; the manifest's schema number is read before its fields; the files must be exactly the ones listed, byte for byte; it must run on a runtime an installation here can serve (an adapter needs one that loads adapters); its harness format must be one this build reads; and its `data/` resource must name the files its contract does. A format 1 folder's files are weighed before they are parsed, and a harness larger than any harness may be is refused before it is read. Only then is the harness parsed (read, never run) and compared with its hash. Tools first load in the sandbox in the installation checks, after the version is installed.
An import never replaces a version. The same package installed twice is found by its digest. A package continues an agent here only when this computer has the version its manifest names as parent, matched by digest; otherwise it becomes a new agent, under its own id when that is free and a new one when not, since anyone holding an export knows an agent's id.
What a computer gives a graduate is its installation, kept in SQLite and never exported: the local model endpoint, a folder for each logical resource, and grants (the write mode and each resource's access). A package's requested access is not a grant: an import grants only what the request names, capped at what the package asks for, and an import that names nothing grants nothing, on any computer. A graduate made here gets its job's model endpoint, its own copy of the job's data for `data/` and the job's write mode, so the same computer never needs an export. Installation checks (platform, memory, runtime and adapter fit; the harness hash; tools load; folders bound with the files and columns named; the base model served, and the same build when the runtime can tell; a short request, timed, with the model unloaded afterwards) are labelled "Installation checks on this computer" and stored apart from the author's evidence, which never changes. Ready means every check passed; needs attention means something the user can fix (a folder to bind, a model to download, a computer the author didn't test on); blocked means it can't run here, and the workspace won't open it. With no folder bound to `data/` a graduate opens no files at all.
An export writes exactly what its review scanned: the version's folder byte for byte unless the user opts into a resource, and then the resource's named files and a manifest that lists them. The best-effort scan (stored key values, common key shapes, user and app folders, also as JSON escapes them) masks everything it finds in every excerpt, and an export with findings goes ahead only when the request names the digest of the findings the user reviewed. The archive is written before the folder moves into place, so a failure leaves nothing behind. Graduates in format 1 are converted in code: when the engine starts, for those already here (their endpoint becomes the installation, their workspace folder and write mode are kept, and their old files stay where they are), and on import.
An adapter is named the way the adapter runtime of decision 035 checks and loads it. In the manifest's words: `model.base.name` is the base's name in Ollama's store (the runtime's `ServeRequest.model`); `model.adapter.base_digest` is the digest of the GGUF file that store holds for it (`OllamaModelFile.digest`, `sha256:<hex>`, which the llama.cpp student reports), and installation checks block a version whose served base has another; `model.adapter.sha256` and `size_bytes` are the GGUF LoRA's, as the training job's `gguf_lora` artifact records them and as the integrity section must list them, or the manifest is refused; `model.adapter.scale` is the scale every request applies (`ServeRequest.scales`); `model.adapter.training_job_id` is the `TrainingJobRecord.id` that made it, when one did, and `stand_in` marks an adapter from the stand-in backend (its `artifacts.standIn`, or a record that isn't `real`), which also adds a limitation saying so. `model.base.digest` stays the digest the runtime that tested the version reported. A version opens with the runtime's request ready (`ActiveVersion.adapter`: the installation's name for the base, the version's own adapter file, its scale), so a rollback hands the runtime the earlier version's harness and adapter together. Only GGUF LoRA adapters go into packages; PEFT files stay with the training job.
**Consequences.** A graduate opens anywhere a compatible runtime serves its base, and the same computer needs no setup to use a new one. Until an installation can serve a version with llama.cpp (decision 035), a package with an adapter exports byte for byte but is refused at import, and a version with one is never opened on Ollama, which would run it without its adapter. The ZIP reading and writing are written here and tested with archives built byte by byte. Hugging Face publishing will upload the same folder; its table exists and is unused so far.

## 039. Every graduate is an agent with immutable versions

**Context.** A graduate had one version: accepting it rewrote its folder, importing refused an id already present, chats didn't record what answered, and a job's contract was overwritten whenever the job was saved. Teach this and Improve agent (spec section 8) need versions that never change, candidates kept apart from what the user runs, and the version recorded with every answer.
**Decision.** A `graduates` row is the agent; `graduate_versions` holds its versions (v1, v2 and on), each an immutable package folder under `graduates/<id>/versions/`. Only a version's state changes: candidate, accepted or rejected. The agent's active version is a pointer, and accepting and promoting are separate events, logged with rejections and rollbacks in `graduate_events`. An agent's first version is active from the start, since nothing else could be; any later one (an improvement, or an imported newer version) waits as a candidate until it is accepted and then promoted. Promotion and rollback move the pointer in one transaction, a rollback only to an earlier accepted version, and because a version's folder holds its harness and adapter together and is verified whenever it opens, they always switch together. A version imported from elsewhere never inherits permission to write without asking: promoting one turns "allow" back to "ask".
A chat records the version that was active when it started, and each reply the version that wrote it. A reply runs on one version, with one set of folders and grants, from start to finish; after a promotion, a rollback or a new binding, the workspace opens the graduate again before its next reply.
Job contracts have versions in `job_contracts`. Saving a job whose scope or success criteria differ from every recorded version adds a new one; renaming it doesn't. A graduate carries the contract version it was tested against, and a package refuses a locked-test result measured against another bar or other task types, so a new contract version never inherits an old graduation result.
An ask-mode write can fail instead of waiting: a message sent with `approvals: 'fail'` ends at the first write that needs approval, nothing is written, the model gets no further turn, and the reply's `failure` holds the change it wanted (`approval_required`). The CLI will use this.
**Consequences.** Migrations 9 to 13 add the tables and backfill chats and replies as version 1, which every earlier graduate becomes. Rejected and superseded versions stay on disk and in the records, so the history across versions stays complete. The screens still read a format 1 shaped view of the active version (`GraduateSummary.manifest`); the versions, import and export screens come next.

## 040. A migrated harness is known by its new hash, and keeps the hash it was tested with

**Context.** Harness format 2 (decision 030) reads a format 1 folder by checking it against the hash it was saved with, then migrating it in memory, which gives it a new hash. As built, that left graduates and runs from before the change stuck: a run frozen with the old hash couldn't take or repeat its locked test, and a graduate couldn't be accepted, since accepting rewrote its folder and the hash no longer matched.
**Decision.** A migrated harness is identified by its migrated hash from then on, and the old one stays as its provenance: `harness.meta.migrated_from` (in memory, never written to `harness.yaml`) and, in a package, `harness.migrated_from` name the format and the hash of the files as they were saved. A graduate made before versions becomes version 1 with the migrated harness's files and hash, and its package keeps the format 1 hash. A version's harness is always checked against its manifest as stored, so a package that keeps a format 1 harness is checked against the old hash and runs migrated. A run frozen in format 1 takes or repeats its locked test when its version's files still have the frozen hash; it is tested as it runs now, on the coding agent's tools, and its graduate's package records the old hash. Accepting never rewrites a version, so it can't fail on a hash.
**Consequences.** What was tested stays traceable to the files it was tested with, and every version opens, is accepted and rolls back like any other. The package says which kind of result it carries: a graduate made before the change lists that its locked test ran on the older format and its tools, and one frozen before and tested after lists that it was trained in the older format and migrated before its test. This replaces the part of 030's as-built notes that kept such runs from their locked test and such graduates from acceptance.

## 041. llama.cpp serves a version with an adapter on the base in Ollama's store, and its installation stays bound to Ollama

**Context.** Decisions 031 and 035 built the adapter runtime, and 038 named an adapter the way that runtime loads it, but nothing served one: a package with an adapter was refused at import, a version with one never opened, and the installation checks compared the adapter's `base_digest` with the digest Ollama's API reports, which Ollama derives from the model's manifest, not from its GGUF weights. The CLI will run graduates through the same agent host as the workspace. This refines 035 and 038.
**Decision.**
- *Which runtime.* The version decides it, not the installation. A version with an adapter runs on llama.cpp, with the base from Ollama's store under the name its installation gives it; a version without one runs on the installation's runtime, as before. So the installation of a version with an adapter stays bound to Ollama (`runtime: 'ollama'`, the base's name in Ollama's store), `llama.cpp` stays out of `BINDABLE_RUNTIMES`, and one agent rolls back from a version with an adapter to one without, or the other way, with nothing rebound. A version with an adapter whose installation names another runtime needs attention and isn't opened. This replaces 038's reading that such an installation would serve its model with llama.cpp.
- *Before serving.* The runtime's request carries the adapter's `base_digest` and its sha256, and the version's context length. Before any start, the runtime refuses a base whose GGUF in Ollama's store has another digest and an adapter file whose sha256 differs (worked out again only when the file's size or time changes). The agent host checks both when it opens a version, and a mismatch blocks it with the reason and the way out, which never replaces the model under its name, since other versions may use it: add the exact build under a name of its own and set the agent's model to it. A missing llama-server or a base not yet downloaded lets the version open; a reply then says what is missing, so installing it needs no reopening.
- *One server, the right files.* A launch names what each adapter file holds (its sha256, else its size and time), so an adapter replaced at the same path, as when an agent is removed and imported again under its id, restarts the server instead of being answered by the one it loaded before. The server runs with the version's context, which its chats' history is sized to. Closing a graduate with an adapter lets go of the server, and the engine's checks that load a model through it take turns, so one never finds it busy with another agent's adapter.
- *Checks and import.* `assertUsable` accepts a package with an adapter whenever it names an adapter runtime this build serves. Whether this computer can serve it is for the installation checks to say, never a refusal at import. The checks ask the runtime for every problem at once: no llama-server, a build older than 10358 and a base not in the store need attention, each with its fix (set its path or install llama.cpp; update it; download the base, with its size and the exact weights it must have); a base of another build or an adapter that isn't the file installed blocks. A new `adapter-runtime` check names the build found, and the model check's short request goes through llama.cpp with the adapter applied, its server stopped afterwards.
- *Two runtimes, one set of settings.* The agent host serves and the engine host checks, each with its own llama-server and its own folder (`local-runtime/workspace`, `local-runtime/engine`), since each stops a server it finds in its folder answering to its key. Both read the same settings at every start: the llama-server path, quiet mode's thread cap, and the Ollama whose models are unloaded first (the default student's, when it is on this computer), and both stop after 10 idle minutes, as 035 says. Main sends the agent host its settings with `host.configure` before any graduate opens and again on every change; the engine gets them in its start and settings messages. `createAgentHost` requires a runtime, so the CLI passes its own (`hostAdapterRuntime`, folder `local-runtime/cli`) and serves adapters the same way.
- *Quitting.* Main asks the agent host to stop instead of killing it, so it stops its llama-server before it exits. A server left behind by a crash is still stopped by the next start (035).
- *The setting.* The renderer can read `llamaServerPath` but not write it: Architect runs that program, so only a file the user picked in a dialog becomes it (`connections.chooseLlamaServer`). Settings › Models lists llama.cpp with its build, as too old with how to update it, or with what is missing, and checks it again on demand. The workspace's status line says "LoRA adapter", or "Stand-in adapter" for one from the stand-in backend.
- *Tests.* The runtime's `command`, the stand-in llama-server, now has its build checked like any other, so a test can make it too old. In the app, the stand-in runs through `ARCHITECT_LLAMA_SERVER_COMMAND`, a launch switch for tests only.
**Consequences.** A graduate with an adapter imports, opens and answers wherever llama-server 10358 or newer and the exact base are, in the workspace and through the agent host the CLI will share; A01 still waits on a real adapter. Not handled yet: an installation check that loads the model starts the engine's llama-server while the workspace's may be running, and after an adapter reply llama-server keeps the GPU for up to 10 idle minutes, which an Ollama graduate's next replies would share.

## 042. Failure-specific mentoring: verified lessons, one intervention per round, an experiment for every round

**Context.** The expanded spec (sections 6, 7, 8, 16 and 17) asks the mentor to point at the failure in a trace, show the right behavior from that point, prove the correction with the checker, teach with related practice, choose one bounded intervention, and leave a record of every attempt with its budget. As built before this, a round was one harness hypothesis judged on dev: nothing was replayed, no lesson was kept, adapters existed only as a runtime, and the workspace couldn't tell the mentor what went wrong in a reply. Two second opinions (GPT 6 Astra) set the requirements used here: answer-blind continuations in a fresh context, verified fixtures and clocks, whole-batch resume points, a bounded fallback that is labeled, an audit of intermediate writes, the student's prefix masked from training, stable category ids, the four-configuration comparison, and durable stages before any teaching call.

**Decision.**
- *Durable stages.* A round now moves through attempting, diagnosing, teaching, training or clarifying, then evaluating, each persisted, so a restart resumes at the stage it left without a second lesson, charge, training job or record. Lessons and experiments have ids derived from the run, round and item (`lsn_` and `exp_` plus a sha256 prefix), so writing one again replaces it. An attempt's identity includes its configuration: who acted (the student, or the mentor as a reference), the backend, and any adapter with its scale (`student`, `student/llama.cpp/<adapter>@<scale>`, `reference/<provider>/none`); older attempts read as `student`.
- *Diagnosis.* The mentor's reply names up to three findings on this round's failed train attempts, each with the model turn it suspects, step-referenced evidence, the cause, a category and the task type, and one intervention from the menu: procedure, retrieval, helper, weights or clarification, with its hypothesis, worked examples, practice per finding, estimated cost and verification plan. The runner checks every finding (a failed train attempt of this round, a turn inside it) and sets aside the rest with the reason. The menu offers only what this run can do (weights needs training compute and a local adapter runtime, clarification needs someone there to answer), and an intervention whose estimate exceeds what is left is refused and recorded, never silently trimmed. Categories belong to the job, keep their id forever, and are matched by id, then by slug, then created; a new slug can't reset a cap.
- *Teaching.* For each finding the runner rebuilds the attempt up to the turn before the suspected failure, at a whole tool batch: same harness hash, tool runtime, business date and data file hashes, replaying each call and comparing what it returned and wrote. If anything differs the replay fails; the environment is never repaired. The mentor's model then continues as the agent, in a fresh context that holds only the task's prompt, the harness and that prefix, with no expected value. If a try doesn't verify (the replay doesn't hold, or the continuation fails the checker or the audit), the runner tries one turn earlier, then a full demonstration of the task from the start, and the lesson records which (`fallback: none | earlier | full_task`). The checker grades the end state, and a mutation audit rejects corrections that pass while doing harm on the way: a declined write, an answer task that changed a table, a table changed and then restored, an original row removed. A verified lesson keeps a training episode whose targets are only the mentor's own turns; the student's prefix is context, never a target. Related practice takes other train tasks of the same task type (never the same family), ranked by how many findings share their category, and verifies each the same way. Caps: 6 lessons per category per run, 12 per task type; a category stops after 2 measured rounds without a dev gain, a type after 4 (a round refused before it taught or measured anything doesn't count). Every mentor turn as the agent passes the same gate as a mentor call (not released, no locked-test content, within the dollar cap) and is charged to the mentor budget, at the most it was allowed to cost when its reply doesn't say what it used; a refusal ends the round's teaching and, for budget or a leak, the run. A pause, a stop or the wall clock ends teaching between corrections, and the next session resumes at the next try. An error the mentor's model can't get past by waiting (a bad request, a content filter) rejects that try with the reason instead of stalling the run, and a mentor whose model can't act as the agent here (Anthropic's API, for now) keeps teaching off the menu.
- *Candidates.* A procedure, retrieval or helper intervention is a harness change; worked examples (at most two, from verified lessons) become `examples/lesson-<round>-<n>.json` with a retrieval rule that loads them for the finding's task type. A change that writes train answers into the harness (a tool holding any train answer, or a file holding the values of two or more train tasks) is refused as a lookup table; worked examples may show a train answer. A draft is measured as a whole harness, whatever intervention its reply names. A weights intervention builds a dataset from the round's verified lessons plus at most 8 earlier ones as seeded rehearsal, submits it to the training worker under the run's id with an idempotency key from the dataset, and waits in 30 second steps on the run's clock. A clarification asks the person one question; the run waits until they answer, the answer reaches the mentor in later rounds, and an answer that changes what counts as success stops the run, since only a new job contract can change it.
- *Evaluation.* The keep rule is unchanged (decisions 007 and 022: a margin on paired dev measurements, then a confirming measurement), and hard gates come after it: every dev write within the job's writable files, p95 latency within the job's limit, and never an adapter from the stand-in backend. A weights round is measured in four configurations with the same backend, base, decoding and seeds: H0/A0, H1/A0, H0/A1, H1/A1, where H1 is the round's harness and A1 its adapter; a measurement reused from earlier says where it came from. Every round that tries a change ends in one experiment record with its kind, inputs (lessons, findings, intervention), measurements, gates, budget (mentor dollars and tokens, student dollars and tokens, compute dollars and minutes, examples, trained tokens, attempts, minutes) and a disposition: kept, reverted, rejected (harmful, or a gate failed), invalid (refused before measurement) or stopped. A failed hard gate always rejects. A clarification round tries no change, so it records its question and answer on its intervention and no experiment; the progress view counts clarifications apart. Progress and the capability breakdown are computed from these records only. Weights are offered only where they can work: a training worker, an adapter runtime, a locked test on the local student (the hosted copy can't load an adapter), and a real backend; the stand-in, which trains nothing, is offered only to tests.
- *Freezing and the locked test.* The frozen graduate records its whole configuration: backend, adapter (id, file, sha256, scale, the base's digest) and decoding. The locked test runs exactly that, refuses an adapter whose file changed, and repeats on the seeds the job declares in advance (`evaluation.lockedTestSeeds`, 101 and 102 in decision 037). Each repeat is stored with its seed and shown on the card, and a scenario passes only if every repeat passes: repeats are never counted as more scenarios.
- *Spark as a reference.* On a finished run, Spark can act as the agent on the run's dev tasks or its locked test, with the frozen harness, as a comparison. It has its own disclosed dollar cap, its own gate and its own configuration key, its costs are filed under `reference` and never as the student's, and nothing it does reaches mentoring, the run's totals, its card, its capability numbers or its list of recent attempts. On dev every request passes the leak check. On the locked test the mentor is released first and the vault opens only on that proof; the leak check is off there because the test's content is the request.
- *Teach this and Improve agent (spec section 8).* Each settled workspace reply keeps its work: every model turn, every call with its arguments, every result as the model saw it. A person corrects one reply by saying what was wrong, what they wanted and their evidence. It goes to the mentor only when the job shares corrections (`sharing.corrections`) and the person consents to that exchange, behind the leak check and a $0.25 cap. The mentor classifies it (procedure, source, weakness, ambiguous, invalid) and proposes a lesson; nothing is queued until the person queues it, and an ambiguous or invalid one can't be. A procedure or source lesson can take effect at once as an instruction-only candidate version: the active version's harness with one line added under "From the person's corrections", unevaluated, its parent recorded. Improve agent runs every queued lesson through the usual rounds as a run that starts from the active version's harness and adapter, shows the lessons to the mentor beside the train evidence, keeps to the budget the person was shown, and ends in a candidate version of the same agent measured on dev. It never takes the locked test again, not by a re-test and not with Spark as a reference: the earlier result isn't reused as guidance, and the candidate says no locked test measured it. It needs the job to still share corrections, and it takes, in the transaction that writes its run, only the lessons still queued. The active version never changes; accepting and promoting stay the person's. Another run holding the student makes it wait, and it says so. Version writes for one agent take the graduate library's lock, so an instruction lesson and an improvement can't race for a number.
- *Wiring.* The engine host resumes the training worker before it recovers runs, scopes jobs by run id, reads the recipe from `trainer/` (packaged under `resources/trainer`), and uses Hugging Face Jobs only when a token resolves, the stand-in otherwise. The engine has one llama-server (decision 041): the utility process makes the adapter runtime once and gives it to the loop's adapter students and to the installation checks, and an evaluation through it takes the same turn the checks take. The mentor acts as the agent through the existing provider code.

**Consequences.** A02 (a failure becomes a replayed or full-task correction that passes the checker), A03 (harness and weights measured apart, a harmful change rejected, the prior version still running), A04 (a correction enters the queue under the sharing setting and becomes a candidate without touching the active version), A05 (progress and capability reconcile with the stored experiments, rejected and stopped included) and the records A14 asks for are covered by tests on fakes, and one whole chain runs on the returns desk with the real tools, sandbox, checker, vault and loop and scripted models; no model, Ollama, llama.cpp, OpenRouter, Meta or Hugging Face call was made. The stand-in backend proves the plumbing and is never kept. Limits as built: the Hugging Face token isn't yet passed to the engine's utility process, so the desktop app trains only with the stand-in; the stand-in's base header is read from the default student in Ollama's store; graduating with an adapter needs the llama.cpp student to report the base's digest; the screens for lessons, experiments and Teach this aren't built; an imported agent can't be taught here, since its job isn't on this computer. Known gaps from the independent review, not fixed yet: a draft's harness isn't checked for train answers; with no business date, a computer at UTC+12 or later records attempts a day ahead, so every replay falls back to a full demonstration; a crash between a refused lesson and the round's end lets teaching go on after restart; closing the app can wait for an adapter download; after a confirmation, the four configurations don't all cover the same seeds, and once an adapter is kept A0 is that adapter, not the bare base; a round stopped during training records compute as of the stop; an adapter's file is hashed as found rather than checked against its job's artifact record; a backend that changes between submit and restart sends a second job; and an improvement that keeps failing while it writes its candidate can't be stopped.

## 043. The architect command runs graduates through the workspace's own agent host

**Context.** Spec section 12 asks for a terminal command over the same package loader, runtime, bindings, permissions and event stream as the desktop app, with no second execution path, versioned JSON in and out, stable exit codes, and no approval that hangs or approves itself. The app's agent host is a plain Node module (decision 003) and already ends an ask-mode write as `approval_required` when nobody can answer (decision 039).
**Decision.**
- *One runtime.* `apps/cli` is a plain Node program. It opens the app's own data folder (Electron's `userData` for "Architect", or `ARCHITECT_USER_DATA`), the same SQLite store, and runs a graduate through `createAgentHost` over `workspaceStore`, in its own process: the same loader, active version check, bindings, grants, write approvals, tools, sandbox and `message.updated` events as a chat in the app. Install, inspect, verify, export and publish call the engine's graduate library, importer, exporter and publisher, opened outside the engine host through `openLocalLibrary`, which converts and clears nothing (that stays the engine host's job at start).
- *Local models.* It reads the app's own `settings.json` for local models the way the app gives its hosts theirs (`runtimeSettingsOf`, `quietThreadCap`): quiet mode's thread cap for a local student and for llama-server, the llama-server chosen in Settings, and the default student's Ollama only when it is on this computer. A version with an adapter runs on a llama-server of the command's own (`local-runtime/cli`, decision 041), which stops when the command ends.
- *Offline.* Before a graduate loads (run, verify, and an install's import step), the command installs the workspace's loopback-only network guard in its process. It never constructs a mentor; lint keeps mentor and vault code out of `apps/cli`. A Hub download happens before the guard goes up, and the import after.
- *Sessions.* A conversation is kept in memory unless `--save` asks for a chat in the app, and either way the session only sees its own chats, so it never settles a conversation the app has running.
- *Batch.* `architect.run-request/1` in, `architect.run-result/1` out, both zod schemas in `packages/shared`, keys snake_case. The request is checked before the agent opens; input references must be files the contract names, in folders bound and granted here. A result is written for every run past its command line, whole or not at all. Steps and messages go to stderr; stdout carries only results.
- *Approvals.* Asked on a terminal, line by line; with `--non-interactive`, a request on stdin, or no terminal, the reply ends `approval_required` with the change it wanted, and nothing is written.
- *Exit codes.* 0 succeeded, 1 runtime error, 2 invalid input, 3 not permitted (approval, binding, grant, blocked or attention-needing installation, token, unaccepted findings), 4 task failed (refused, no answer, an unusable reply), 130 cancelled. A runtime failure is told from a task failure by whether the agent host reported an error for the reply, as it does for adapter errors the loop treats as the runtime's.
- *Getting it.* `pnpm architect` in development, through tsx. The desktop build bundles the same sources (`out/cli/architect.mjs`, about 1 MB) beside the sandbox, packaging leaves it out of the archive, and each installer carries a launcher that runs it on the app's own binary with `ELECTRON_RUN_AS_NODE=1`: `architect.cmd` beside `Architect.exe`, `Contents/Resources/architect` on macOS. Nothing adds it to `PATH`.
**Consequences.** What the command does is what the app does, so tests compare them directly (A10). The command can't read keys saved in the desktop app (the system encrypts them for the app), so its export scan knows only the Hugging Face token it would use, and it doesn't follow the app's quiet mode for local models. An import from the command and one from the app for the same agent at the same moment aren't coordinated: version numbers are taken in each process. Checked on Windows with the unpacked installer build; the macOS launcher is untested.

## 044. Hugging Face publishing and installation, by commit

**Context.** Spec section 13: publish the same package to the Hub, private by default, never widening a repository's visibility, with a generated model card; install by an immutable revision; never show a failed or partial upload as a release, and let a retry finish without duplicate records. Training already had a Hub client with small commits only (decision 035), and an adapter is about 200 MB. No Hugging Face token exists on this PC yet.
**Decision.**
- *One client, one fake.* The training client moves to `packages/engine/src/hub` and gains what publishing needs, through the Hub's documented HTTP API rather than a new dependency: repository visibility, public or private creation, preupload, the LFS batch API with basic and multipart transfers, LFS verification, commits that add LFS files and delete files and can name their parent commit, file listings by revision across pages, and capped downloads. The token goes only to the Hub's own API for calls that need it: never to an upload or download host, a signed completion address or a redirect. The fake Hub in `test/support` serves all of it, with a second host for uploads and downloads that records whether a token ever reached it.
- *Public repositories.* Reading one needs no token: a read goes without one when there is none, and only a change requires it. Plain HTTP is allowed only to a Hub on this computer (tests), never for an address a Hub on the internet hands out.
- *The token.* One resolver for publishing and the training backend: the key saved in the app first (the new `huggingface` service, bound to `huggingface.co`, and only when the token goes there), then `HF_TOKEN` or `HUGGING_FACE_HUB_TOKEN`, then the token file `hf auth login` writes. The command uses the last two. It reports where a token came from, never its value.
- *What a repository holds.* The package at its root, exactly as an export would write it, and `README.md` beside it. The package goes up in one commit (LFS for whatever the Hub asks), and is checked file by file against the Hub's own listing at that commit; a second commit adds the model card, which names that commit in its install command. Files an earlier version left in the package's folders are deleted in the same commit as the new package; the rest of the repository is left alone.
- *Privacy.* A new repository is private unless the request says public. An existing private repository stays private (the publication records it as private and says so); a public one is refused for a private publication. Publishing runs the export's review and scan over the package and the card, and stops on findings until the request names the digest of the ones reviewed.
- *Records.* One `publications` row per version and repository (a unique index): `staged`, `uploading`, then `complete` with the package's commit and the repository's URL, or `failed` with the reason. Trying again reuses the row. When the Hub already holds exactly the package at the branch's head (an attempt that failed after its commit), no new commit is made, and only the card is added if missing. A complete publication of the same package is returned as it is; one of other files (other shared resources) to the same repository is refused.
- *Installing.* `hf://owner/name` resolves the commit once (the one named, or the one `main` points at) and records it with the version (`graduate_versions.source`, migration 15). Only `graduate.json` (at most 1 MB) and the files it lists are downloaded, within a package's limits, each checked by sha256 and size as it arrives; then the folder goes through `importPackage` like any package. A newer publication never changes an installed version; installing again without a commit adds the newer one beside it, as a candidate.
- *The package format* doesn't change. The model card and the records are outside the package.
**Consequences.** Live Hub validation waits on a token: everything is tested against the fake Hub, including LFS uploads, multipart, failed uploads and retries, and A12 stays partly done until one real publish and install. The Hub now stores new files with Xet; huggingface_hub without its Xet extension still uploads through the LFS API this client speaks, and whether the Hub takes that for every repository is the main thing a live run must confirm. Publishing over IPC has no progress events yet, and the desktop screens for it are the UI's work.

## 045. The comparisons runner, and where it refines 037

**Context.** Decision 037 fixed the evaluation plan before any measurement on the coding-agent runtime. `scripts/experiment.ts` can't run it: it hard-codes home services and the old methods, and its one-shot is a harness draft, not an adapter. Running 037 also needs the gaps decision 042's review left in a weights round closed, records it lacks (peak memory, cold start), and a few choices 037 left open. They are settled here, before any measurement.
**Decision.**
- *The runner.* `packages/engine/scripts/comparisons.ts` (plan, run, probe, report) over `packages/engine/src/comparisons`. One data folder per comparison: every arm is a run in one store, found again by the arm its protocol names, so a restart never starts one twice; calibration is written attempt by attempt; the engine resumes the rest.
- *Cost first.* The bare student on the 15 calibration tasks, hosted, prices and times an attempt before any arm spends. Each arm is projected at the most its caps allow (a refinement round is its 12 train attempts and four dev runs of 45, for a confirmation), Spark at each arm's own cap and compute at each job's whole authorization. What isn't measured is assumed and labeled so in the projection and the report: a Spark author call (40,000 tokens in, 6,000 out), Spark as the agent on a task (the student's measured tokens at Spark's price), a local attempt (117 s until the probe times the 2-bit build) and a job ($2.70).
- *Funding in 037's order.* An arm is funded when every budget it draws on (student credit, Spark, compute, local GPU minutes) still has room after the arms before it; the fixed arm needs at least $5 of student credit left, as 037 says. An arm that doesn't fit is not run, with the reason, and a plan the caps cut down waits for `--confirm`; one missing a prerequisite (compute, the GPU window, the arm it starts from) is reported and doesn't wait. A later arm on other budgets may run when an earlier one didn't fit: with $15 of student credit, arms 1 to 5 take $11.09 with the headroom, the fixed arm needs $5.87 and is dropped, and the weights arms, which need about $2 of it and otherwise compute and GPU time, run when those are granted. Calibration and the regression check come off the credit first. A plan is fixed once confirmed, its arms and every setting that changes what it spends or measures: no arm joins it later, since one that learned after others' results were read would break the next rule; only the local re-tests of graduates already frozen may join, when granted GPU minutes cover them.
- *Freezing before reveal.* Every arm's run holds its locked test after freezing (`holdTest`); the runner releases the tests only once every funded arm is frozen or has ended without a graduate. Spark as a reference, the local re-tests and the repeats run after that.
- *Repeats.* Each arm declares seeds 101 and 102 at freezing, as 037 says, but its locked test runs 101 alone (`deferRepeats`); the repeat, arm 5, runs 102 later as a resumable session of its own (`controller.repeat`), so it can be dropped when money runs short. It never changes the run, its totals or its card.
- *Each arm's caps.* Spark, compute and the wall clock (twice the arm's projection, at least 12 hours) are the run's own job budget, which the engine holds hard. The hosted student's dollars are the runner's to hold, at every step and at the prices attempts have actually cost: before an arm starts, its worst case must fit what is left after everything paid and what the arms before it still hold (the repeat counted before arms 6 and 7); the locked tests are released in 037's order while the credit pays for them; each repeat runs while it does, priced at that arm's own test attempts. Each arm's own cap is its projection times 1.2 (`--headroom`, or set by hand). An arm whose rounds decide its size (targeted, fixed, the failure-specific adapter) is held to it at each round's start once it has kept a change: a round at its most and its locked test, at its own attempts' price, must fit, or it stops there and freezes what it kept. A fixed-size arm (bare, draft, the one-shot adapter) is never stopped, since stopping one could only lose it: a stopped bare run takes no locked test. When prices drift, a fixed-size arm can pass its own cap, and later arms are dropped for it, in 037's order. An independent review found the first version stopping arms on 4% of price noise, and its findings are the tests in `comparisons-runner.test.ts`.
- *The arms.* 1 bare (the blank harness). 2 the draft (one-shot, Spark capped at $1). 3 targeted: the draft's kept harness, two refinement rounds, $5 of Spark less the draft's spend (decision 026). 4 Spark as the agent with the bare arm's frozen harness, so it sees no lesson, on the same 60 tasks, tools, limits and seed 101, capped at $4. 5 the repeat of arms 1 to 3 under seed 102. 6 the fixed intervention: targeted's setup with the menu fixed to procedure (`interventions`). 7, only with real compute and the GPU window: a one-shot adapter, one job on verified demonstrations of 4 train tasks per type chosen by seed and never from a failure, kept as measured unless a hard gate fails (`oneShotAdapter`); and a failure-specific adapter, the menu fixed to weights, two training rounds under the keep rule. Both weights arms start from the blank harness (H0) and adopt the targeted arm's frozen harness whole as round 1 (H1, `adopt`), so their four configurations are the two harnesses 037 names; their rounds run whatever dev says (`fixedRounds`), since one that stopped at the target would measure nothing; each job is authorized for 90 minutes at most (`maxJobMinutes`); their verified lessons may go to remote training, the shop being synthetic. They take the locked test on this computer: on llama-server with an adapter they kept, on Ollama without one.
- *Backends.* Mentoring, dev and the locked test run on the hosted copy, pinned on OpenRouter to DeepInfra's bf16 with no fallback, since OpenRouter also routes Glimmer to Together's FP8 (a hosted endpoint's new `providers`, sent as `provider.order`). This computer's student is the 2-bit build that fits its GPU (`muse-glimmer:30b-iq2`, or `--local-model`): every graduate pins it when it freezes, which reads Ollama's metadata and loads nothing, so the runner checks it before anything spends. With `--local-ollama` the bare and targeted graduates also take the locked test on this computer, after the probe (3 calibration tasks, with the meter) has timed it. The report has one table per backend (hosted, Spark, local Ollama, local llama-server), and pairs only within a table, except Spark's, which pair with the hosted arms as a reference.
- *The report.* JSON for the app (`ComparisonReportSchema` in shared) and Markdown for the README, from stored records only: per backend, counts with 95% Wilson intervals, paired wins and losses per scenario and per type, refusals (each a failure, since the contract supports every type), p50 and p95 latency, cold start and peak memory apart; per arm, Spark's tokens and dollars, the student's dollars and tokens, compute dollars and minutes ("at most" while a job may still run), examples and trained tokens, its caps, and each round's dev regressions by type; a row from a test that didn't finish is marked partial; repeats as each seed and "passed under every seed"; the weights rounds' configurations; identity (model, provider, quantization, GGUF sha256, runtime build, chat template, sampling and limits, harness and adapter hashes); the measurement model and projection; disclosures, 037's statement when no weights arm ran among them; "not run" with the reason. A dry run on fakes says so at its top.
- *Records the evidence screens can read*, all additive (migration 16): a run's `protocol` (`RunProtocolSchema`: `arm`, `holdTest`, `released`, `deferRepeats`, `interventions`, `adopt`, `oneShotAdapter`, `maxJobMinutes`, `fixedRounds`); `repeats` (run, target, status, error); `runtime_measurements` (`RuntimeMeasurementSchema`: run, split, target, configuration key, harness version, seeds, backend, `peakProcessBytes`, `peakGpuBytes`, `coldStartMs`, samples, sampler), written by an optional meter for each stretch of a locked test on this computer; `computeSettled: false` on an experiment budget whose training job hadn't ended; and a `demonstration` teaching item.
- *Decision 042's gaps the runner relies on*, each with a test: when a round confirms, every configuration is measured again, so all four cover the same seeds; A0 is always the bare base, and the incumbent with its kept adapter is measured apart as what the candidate must beat; a job this run already sent for the same examples is the round's job, whatever backend is set up now; a round that ends while its job runs records the job's whole authorization until the job ends, then its own cost; an adapter file must match its job's artifact record, or the round is invalid.
**Consequences.** Every number the README and the demo will claim comes from these records, and the dry run (`comparisons-dry-run.test.ts`) runs every arm through them on fakes, including a dropped arm, a stopped one, and a kept adapter that freezes and packages with its `base_digest`. The real runs wait on the owner's go-ahead and money; the weights arms on a Hugging Face token and a GPU window, and without them the report carries 037's statement. The stand-in never trains a comparison's adapter; the dry run's trainer is a fake labeled as one. One process holds an output folder at a time (a lock), since two would pay twice. Not handled: the student's credit is held at each step at measured prices, not per attempt, so a step already started can pass it by what its attempts cost beyond the measure, and OpenRouter's own balance is what stops calls past it; local GPU minutes are a funding check, not a hold on the running time; OpenRouter's provider pin and the meter's readings are unverified live; Ollama's and llama-server's builds are read when the plan is made, not per attempt.

## 046. One GPU lease for all of Architect's processes

**Context.** On one computer Architect has four users of the GPU: Ollama, which it asks for student runs, plain graduates' chats and checks, and the three llama-servers it starts itself, the workspace's (`local-runtime/workspace`), the engine host's for checks and weights rounds (`local-runtime/engine`) and the architect command's (`local-runtime/cli`) (decision 041). A llama-server start unloaded Ollama's models, and nothing else coordinated them. An engine check, or `architect run` beside the open app, could start a second llama-server while the workspace's held the GPU, which runs out of memory on a 12 GB card (the 2-bit base alone is 10.7 GB); and an idle llama-server kept the GPU for its 10 idle minutes while Ollama answered a plain graduate's chat, so Ollama spilled to the CPU.
**Decision.**
- *One lease, in two files.* Every Architect process on one data folder takes the GPU lease before a model loads on the GPU and holds it while a request runs. `local-runtime/gpu-lease.json` says who holds the GPU (each process's use of it, busy or not, and what it is doing) and who waits (each with its place in line); `local-runtime/gpu-lease.lock`, created exclusively, is held while one process reads the lease, changes it and writes it back in one synchronous step, so no two processes interleave and the lock lasts milliseconds. A process takes the lock only when its look would change something: most looks only read. The lease is replaced by a rename, so a process that only looks never reads half of it, and a decision stands only once it is written: a grant whose write fails is taken back, and the request waits again. Plain files behave the same in Node (the command) and in Electron's utility processes, with no native module. Two simpler designs were set aside: a lock taken only around a llama-server start can't tell an idle server from a busy one, nor keep a llama-server from starting under Ollama mid-reply; and one process coordinating the others over a local pipe needs a way to hand over when it exits, and would show as a connection in the workspace's offline test.
- *Who holds it.* A llama-server holds the GPU alone. Ollama's users share it, since Ollama schedules its own models. One process holds one use at a time: one that has an idle llama-server and needs Ollama gives its own server up first.
- *Giving it up.* A holder with nothing running gives the GPU up as soon as someone who can't share it waits: it stops its llama-server, or unloads the Ollama models it sent requests to (`keep_alive` 0), and only then leaves the lease, so whoever waits never loads a model beside it. A holder whose server stopped by itself (its 10-minute idle stop, or a crash) leaves at once. An Ollama user leaves once Ollama's own keep-alive, 5 minutes, has passed since its last request, without unloading anything.
- *Waiting.* A busy holder keeps the GPU. Whoever asks waits its turn for up to 5 minutes, then fails with a busy error that says who holds the GPU and what they are doing ("The GPU is busy: the workspace is answering a chat with Returns desk.") and what to do ("Wait for that reply to finish, or stop it, then try again."). It is the runtime's error (`gpu_busy`), so an evaluation stops on it and waits as decision 029 says, an installation check reports it as needing attention, and the command exits 1. A request still waiting can be stopped.
- *Turns.* A reply someone is reading goes first, then an installation check, then a run's request; within a rank, whoever waited longest, and a process that already holds the GPU lets a new request of its own in only when nobody waits ahead of it. A reply in the workspace or the command holds the GPU from its start to its end, and its model turns run inside that hold (`GpuHold.run`), so they always go on and the model isn't swapped out between them. While it waits on a person (an approval, or a change to try saving again) it runs no model and may wait for hours, so it gives the GPU up as an idle holder does (`GpuHold.pause`), and its next model turn takes it back in its turn; if someone took it meanwhile, that turn waits like any request and the model loads again. A run holds it for each request, so a chat or a check gets a turn between a run's requests. A check holds it for its one request. A request the guardrails refuse never reaches the model, so it takes no turn.
- *A reply that waits says so.* When a reply has to wait its turn, the lease tells the agent host who has the GPU (`GpuWatch`), and the reply shows one quiet step in its steps, in their usual style: "Waiting for the GPU: Architect is checking an agent on this computer". The step (`kind: 'wait'`) goes as soon as the reply has the GPU, and a settled reply never keeps one. A GPU that is free is taken at once, with nothing to say.
- *Before Ollama.* A request to Ollama on this computer takes the lease as Ollama's, so every idle llama-server of Architect's, in any process, stops before Ollama is asked anything.
- *The comparisons script.* The comparisons runner (decision 045) works on a data folder of its own, and takes the lease on the app's (`appDataDir`, found as the app and the command find it) as `comparisons`. Its own llama-server (`local-runtime/comparisons` in the comparison's folder) and its students on Ollama hold the GPU for each request, as the engine's do, and give it up when idle to any process of the app that asks. Unlike the app's processes, it takes the GPU only when it is free: no other process holds any of it, not even a share of Ollama, and none waits for it first (`onlyWhenFree`). Otherwise it fails at once with the busy error and "Close Architect while a comparison runs, then run the command again.", since a measurement taken beside the app's work would be wrong, waiting out a long local evaluation could take hours, and taking the GPU from an idle app would trade model loads back and forth. In a run the failure goes the way of any busy GPU (the evaluation stops, waits as 029 says, and pauses with the reason, and the comparison ends incomplete until it is run again); `probe` fails at once. The meter's unload before it times a cold start goes through the lease too: the script holds the GPU alone while its llama-server stops and Ollama's presets unload, its own students on Ollama having given the GPU up first and unloaded what they used, so either backend's cold start begins with nothing of Architect's on the GPU, and no process of the app loads a model meanwhile.
- *Processes that die.* An entry whose process has exited is gone, and so is one its process hasn't renewed for 60 seconds (as when the system gives a dead process's id to another). A dead llama-server holder still blocks until its server is gone: the next process to look stops the server its folder records if it answers to the record's key, or is still loading (llama-server answers "Loading model" before it checks any key), giving it 10 seconds to answer, since a server on a busy computer can be slow to and one taken for another program would be left running; it drops the entry only once that process has exited. On Windows the server goes with its parent anyway (GOTCHAS); on macOS and Linux it outlives it. After the computer sleeps every entry is old at once, so a process that finds it slept gives the others 60 seconds to renew theirs, and gives up what it held idle, which may have been taken. A process that closes takes its entries with it; one that exits without closing leaves its llama-server's entry, for the next process to find the server gone or stop it. A lock left by a process that died mid-change is taken away once its process is gone or 5 seconds have passed, by one process at a time, under a second lock, and only if it is still the same lock; a lock that can't be taken for 10 seconds means the folder can't be written, and waiting requests fail with that at their time.
- *Unchanged.* Quiet mode's thread cap is still part of each launch, and the 10-minute idle stop still stops the server, which then leaves the lease. A llama-server start still unloads Ollama's models first, which now matters only for models something other than Architect loaded.
- *Where.* `GpuLease` (`local-runtime/lease.ts`), with its rules apart in `lease-rules.ts` and its files in `lease-store.ts`. The adapter runtime holds it around each llama.cpp request and stops its server when asked; `OllamaUse` holds it around each request of a student on Ollama here. The agent host's process (owner `workspace`), the engine's utility process (`engine`) and the command (`cli`, through `openLocalLibrary`) each make one, and so does the comparisons script (`comparisons`, through `comparisonLease` in `comparisons/environment.ts`). `createAgentHost` requires one, as it requires a runtime; `createEngineHost` takes one, and without it (tests and scripts on a data folder of their own) coordinates nothing.
- *Also in this change.* A base of another build is refused with a fix that can be followed: Ollama can't download a build by its weights, so the person needs the exact GGUF the adapter was trained on, from whoever published the agent, added to Ollama under a name of its own, then set as the agent's model; the fix names the base as the package records it when that says more than the name here (a hub address, a revision). And the agent loop's entry points take the part of a job they read (`AgentJob`: the business date and the output folder), which a job and the workspace's object both are, so the workspace no longer builds a job with a budget of one round, splits of 1/1/1 and a mentor labeled "None".
**Consequences.** Two llama-servers never hold the GPU at once, and Ollama never answers while an idle llama-server of Architect's holds it, across the workspace, the engine, the command and the comparisons script; tests show it between real processes with the stand-in llama-server, which now records any other stand-in still running when it starts. An independent review of the first build found nine problems, all fixed with tests or probes: a grant that stood although its write failed, a lock wait with no end, a dead holder's server taken for gone while still loading, an exit that dropped a server's entry before the server stopped, a lock left behind for a moment on Windows, a race between two processes clearing one lock, a process not noticing it lost the GPU while it slept, a new request jumping an equal one that waited longer, and a busy error that called an idle holder one letting go. A chat can wait behind a run's request and a check behind a chat, and each change of hands costs a model load. A training run whose request waits past 5 minutes for a long chat stops with the busy error, waits as 029 says, and pauses with the reason if the GPU still isn't free. Not covered: the lease belongs to a data folder, so two copies of Architect on different data folders don't coordinate; Architect can't free memory another program holds (LM Studio, a llama-server the user runs, a model loaded through Ollama by another app); and a mentor or a student on another runtime on this computer (LM Studio, an OpenAI-compatible server) takes no part.

## 047. Versions, export and import on screen, and what they asked of the engine

**Context.** Decisions 038 and 039 gave every graduate versions, an installation and a package, with an API but no screens. The screens had to follow the design canvas (rows, icon-led actions, no standing captions), keep this computer's checks apart from the author's result (spec section 11, A13), and show nothing the records don't hold. A few gaps in the engine stood in the way.
**Decision.**
- *Words.* The screens say what the General tab already said: a version's harness is its *setup*, an adapter is its *trained weights*, and a folder is *chosen*, never bound. A blind read of the first screenshots (a fresh reviewer who saw only the images) stumbled on harness, adapter, bound, "Your data/ files" and a bare "57/60"; those were replaced, not explained. A second blind read, after the merge, found two rows vouching for each other ("Runs it with llama.cpp" with a check beside "llama-server isn't installed"), so the computer's row now names only the computer; it also stumbled on "locked test", which the screens now call the final test, as the General tab does.
- *Versions* live in a Teaching tab of the agent's settings (General, Permissions, Teaching, Report, Export), newest first. Each row shows the version's standing (active, candidate, rejected, or its own evaluation: ready, experimental with why, below its target or tested on a hosted copy, or not evaluated), the score from its own report ("55 of 60 passed", under a "Final test" column), where it came from (its parent, or imported) and its date. Promote (a candidate or a newer accepted version) and Roll back (an older accepted version) each ask first, in a dialog that lists what changes: which version's setup, and trained weights when it has them, answers from the next reply; that the one it replaces stays; for a version from another computer, that saving goes back to Ask first; and, for a version its own locked test didn't vouch for, that it hasn't taken a final test, by how much it fell short of the job's target, or that it took its final test on a hosted copy. Promoting a candidate records its acceptance and its promotion as the two events they are. A reply's steps end with the version that answered it; nothing else in the chat names a version.
- *Export* is a review that comes first: what goes in the package, the scan, what stays on this computer (each with a lock), then the setup, the trained weights and the report on their own. Sharing a resource is a switch, off until chosen. A finding holds back every export that would carry it until the user ticks "Export anyway", and the footer says how many flagged lines wait for that. The scan carries one line that trained weights may retain information from their training data, or, for a version without them, that its setup is written from the user's tasks and may quote them. The old folder export is gone from the screen: the package export writes the folder and the `.architect.zip` together (038).
- *Import* opens from the sidebar's agent menu and runs as its own flow: Package (the package, this computer and its model, and the author's result, titled "Evaluated on the author's computer"), Folders, Permissions (nothing the package asks for is granted until chosen, and a folder left unchosen has nothing to grant), then Install, whose results are titled "Install checks on this computer" and read Ready to run, Needs attention or Can't run. A package that continues an agent here skips Folders and Permissions, since that agent keeps its own (038). Every failed check comes with a way out: choose or allow a folder, set up llama.cpp, download the model, check again, or remove an import that can't run here. A version with trained weights (041) adds a llama.cpp row to the Package step and to the install checks, with its build or what is missing; Set up llama.cpp in Settings opens Settings at Models, where 041's llama.cpp row is, and closing Settings checks the package again.
- *What the engine gained*, all additive: `previewImport` (the package checked exactly as an import checks it, where it would go, and the compatibility and model checks the installation runs, before anything is installed or loaded; for a package with an adapter, the adapter runtime looks at llama-server, the base and the staged adapter file, as 041's checks do, through `adapterRequest`, which `serveRequestFor` now builds on); `exportPart` (a part copied from the verified version under the same scan, the review listing each part with its own findings digest); `report` (the report card a version carries); install checks run the first time a graduate is listed, accepted, promoted or rolled back to, with the model described but not loaded, so one made here never shows as unchecked; and an approval that was allowed but couldn't be saved goes back to waiting with the reason (a file open in another program, a read-only file or a full disk said as such), so the user can try again or give up, and shows as failed when given up, stopped or unanswerable. A table read's step counts rows, as its table does.
**Consequences.** An imported agent's tabs work without its author's job or run: General and Permissions read the version's contract, and Report reads the report card the version carries (`graduates.report`, held to its checksum), titled as the author's when the version came from elsewhere. The checks run on first listing ask the local runtime to describe the model once; with no runtime running they fail fast and say so. The renderer turns a passed or skipped check into plain words and keeps a failed check's own sentence, which says what to do; it reads a few of the engine's phrases to do so, which a test pins.

## 048. Teach this, the teaching queue and Improve agent on screen

**Context.** Decision 042 built Teach this and Improve agent in the engine with an API but no screens. The expanded spec (section 8, A04) asks that a correction be shown as a proposed lesson before anything is queued, that nothing leave the computer without consent, that an instruction can take effect as a recorded version without retraining, and that Improve agent run within a displayed budget, make a candidate without touching the active version, and say what improved, what didn't and whether promotion is allowed. Two gaps stood in the way: an improvement that kept failing while it wrote its candidate couldn't be stopped (042), and a job's `sharing.corrections`, which Teach this needs, had no control anywhere on screen.
**Decision.**
- *Teach this.* Every settled reply has a flag beside Copy, named "Flag for teaching". It opens a sheet that asks what was wrong and what it should have done (or the right result), and, optionally, what it should have used: the files its job lists, as chips, or rows pasted in. The footer says what leaves, "Only this exchange, its steps and what you add go to Spark", with the cap ("Up to $0.25"), beside the one button that sends it, "Share with Spark"; until then nothing reaches the engine. Both are worded to agree with the status line's "Private from Spark" (050): chats stay private, and this exchange is the one the person shares. That send is also the job's leave to share flagged answers (`teach.shareCorrections`), since nothing else on screen could give it, and each flagged answer still needs its own send.

The choices are to queue it for Improve agent, to save an instruction as the next version (the active version keeps answering; the new one is a candidate with no final test yet, and only Promote makes it live), or to discard it; any lesson can be said again. The engine's leak-check refusal, which names the locked test, takes the form's place as "Spark can't read this exchange: it quotes a task from its final test, which Spark must never see", so the same exchange isn't offered again; any other failure keeps the form, to send again.
- *An agent from another computer* opens the same sheet, which says why it can't be taught here, and Teaching says so in place of its rows. No dead buttons.
- *Teaching* gains Lessons above Versions: Flagged answers (what waits for the person and what is queued, with a review drawer where each lesson can still be queued, saved as a version or discarded), Teach it something new (a new chat, then a flag on its answer, since a lesson is always taught from an exchange), and Improve agent with the budget it keeps to.
- *Improve agent's budget* is the job's own caps, cut to what one improvement may be given (10 rounds, $100), with compute dollars only where weights may train here, and time; it says when it would wait for another run using the student. It asks first, then opens the Train screen.
- *The improvement runs on the Train screen* and its drawers, with its own steps (Lessons, Improve, Report), the lessons it teaches at the top, "Not taken" for the final test, "Writing its new version" where a training run takes its final test, and Stop at every point. *Its report* (`/runs/:id/improvement`) gives the new version's score on the check tasks against the version it started from, per task type what improved and what didn't, what it spent, its lessons, and whether it may be promoted, with Promote; it says the version hasn't taken a final test.
- *What the engine gained*, additive with zod schemas: `teach.overview` (whether the agent can be taught here and why not, the mentor, the cap, Improve agent's budget, whether it would wait), `teach.shareCorrections`, a run's `improves` in its detail, and the improvement limits as shared constants. One fix: Stop ends an improvement while it freezes or writes its candidate (a step in flight finishes first, and a candidate it wrote stands; otherwise it ends stopped, with its lessons back in the queue), where before such an improvement stayed paused for good.
- *A blind read.* A fresh reviewer saw only the 23 screenshots and said what each was for and what it would do next. Its findings, fixed with words rather than explanations: "Apply as version 3" read as going live (now "Save as version 3", so only Promote means that); "Not evaluated" beside a score on the check tasks read as a contradiction (now "No final test yet" in the versions list too); "Add to the queue" didn't say which queue ("Queue for Improve agent"), and a queued lesson seemed to start itself ("waits until you start Improve agent"); the line of what leaves didn't say the note goes too, and its amber dot read as a warning; the proposal's "Spark" row read as a name, not a reason (now "Why"), and a flagged lesson hid what the person had said (now "You said"); the leak refusal offered to send the same exchange again; the improvement dialog left out its rounds cap and what happens when nothing scores better; "kept no change" was jargon; the report's Candidate badge carried a check mark and its "What didn't" bars looked like wins; and "the job it learned from" clashed with `jobs.csv` and offered no way forward (now a way forward on the computer that made it). Left for their own areas: the status line's "The setup from round 7" and "Spark not connected", the sidebar's training percentage, which reads as progress, the Train screen's practice, check and final-test tasks, and v1's "Experimental".
- *A second blind read*, by a different model, of 13 screens after those fixes. It now said what leaves and what it may cost, which version answers after "Save as version 3", that a queued lesson waits for Improve agent, Improve agent's caps and that the active version keeps answering, and that the new version took no final test and can be rolled back from. What it still stumbled on, fixed with words: whether a file picked in the sheet leaves (the line now names the reply's steps and "what you add here", and the files sit under "What it should have used", which names them rather than attaching them); "Needs training: No" (now "No, an instruction is enough"); the leak refusal reading as a fault (now "Spark can't read this exchange", in the form's place); a lock for an agent from another computer, read as a permission (now a computer); "training tasks", a fourth name for the tasks ("It can be taught there, where its practice and check tasks are"); "a copy of version 2" against the Train screen's "Improving version 2" (now "Improving from version 2"); and the report's rounds under Time (each figure now stands against its own cap: Spark, Time, Rounds). Left for their own areas again: "Spark not connected" in the status line beside "Send to Spark", which both reads flagged first (050 has since made it "Private from Spark", and the sheet now says "Share with Spark"), and the versions list's Experimental, Ready and imported.

## 051. The comparisons runner holds money and the GPU at each request, and claims only what its records show

**Context.** The owner will be asked to fund the first real run of decision 045's runner: calibration, the regression check, arms 1 to 4, then arm 5. A source review of the runner, in a second opinion on the run plan (GPT 6 Astra), found ways it could spend before it checked anything, pay twice without counting it, let an arm develop after a locked result was released, and report more than its records show. It also proposed three options to fix before any run. All of it is settled here, before any paid call; no model was called to build or test it.
**Decision.**
- *Nothing resumes before the checks.* The engine opens without resuming anything. The runner first checks the plan's pinned inputs and, for a confirmed plan, the request against the plan's arms and settings; then it sets up its guards (below) and the round watcher, and only then resumes what an earlier process left active (`ComparisonEngine.recover`). `plan`, and a request the plan wasn't confirmed with, resume nothing; `probe` and `report` never did. When the command may work on this computer (the plan or the request has local work and `--gpu-minutes` grants a window), it also checks through the GPU lease of decision 046 that the app has none of the GPU (`checkGpu`, a hold the lease refuses at once when it isn't free), before anything is paid, and stops with the lease's busy error if it has; otherwise a run would find out only through the retries of decision 029, minutes later. `probe` checks too; `plan` and a hosted-only run never ask.
- *The test-release barrier.* The plan records when the first locked result was released (`releasedAt`), written just before it. From then on the runner develops nothing: no arm starts, and a run found still developing is paused for good and reported stopped (tests are released only when every arm is frozen or ended, so this finds nothing unless the records were changed by hand). A decision is final: an arm dropped, a locked test held for money (a new decision kind, `held`), or a repeat the credit stopped is never reconsidered by a later run of the same plan. Before this, an arm dropped while other arms held their share of the credit started in a later run once that money was spent, after locked results existed.
- *Pinned inputs.* The plan pins by sha256 the job's `job.json`, `tasks.jsonl`, every file under `data/` and its checker, and the regression job's the same way, or none. A run on changed files, with another regression job, or without the one the plan has, is refused before anything spends, and each arm's own copy of the job is checked against the pin before it is imported. The plan file is format 2; a folder from the earlier runner is refused with a message.
- *The request journal and the student's cap.* Every hosted student request is reserved against `--student-usd` at the most it could cost, then written to `requests.jsonl` and flushed to disk, before it is sent; its reply settles it. The most a request can cost: every byte of its messages and tools as JSON a token (no tokenizer makes more tokens than bytes), 16 more for each message, and every output token it allows, at the listed price, times calibration's billing ratio when that is above 1. A settled request counts at what the provider billed, else at the listed price of the usage it reported. A reply with neither usage nor a charge, a request that failed partway or that its reader abandoned, and one a crash left without a settlement count as spent at their worst; one refused with an HTTP 4xx before any reply counts nothing. What is paid and what is in flight together never pass the cap: a request that could is refused as a runtime failure, so no attempt is scored by it, its run pauses with the reason, and the runner asks again only while the credit has room. The holds of 045 (funding each arm, releasing each test, each repeat) now read what was paid from the journal, in-flight requests included.
- *What a restart guarantees, exactly.* It repeats no recorded attempt, no recorded Spark reply (decision 023) and no training job (decision 035). An attempt in flight when the process stopped is made again, and the requests it had already sent count in the journal at their worst. A Spark call in flight is paid again, and only the second counts against its arm's Spark cap. The sentence that a crash pays for nothing twice is gone from the code, the docs and the output.
- *Unknown costs.* A hosted student with no known price is refused before anything is sent. An unknown cost never counts as zero: in the journal it counts at its worst, a calibration attempt whose cost can't be known stops the plan, and a recorded hosted cost of null stops the holds with the attempt's id.
- *Billing.* OpenRouter includes each call's charge in its usage (`usage.cost`, in every response, per its usage-accounting guide). Every local request, on Ollama or on llama-server with adapters, goes through the window. A repeat with fewer scenarios than the test holds is marked partial, as rows already were. The adapter configurations table is headed "Development only", each cell says whether it ran on dev or on train tasks, and it stays apart from the locked-test tables. Each arm gets a cumulative development cost with what it builds on (the targeted and fixed arms the shared draft; the weights arms the targeted arm and its draft), while the totals count each dollar once. A failure to write one is reported and never stops the run. The comparisons runner drives its arms through the same controller, so every arm keeps its events too. Nothing new about the locked test is written: a locked-test attempt's event never carries its request, and its result is already among the run's records.
**Consequences.** A finished run can be shown again as it happened, at any speed, from its own records and labeled as a replay; nothing about it is made up. The file grows with the run, a few megabytes for a long one.

## 053. A reply the runtime couldn't read is asked for again, twice, before it counts

**Context.** On Oct 28 the 2-bit Glimmer on this computer wrote tool calls that Ollama 0.40.9 couldn't parse ("parse Glimmer call to run: missing ATEM function_calls wrapper"), mostly calls to `run` in the middle of a real task. Ollama answers that with HTTP 500, so it read as an outage: an evaluation stopped and retried the whole batch after 30 seconds, and a chat in the workspace would have failed. The same request with the same seed writes the same call, so retrying it as it stands never helps. A short request with the same tools parsed fine through both Ollama and llama-server.
**Decision.** Ollama's parse error, at the start of a reply or in the middle, is the model's reply that couldn't be read (`bad_response`), not a server fault, so it is never resent unchanged. The agent loop asks for a turn again when its reply couldn't be read and none of it was shown, at most twice, each time with a seed that follows from the turn's own (the seed plus 1,000,003 per retry), so a repeated run asks the same questions. After that the attempt ends with the error and counts against the student, as an unreadable reply always has. The rule is the same for every student and every arm of a comparison.
**Consequences.** A small model's occasional malformed call costs a retry instead of the attempt. A reply that had already started to show stays as it was, and ends on the error.

## 056. The comparison report says what it measured, where, and what each figure is

**Context.** A reviewer read the report of comparison 1 as an outsider and found eight places where it said more than its records show, less than a reader needs, or two things that looked like one contradiction. It named both locked-test seeds when only 101 had results. It listed two sampling configurations joined by "or". It said "Frozen: harness version 2 on ollama" beside every agent while every number came from the hosted student. It put $3.76 beside $3.81 and $0.14 for the same spending. Its dev column set one run of 45 beside two runs of 90. It carried an arrow character in its prose. It printed an adapter protocol when no adapter ran. And it paired the arms with counts but no interval. Comparison 2's plan (`docs/comparisons/returns-desk-2-plan.md`) names the difference in pass rate with a 95% interval for paired proportions as its primary outcome, so that had to exist before it ran.
**Decision.** Wording, and the figures the report works out from stored records. Nothing the runner runs, records, spends or decides changed, no stored record changed, and the report is still made from stored records only (045). Its format is now `architect.comparisons/3`; the app does not read a report in the earlier format.
- *Seeds.* `plan.seedResults` lists each declared seed, then any other a locked test ran under, with the arms that have a stored locked-test result under it. A declared seed with no arm was not run, and the opening and the disclosures say so ("Seed 102 was declared for the decoding repeat and was not run, so no result in this report is under it"). The seeds, the mentoring seed and the training-compute flag the report names come from the confirmed plan, not from the flags of the command that asks for the report, so a report asked for later says what ran.
- *Settings.* Each table has a row of temperature, top_p, top_k, reasoning, turn limit and output tokens a turn for every row of results, as its frozen harness set them, and says that the harness sets them, so each row compares a whole configuration: the harness text with its sampling and limits.
- *Where it was measured.* Each frozen agent is "set to run on `<build>` on `<runtime>` once installed", with the build its freeze pinned (`frozen.localModel`). Its measurements are said to come from the hosted student and the local build to be unmeasured, unless a local table holds a row of that arm (`measuredOn`), in which case the report says that instead.
- *Money.* The student's spending is three counts of the same requests, each named for what it is: the attempts' recorded costs (the arms', the calibration's and the regression check's, each dollar once), what the provider settled, and what the request journal holds as uncertain, counted at its worst. They are not added together. The section shows them to a tenth of a cent, each rounded once from the unrounded value and each difference taken between the rounded figures, so what is shown adds up. The projection is a section of its own, "Projection made before the run, not what was spent", with its columns headed "Projected". The disclosures keep the caveats and no longer repeat the figures.
- *Development.* The arms table shows the first dev measurement (one run) and the last kept round's own before and after, which are on one scale (the keep rule's confirmation over several runs, or one run each for a one-shot draft, which is kept without a check), and beside them the rounds used of the most allowed and why training ended: cap reached, patience, money, time, or done. What each arm spent is a table of its own.
- *Words.* The records keep their words as they are. The report says them in plain text: an arrow is "to", and typographic dashes, quotes and dots are ASCII (`plainStrings` over the whole report).
- *Adapters.* The protocol is printed only when an adapter arm ran. Otherwise one sentence says every reported agent is harness-only, and the adapter column and the "no adapter" after each agent go. 037's statement stays among the disclosures.
- *The difference.* Every pair carries the first arm's pass rate less the second's, with Newcombe's hybrid score interval for paired proportions, his method 10 (Statistics in Medicine 1998; 17: 2635-2650): the Wilson score interval of each pass rate, combined through the phi coefficient of the table of wins, losses, both and neither, with half the scenario count taken off phi's numerator when it is positive. It is made from the four counts. The tests hold it to the 18 intervals of the paper's Table III that method 10 gives, which include tables with no wins or losses and one with only wins (for one lower limit the paper prints 0.8736 under method 10 and 0.8737 under method 8, which is the same interval there; it is 0.87367). With no wins or losses the interval is not a point; with 60 wins and nothing else its lower limit is 91.5 points. An interval that includes zero shows no difference, which is not the same as showing there is none.
**Consequences.** Comparison 1's report was made again from its records with the `report` command and published as `docs/comparisons/returns-desk-1.md`. ## 057. A student's prompt is kept inside its context, and a turn that can't be used is asked again

**Context.** On Oct 28 the returns desk agent ran one read-only request through `architect run` on this computer's Glimmer build (`muse-glimmer:30b-iq2`, Ollama, `num_ctx` 16,384). It made 13 correct tool calls, seven of them reads of 60 to 200 rows of CSV, and the prompt grew to about 15,800 tokens. Ollama's log then showed `stop processing: n_tokens = 16383, truncated = 1` three times: each reply was cut off at the end of the context, partway through a tool call, and Glimmer's parser said "missing ATEM function_calls wrapper". The loop took that for a call the model wrote badly (053), and the run failed with exit 4 after 119 s. Nothing in the loop kept a conversation inside the context. Runs on the hosted student (OpenRouter, a 131K context) never met the limit, so it went unseen. A second gap made it worse: 053 asked a turn again only if none of its text had been shown, and the agent host always streams text, so in the app and the CLI a turn that showed any text before its broken call was never asked again.
**Decision.**
- *The budget.* Every student says what context it runs under (`StudentAdapter.contextLength`): Ollama's `num_ctx`, llama-server's `--ctx-size`, and for a hosted copy the job's own setting, so an agent is developed under the limit it later runs under. A prompt may take the context less the room kept for the reply: what the harness lets a turn write, but at most a quarter of the context. A 16,384 context with the default 4,096 output limit leaves 12,288 tokens for the prompt. The mentor's model acting as the agent (Spark as a reference, and corrections) has a window far beyond any task here, says `null`, and gets no budget.
- *The estimate.* Before each turn the loop sizes the prompt from the usage the adapter reported for the turn before (its prompt and its output), plus what was added since, counted by characters. Before the first turn, or when an adapter reports nothing or less than 40% of what the characters say, everything is counted by characters. When results were cleared since the report, the reported size is scaled down by the share the count says they held. Characters are counted the way Glimmer's tokenizer spends them, because a single ratio is wrong for one kind of text or the other: a digit costs a token, any other ASCII character a third of one, any wider character one, and 10% is added; the chat template adds 16 per message, 40 per call and 320 before the tool list. The constants were fitted to 143 samples (the returns desk's and home services' files as the read tool prints them, search and code output, calls, and text that isn't English), counted with Glimmer's own vocabulary by llama.cpp's `llama-tokenize` against the 2-bit build (vocabulary only: no weights load and the GPU is hidden). A table of ids and dates runs near 1.7 characters a token and prose near 3.8. No sample is counted under its true size; of the 127 over 100 characters the typical one is 34% high, the 90th percentile 49% and the highest 68%. The lowest flat ratio that never undercounts, 1.66 characters a token, is 33%, 112% and 172% high. `packages/engine/test/token-estimate.test.ts` keeps 16 of them with their real counts.
- *What is cleared.* While the estimate is over the budget, the oldest tool results are replaced, in what the model is sent, by a note such as `[Cleared to make room: read data/orders.csv, lines 1-119. Read it again if you need it.]` (the call, the lines the result really showed, and how to ask for it again), one at a time until the prompt fits. Never cleared: the system prompt (the harness's instructions, skills and examples), the person's messages, the model's own messages, the results of the model's latest turn, which it has not read yet, and a result no longer than its note. A cleared result stays cleared for the rest of the run. The trace keeps every message whole and records each clearing in `Trace.cleared` (the turn, the call, the tool and the note); the mentor's compact trace marks the results the student no longer had.
- *When it can't fit.* If the request, the instructions and the latest results don't fit with every older result cleared, the attempt ends before the model is called, with "This task needs more room than the model's context allows." and the figures. It counts against the student like any attempt that ends in an error, so a harness too long for the context shows up in the mentor's diagnosis.
- *A reply cut off at its length limit* is named as that, not as an unreadable call, and its turn is asked again (twice at most, seeds as in 053). The cut-off call's usage shows how big the prompt really was, so the prompt is sized again from it, and the next try keeps the harness's whole output limit free for the reply (at most half the context). A reply cut in the middle of a call by an OpenAI-compatible host now comes back as a cut-off with no call, where it used to be "arguments that aren't JSON". Ollama still reports a call cut off by the end of the context as one it could not parse; with the budget that should not follow from a full context. The replies thrown away were paid for, so their usage, and their charge when the provider billed every one, are added to the turn that follows. After the last try, a reply still cut off ends the attempt with an error that says which limit it hit: the output limit, or the end of the context.
- *Asking again after text was shown.* `runAgent` takes `onRetract(chars)` beside `onText`: when it asks a turn again it says how much of that turn's text it had sent. The agent host's reply goes back to how its text stood before the turn and publishes that at once, so the app's chat shows only the retried turn's text and the saved reply holds only the turns that were kept. The CLI conversation can't un-print: it prints `(asked again)` on a line of its own, then the new text. A JSON result's `answer` is the settled reply's text, which has only the final turns. 053's limits stand: twice, with seeds that follow from the turn's own.
**Consequences.** Comparisons 1 and 2 ran without any of this. Their hosted students ran on a 131K context with nothing holding them to the job's 16,384, so their agents were developed under no limit; their results are not comparable with a run that has the budget, and a later comparison's plan should pin it. In a closed loop on the returns desk's real files (twelve reads of 60 to 200 lines, 16,384 context, real token counts from Glimmer's vocabulary standing in for the runtime's usage), the prompt without a budget went from 1,384 tokens at turn 1 to 40,419 at turn 13; with it, eight results were cleared and no prompt passed 10,728 of the 12,288 tokens. The estimate was 1.48 times the real count at turn 1 and between 1.04 and 1.30 times after it, never below. A 16K context holds about two full reads of a table beside the instructions and the tool list (about 1,100 tokens), so a task that works through a table re-reads more and takes more turns; changing an old message makes the runtime read the prompt again from there, so a turn that clears something is slower (neither measured on the real model). A job that reads a lot is better with 32K, which docs/MODELS.md puts at about 0.2 GiB more on this model (an estimate). Not done: a long chat's earlier messages (up to a quarter of the context, taken before the first turn) are never cleared; the Spark reference and corrections run unbudgeted, so a correction can read more than the student could; the estimate counts a reply's reasoning, which the template does not send back, so it errs high by that much; and a tool result's size (8,000 characters) is not tied to the context.

## 058. A job is drafted from the person's own files, and Architect makes every expected answer

**Context.** Describing a job ended in "Drafting a job with the mentor isn't available in this build". `JobDrafter` had no implementation and the desktop never passed one, so only the sample job and the ready-made agent could be trained or used; the hidden flow spec passed because it stubbed the engine's turns. The design below was reviewed by GPT-6 Astra before it was built. Its rule: the teacher understands the job and configures it, Architect computes every expected answer, and the teacher never writes code that decides a right answer.
**Decision.**
- *The conversation.* `start` reads each attached file in full and keeps its bytes until the job is drafted. A CSV table gives its row count, each column with a profile (numbers or dates or text, how many different values, how many empty, a few example values) and its first five rows; a text or Markdown file gives its text; a `tasks.jsonl` gives only its count and its types. (Decision 061's amendments say exactly which examples, how much text, and everything else the teacher is sent.) Anything else (a spreadsheet, a PDF, a semicolon-separated file, a binary one) is refused with a sentence that says what to attach instead. The teacher replies with one JSON object: a question with two to four options, or a draft. It asks at most three questions, counted by the app; after the third answer, or when the person picks "Draft it now" (which the app adds to every question), it may only draft, and a draft made early lists what the files and answers don't settle in `unresolved`, never inventing a rule. A reply that can't be used (the wrong shape, a question with one option, a draft naming a file that wasn't attached, a kind of task its table can't make) goes back once with the reasons, as decision 023 does, and a second one ends the turn with them. The conversation talks to the teacher the person chose in Settings: the main process passes it to the engine on every call (`jobs.draftStart` and `jobs.draftReply` take it as a third argument in the engine's API, so the renderer's contract is unchanged). It goes through the mentor gate with a hard cap of $1 for a whole conversation and a price that must be known, and the cost of every call is kept with the job. No task is ever sent. The sets are made after the conversation, from the same records, so what the teacher may read of them is held to the rules in decision 061's last amendment.
- *The task catalog.* The teacher picks one to three types, each from three templates Architect owns, and configures it (table, columns, filters, the wording of the request with `{key}`, `{group}`, `{from}` and `{to}` where values go, units):
  - **lookup** asks for one to three columns of the row with a given key, expected as `facts`; rows whose key another row shares, or that lack a value, are left out.
  - **filtered list** asks for the key values of the rows that meet fixed conditions (equals, not equals, empty, filled) while one or two columns take each of their values in turn, expected as an `answer` compared as a set; a list over 20 values is not asked for.
  - **group total** asks for the sum or the count for one value of a grouping column, maybe within a range of dates, expected as an `answer` compared as a number: a tolerance of half the last decimal place for a sum, none for a count or for cents. Ranges of one group never overlap, so no two requests share a row.
  Architect reads the values the same way every time. Wrapping quotes, odd and doubled spaces and case are ignored. Money reads currency signs and codes, brackets and signs, comma or point or space thousands separators and a decimal comma (`1,234` is 1234, `12,5` is 12.5, and a lone point is always a decimal point, so `1.234` is 1.234). Dates read ISO, slashes, points (always day first), month names and a weekday in front, and `03/04/2026` reads as the person said, or as the file shows (a day over 12 settles it), or, when nothing does, month first, said in a note. `N/A`, `null`, a dash and the like count as empty in a column of numbers or dates. Any other cell that can't be read stops the totals that use it with a message naming it, so no total rests on a guess, and a lookup leaves out the rows with a value it can't read, with a note. A configuration that names a column the table lacks, a placeholder that doesn't exist, a value no row has, or whose requests would all have one answer, is rejected with its reasons. Cases are chosen with a seeded generator whose seed follows from the files and the specification, so the same files and answers make the same job. No answer is right for more than three requests of a type (two for an empty list) and no family has more than three, as decision 018 asks of the sample jobs. A family is the row, the first varying value, or a group with one date range.
- *Coverage and the least that can train.* Every type makes as many different requests as its table honestly supports, and the types share about 120 tasks, a type that can give only some leaving the rest to the others. A type with fewer than 6 different requests is set aside after one try to fix it, with a note. The least a job needs to train is 30 tasks: split as the sample jobs are (a third to the final test, a quarter to the check tasks, a twelfth to calibration, the rest to practice), 30 leaves 10 final-test tasks, 8 check tasks and 9 practice tasks. With fewer, the check tasks can't tell the two-task gain the keep rule asks for from luck, and a final test under 8 can't tell a 90% agent from a 70% one. Below that, the conversation ends with no job: it says how many tasks the files support and what to attach (more rows, or a `tasks.jsonl`), and puts the description back to edit with more files. When the files hold no table, or fewer rows than 30 in all, that is certain at once and the teacher isn't asked at all.
- *A tasks file bypasses all of this.* One `tasks.jsonl` in Architect's format is parsed with the task schema and used as the tasks. Tasks that expect an end state need a checker file and are refused. The teacher is told only its count and each type's count; it names and describes the types.
- *Finalization is the engine's.* The teacher supplies the meaning: name, summary, description, what the agent does and doesn't do, each file's description and access, the task types, the business date and a target pass rate. Application code supplies the rest: the id, the data copied byte for byte from what was read, the budget and evaluation defaults of the sample jobs, a blank starting harness, and the teacher and agent's model the sample jobs ship with (`shippedModels`). Putting the person's own models on a new job is the main process's, once for every new job, and isn't done here. `JobLibrary.create` splits the tasks first (a job that can't be split writes nothing; tasks that can't be divided lose their last ones, from the largest type, until they can), writes the data, the job and `drafting.json`, seals the final test in the vault and records the job, so that Clarify's `jobs.save` and Start training work as for an imported one. Files are read-only for training tasks; a file the teacher marks writable stays so for the workspace.
- *What the person and the teacher may see.* The review examples on Define come from the practice tasks first and the calibration tasks next, never the check tasks or the final test or their families (a family never crosses a set); the final test is only counted, by type, by the vault. `jobs.taskPlan` gives the Example tasks tab where the tasks came from, the rule behind each type ("Total of amount for each region, within a range of dates in order_date, from orders.csv", worked out by Architect, never by the teacher), three examples with their expected answers and the counts in each set, with what the teacher left open and what Architect assumed or left out.
- *Saying what it is.* `drafting.json` records the source, the seed, each type's specification and rule, what the teacher left open, Architect's notes and what drafting cost. The report card carries `tasks: { source, draftingUsd }`, so the job's report (`report.md`) and the Results page's Details say that the final test's requests were generated by Architect from the person's files following a job description the teacher drafted, that the answers are checked against it and are not independently certified as correct for the business, and what drafting cost, before training. Define says the same under Example tasks.
- *Not in this version.* Tasks that write to files, solvers written by the teacher, regenerating one type, and files other than CSV, text and Markdown.
**Consequences.** A person with a table of records can describe a job and train an agent on tasks made from it, and the final test is as honest as the specification: what it can't say is whether the business would call the answers right. The three templates decide what a drafted job can be about; a job that needs rules from a text file (a refund policy, say) can have only the lookups its tables support. A draft is recorded when it is made, so a conversation abandoned after its draft leaves an unused job, with its data and its sealed test, in the library; nothing removes it yet. The teacher's reply format has been checked only against a scripted teacher, not a live model, and the first real session will show how often a reply needs its one fix. The sample job still takes its models from its job file, not from Settings; that change is the main process's, made elsewhere. Not done: `.xlsx` and other formats, mixed units or percentages in a column, delimiters other than a comma, and a second round of questions about the tasks Architect made.

## 059. New jobs start from what the person set up, a run says what it needs, and the final test can run online

**Context.** An audit of the real app on Oct 28, which traced every call a screen makes to the engine, found six places where a screen promised what the app didn't do. The teacher and model picked in setup or Settings only wrote `defaultMentor` and `defaultStudent`, and nothing applied them to a job: the sample job asked for Spark and the 4-bit model whatever the setup had steered the person to, had no hosted copy, and "Train online" said "Choose a host". A run could start with no teacher key and no model, and fail long after it began. The engine could take the final test on the online copy (`lockedTestOn: 'hosted'`) and test an agent on this computer later (`runs.retest`), and no screen offered either. `jobs.importFile` was wired and nothing called it, though 010 promises it. Three settings did nothing: the checker file stored a path the engine can't load, the task sets could be edited after the tasks were split though nothing splits them again, and "Opening files outside the job" is enforced nowhere. And the Privacy tab said the teacher never sees a chat, which Teach this contradicts.
**Decision.**
- *New jobs.* One function in the main process, `applyChoices` (`apps/desktop/src/main/jobs/choices.ts`), puts the person's choices into a job that has just been made: the teacher (`defaultMentor`), the model on this computer with its build, runtime and address (`defaultStudent`), a hosted copy of Glimmer when a host that serves one has a saved key (OpenRouter first, since setup offers it, else Together or DeepInfra), and training online when there is a copy to train on. The job's own context size stays, since the agent is developed under the limit it later runs under (057). A model that isn't one of Glimmer's builds gets no hosted copy, which would be a copy of Glimmer's weights, and is named by its own id. A job file's own hosted copy is dropped: where a person's tasks and files are sent is theirs to choose. Main's handlers make the one call: for the sample job when it is new (it was not in the job list before the call; asking again opens it as it is), for an imported job file, and for a drafted job (058) when its draft arrives in either reply. The engine has already made a drafted job from the shipped models, so the handler saves it again with the person's choices, and does nothing when it already has them. A job that exists keeps what it has. "The setup's faster-training choice" is a host with a saved key, which is all setup's last step records; a key saved only for the teacher counts too, and Define shows the plan's cost and the choice before anything starts.
- *What a run needs.* Before Start training, Define reads what it can without a model: the teacher's key is saved (`secrets.status`), the model is on this computer when practice or the final test runs there (`connections.detectLocal`, at the address the job names), and the online copy has a host and a saved key when anything runs on it (`hostedAvailability`). What is missing is listed under "Before it can start", each with the one button that fixes it: add the provider's key in the dialog Settings uses, download the model, look again when Ollama isn't running, choose a host. Start waits, and the footer names the first thing missing. The online copy is asked live (`connections.testStudent`, which lists the host's models and loads nothing) when a run is about to start, so a copy that doesn't answer stops it there with the reason and a Try again, instead of failing hours into training.
- *Where the final test runs.* Advanced settings, under Ready when, offers it on this computer (the default: the agent is marked ready when it passes) or on the online copy (faster: the agent is marked as tested online and can be tested on this computer later), each with its time and cost. The choice belongs to the run, not the job. Start training sends `lockedTestOn` with it, the same to the comparison's baselines so the four runs compare like for like, and `interactive: true` so Spark may stop to ask one question (the Train screen's answer box is another branch's). The plan's time and bills follow the choice, the online test as a line of its own.
- *An agent tested online.* The Results page badges it "Passed online" and says it finished training, never "Ready" or "graduated", until a final test on this computer met the targets; a miss there says so, whatever it scored online. The offer to take that test, "Test on this computer" (`runs.retest`), sits right under the badge, before the figures, with how long it takes (2.5 minutes a task, so about 2.5 hours for 60 tasks and an hour for 30) and that it uses the graphics card; it shows how far the test has got, why it stopped and how to go on, and its result when it is done. The agent's own Results tab has the same offer. `runs.get` now lists a run's re-tests with where each stands (additive), so a page opened mid-test knows. An agent whose records aren't on this computer isn't offered the test. The agent's version stays as it was made, since versions are immutable (039): its package still says tested online, and the local result is the run's.
- *Job files.* "Import a job file" sits beside the sample job and the ready-made agent on the new-agent screen and imports through the system's open dialog. A file that isn't JSON, or isn't a job, fails with the code `not_a_job` and says what a job folder holds (job.json, tasks.jsonl and a data folder); a line of tasks.jsonl that isn't a task is named by its number. "Export the job file" in Advanced settings writes the job's settings through a new save dialog (`files.save`; the file chosen is the one file that may then be written). The file holds no tasks, so the test split never leaves the vault, and it imports again beside its tasks and data.
- *Settings that did nothing.* A checker file chosen by its full path is copied into the job's folder when the job saves (the engine's `keepChecker`), under a name that follows what is in it, and the job points at the copy. Main allows only a file the person picked, and the editor takes the copy's name on from then on. A name that follows the content means a changed file is a new file, so a run graded with the old one still finds it. The task sets show what they are, read-only, with one line saying they were split when the tasks were added; a job with no tasks yet isn't held to them. "Opening files outside the job" is gone from Define and from the agent's settings: the agent's file tools reach only the files its job declares, so there was nothing to choose. The field stays in the job and its contract, where the package format carries it.
- *Privacy.* The tab says the teacher sees practice attempts and samples of the files while it trains, never the final test, and never a chat except the one exchange Teach this sends after the person confirms, with its steps and their notes.
- *Tests.* Unit tests for `applyChoices` and the handlers that call it (a new sample job, an imported file and a drafted job in either reply get the choices; a job that exists, or already has them, is left as it is), the pre-flight's rules, the estimates with the final test online, the verdict for an agent tested online, a re-test's phases, the engine's import errors and checker copy, the main process's check of a checker path, and the job file's name; hidden e2e for the pre-flight and each fix it offers, the final-test choice, the re-test from Results and from the agent's settings, and, on the real engine, an import, a file that isn't a job, an export that imports again, a checker copied into a job, and a described job that arrives with the teacher and model the person set up and trains on them. Each new rule was checked by taking its code out.
**Consequences.** A new job agrees with setup from its first screen, whether it is the sample job, a job file or one drafted from the person's files, and a run that can't start says why before it does. An export is only the job's settings; to give a job to someone else, hand over its folder. The online final test is chosen on each visit to Define and isn't saved with the job. An agent tested online and then here shows "Ready" on the Results page while its version's own record still says tested online. A drafted job is saved twice, once as the engine makes it and once with the person's choices, so for an instant between them it holds the shipped models; nothing runs in that time. Not done: the pre-flight can tell only about Ollama at the address it looked at, and reads the model when the screen opens or the person asks again, not at the moment Start is pressed; and a hosted copy of a model other than Glimmer.

## 060. A person can always get back to a run, a paused run says why, and Spark's questions have a place

**Context.** An audit of the real app, not the e2e fixtures, found seven ways to lose a run or leave someone guessing. The sidebar listed only runs in training and the results page was reachable only from the training screen, so a run that ended while the person was elsewhere left no way back, and a failed or stopped run couldn't be opened again. The agents list was read again only on a restart. With comparison mode on, the baselines start after the agent's own run and a job's summary took its newest run, so the sidebar opened a queued baseline. The training screen showed `run.error` only for a failed run, and the live line about a pause was gone once the screen was opened again, so Resume was a blind retry. A run started from the app can pause on one question from Spark (decision 042), and the training screen had no place for it. Quiet mode's thread cap reached an agent only as it opened. The runtime meter (decision 045) was wired only in the comparisons runner.
**Decision.**
- *A job's newest run is its agent's own.* `JobSummary.latestRun` is the job's newest run that isn't a baseline (`isBaselineMethod`: any method but `architect`, so an improvement still counts). It carries `improves` for an improvement and `accepted`, whether the version that run made is accepted, which is absent when the run made no version or its agent has since been removed.
- *Rows in the sidebar.* One row for each job whose newest run has something to open (`shell/training-rows.ts`): Training (queued, running, stopping or testing), Paused, Needs you (paused with the new phase `clarifying`), Results ready (finished, made an agent that isn't accepted yet, not an improvement; opens the Results page), and Stopped and Error (open the run, which says what happened). A finished run whose agent is accepted has no row, since its agent is in the list, and neither has a finished improvement, whose new version is under the agent's Teaching. A stopped or failed run keeps its row until the job's next run takes its place; nothing dismisses it.
- *The lists follow the engine, from one place.* `useEngineUpdates`, mounted by the App so it works on the training and results screens that have no sidebar, reads the jobs again when a run changes status or starts waiting for an answer (not on every attempt), and the agents and jobs when a graduate becomes ready. The sidebar still reads the jobs when it appears, and accepting an agent on the results screen reads both, so its row stops saying Results ready. An agent made while the person is on any screen is in the list by the time they leave it.
- *A run says it waits for an answer.* The engine sets the run's phase to `clarifying`, which the run schema already named for this, when it takes a question, and announces the intervention as changed once the answer is taken up (`mentoring.updated`), so a screen that shows the question reads the answer back. The phase text reads "Spark has a question for you", and Resume waits, since going on without the answer would only ask again.
- *A paused run says why, and what puts it right.* A run paused with an error (a pause nobody asked for) shows a notice on the training screen whenever it is opened. The run records only the engine's sentence for why it paused, no code, and decisions 050 and 055 keep screens from reading sentences for meaning, so the notice looks at the computer now (`flow/train/pause.ts`): the teacher's key while the run teaches, the online student's key while a hosted run practices, and for a student on this computer, the final test included, whether Ollama runs and whether the model is downloaded. A fact not read yet claims nothing. Each cause has its action: Add the key (opens Settings, Models), Check again (reads the local runtimes again) and Download (the control Settings has). The engine's own sentence waits under Details when a cause was found, and leads, with Press Resume to try again, when nothing on this computer explains the pause. The live line the round's panel showed for the same pause is dropped, since the notice says it.
- *Spark's question, in the round.* The current round's panel shows the question with a box for the answer (up to the 4000 characters the route takes) and the one choice the route offers, "This changes what counts as success". Choosing it says, before anything is sent, that the run stops, since its final test belongs to the job as it was, and the button then reads "Send answer and stop this run". The answer goes through the existing `mentoring.answer` route, and a failure shows as a toast with the text kept. Once the engine has taken it up, the round says "You answered: ..." and what Spark did with it: kept it as what the person meant and shows it with every round from here on (the mentor's view lists the answers, decision 042), or the run stopped for a new job. In the list of rounds a question reads Needs you and then Answered, with the question or the answer under its title. Its own page names it and leaves out the measurement, the files and the gates, which a question that tries no change doesn't have. A run that ended with its question still open (stopped, say) offers no box, since the engine could no longer take the answer: the round says what was asked and that training ended before it was answered, and the list says Not answered. It is not a dialog.
- *Quiet mode follows Settings.* A student takes its thread cap and its rest as a setting to follow (`Following<T>`: a value, or a function asked at every request). The workspace host reads the cap it last received with `configure`, the message that already carries the llama-server's settings, at each request, so the app no longer sends the cap as an agent opens (the command still opens an agent with its own). A llama-server agent already followed it, since the cap is part of the server's launch and a changed launch restarts an idle server at the next request. A run's student follows the cap and the rest the same way (`followedQuietSettings`), where it was made with the values of the moment. Rests are still for a student in a run only, as the commit that built them says: after a reply in a chat, a rest would keep the reply open, and the next message waiting, for up to three quarters of that last turn's time. If rests should apply to chats, they belong in front of the next turn, not after the last.
- *The runtime meter stays out of the app.* Wiring it would put an instrument that has never run against a real runtime ("unverified live" in 045, and this pass may run no model and no GPU) into every local final test. Its cold start unloads the person's models, holds the GPU lease alone and times a first reply, a load and a reply nobody asked for. Its GPU figure is the whole card's memory in use, so on a computer that is also running a browser or a game the Results page would give that as the agent's. And its unload names Ollama's preset models, not the job's own, because `RuntimeMeter.start` isn't told the endpoint. What it would take: per-process GPU memory or a figure labelled as the whole card, the job's endpoint in `start`, a go-ahead for the unload, and one supervised run on a real card.
- *Tests.* Engine `job-summaries.test.ts` (a baseline newer than the agent's run is skipped, a job with only baselines has none, accepted and removed agents, an improvement) and `mentoring-api.test.ts` (the phase while waiting, in the job's list, and the announcement after the answer; each was checked to fail with its change taken out). Desktop unit tests `training-rows`, `updates`, `pause` and `questions`, and the phase text. Adapters: a thread cap and a rest that change while a student is open, for Ollama and llama.cpp. Engine `agent-host.test.ts` (an agent already open follows the cap at each reply; one opened with its own keeps it) and `quiet-settings.test.ts`. Hidden e2e `runs.spec.ts` on a stand-in engine (every row and where it opens, a row going once the agent is taken, an agent appearing while the person is on the training screen, the paused notice for a missing key, a pause nothing explains, Ollama not running, a missing model, the question and its answer, an answer that stops the run, an answer that can't be sent), `runs-engine.spec.ts` on the real engine (the recorded run's results row and its removal after accepting, and an agent appearing the moment a run ends with no restart or reload; both agent-appears tests fail with `useEngineUpdates` taken out), and `agent-host.spec.ts` (switching quiet mode in Settings reaches an open agent's next reply). Captures `runs-sidebar`, `train-paused`, `train-question`, `train-answered` and `train-question-round`, in both themes.

**Consequences.** A run can be found again from the sidebar while it is its job's newest, and an agent is listed when its run ends, not after a restart. A run paused before this change while waiting on a question reads Paused in the sidebar, since its phase wasn't `clarifying`, though its training screen shows the question. A paused run's notice says what the computer lacks now, so it can leave out a cause it can't see (a key that is saved but refused, which only the engine's sentence under Details says). Not done: a way to dismiss a stopped or failed row, a notification when a run ends while the app is in the background, rests in chats, and the meter.

## 061. A drafted job can have a rule, and the person confirms it before anything trains

**Context.** The first real drafted job (a bike repair shop, Oct 29: one Spark call from one sentence and three files) came out as contact lookups, a customer's open tickets and a mechanic's hours. Glimmer already does those, so it met the target on the check tasks before any round and nothing was taught. The shop's policy (labor at $65 an hour in half-hour steps, members 10% off labor and never off parts) was in the files and made no task: the three templates of decision 058 can't apply a policy. The same draft showed what a reviewer meets first. Spark wrote the open tickets as "status is not Picked up", which also keeps tickets with a blank or an unfamiliar status. The policy file was cut at 4,000 characters before Spark read it. The Describe screen said nothing of what drafting needs. And the examples on Define were the first three requests of a type. GPT-6 Astra reviewed the plan below, and this follows its advice: one bounded numeric template, a confirmation that binds, the holdout kept, the trust claim made conditional, and no promise that a rule makes teaching pay (calibration says whether the student needs it).
**Decision.**
- *A rule is a typed expression.* The teacher configures one numeric answer per row of a table as a JSON tree (`packages/shared/src/rules.ts`, `packages/engine/src/drafting/rule`): decimal literals, columns of the row or of one looked-up row, plus, minus, times, division by a nonzero literal, smallest and largest, rounding to a stated step in a stated mode (`up` to the larger multiple, `down` to the smaller, `half_up` to the nearest with a tie going up, and the same words below zero), and `if` over a category test (equals, or in a stated set) or a threshold (more than, at least, less than, at most). At most 32 parts, 6 operations nested (a column or a number isn't one), 2 conditions, 4 operands to a sum or a product, and one lookup into another table by a key that is unique there. The last step is a rounding, so every answer is written one way. There is no "not", no loop, function, chained lookup, aggregation or date arithmetic. The reply format carries the expression as a list of steps that name one another by id, the way a calculation is worked on paper ("hours", "labor is hours times 65", "total is labor plus parts, rounded"), and the id of the last. A step is an `op` and the few fields it uses, the rest empty, and one step may be used in two places. A list has no `$ref` and nests no deeper than the rest of the reply, so providers that limit how deep a schema nests take it, where a tree unrolled to the rule's own depth would not. Architect expands the steps into the typed tree, counting a step each time it is used, or sends back what is wrong with which step by its id: one that doesn't exist, two with one id, steps that use each other in a circle, the wrong number of steps inside one, a number that isn't one, a step nothing uses (decision 023's one fix).
- *Exact, and never zero unless the person said so.* Arithmetic is on fractions of integers until a rounding step. Cells are read with 058's rules. An empty, N/A or unreadable input leaves its row out and is counted with its reason, and is never read as zero, except an empty cell of a column the person answered a question about with "Count it as zero" (the amendment below). An answer is graded as a number, so a rule whose answers need more than thirteen significant digits is refused: at fifteen a wrong answer one step off would be the same number as the right one. So do a category the rule doesn't list, a row with no match in the lookup table, a key that table lists twice (a lookup table where over a fifth of the rows share a key is refused as no key), an answer below zero and one above a billion. The rule declares the currency of its amounts: a cell in another currency leaves its row out, and a column that mixes currencies, or has signs where the rule names none, refuses the rule. The answer is compared as a number within half the last rounding step, at most half a cent, so one cent off fails.
- *Architect writes the words.* The statement ("Start with (labor hours rounded up to a multiple of 0.5) times 65 times 0.9 when member (customers.csv) is yes. Add parts cost. The result is rounded to the nearest cent, halves going up.") and the working of each example (each step with the number it came to, and the values read from the records) come from the expression alone. The teacher's words are in the request and in the passages it quotes.
- *The passages and the holdout.* A rule quotes the passages it rests on. Architect finds each word for word in an attached text file or in what the person typed or answered (`description`, `answers`), and sends back one that isn't there. The rule is written from the policy and the person's answers, never from the rows. The examples are chosen from the practice and starting tasks of the job's own split, never the check tasks or the final test: three or more that between them take every side of every condition and a rounding edge. Where no record needs rounding (the shop's hours are all half hours already), Architect makes up numbers for it, works them through the same code, and says they are made up. Cases of one entity are one family: the case's own key, or the column the teacher names as the entity (a customer), so reusing it can't cross sets.
- *Guards.* A rule is refused, and the reason goes back to the teacher, when every case comes to the same answer, the answer is the key (as a number), the answer is the value of a column in 90% of rows, a side of a condition never changes any answer (no row takes it, or both sides give the same number), or an operand of a smallest or a largest never decides one. An answer already written in a column in a quarter of the rows is allowed and said, and so is a rounding that never changes a value in the records.
- *What the policy leaves open.* The teacher lists in the rule what the policy leaves open and whether it changes a number. One that does is never decided for the person: Architect puts it to them as a question with two to four answers, and no "Draft it now" (typed, it asks the question again and the teacher isn't called). A draft made under "Draft it now" is asked about too. The answer is kept with the job and the teacher drafts again with it, quoting it as `answers` if the rule rests on it. After three the conversation ends and says what is still open. One that changes no number is listed as left open.
- *Confirmation that binds.* A job with a rule doesn't train until the person confirms it on Define over these records. `confirmation.json`, beside the job, holds each rule's version (a hash of the rule and of how Architect reads and rounds) and the hash of every data file. The task plan carries a token of both, and confirming sends it back, so a rule or a file that changed since the person looked is refused (`rule_changed`). The draft records the hash of each file its tasks were made from. A file that isn't the one the tasks were made from or the one confirmed, or a rule that isn't the one confirmed, makes the state `changed`: confirming again can't bring back tasks and a final test made from other records, so the person is sent to describe the job again, which makes a new job whose rule nobody has confirmed. The engine refuses every kind of run on an unconfirmed rule (`rule_unconfirmed`), the baselines and an improvement included, not only the button. Headless, `--confirm-rules` is the person's say-so, after `scripts/draft.ts` has printed the rule and its examples.
- *Saying what it is.* Beside the Results score, and right after the score in the report: "Expected answers were calculated by Architect using Spark's interpretation of your policy, which you confirmed. This score measures agreement with that rule on held-out cases; it does not independently establish that the rule matches your business policy." Under Details and in the report, for each rule: its words, its version, the exact expression, when it was confirmed, the passages, how numbers and rounding are read, the rows left out and why, what each side of a condition did, and whether teaching ran. The report card carries them (`tasks.rules`).
- *The fixes a reviewer meets first.* (1) A list keeps rows by a stated set (`in`), never by what a row is not: a reply with "is not" is sent back with the reason, a set naming a value the column lacks is refused, and the notes say what else the column holds and how many rows that leaves out. ## 062. Every run needs its model on this computer, and a screen reads again what it left

**Context.** An independent review (GPT-6 Astra) of the app after decisions 059 and 060 found four places where a screen told the person less than was true. Define left the model on this computer out of what a run needs when practice and the final test both ran online, but the engine asks the local runtime which build the agent runs on when it freezes the graduate, so a person without Ollama or the model paid for the training and the host's bill and met the pause only then. The training screen kept the records of an earlier visit and never read them again, so a question Spark asked while the person was on another screen showed as a placeholder that no read was filling. Results did the same with a run's detail: a test on this computer that ended or stopped while the person was elsewhere still said it was testing, with no verdict and no Try again. And a final test taken online that paused was diagnosed as if it ran on this computer, so a missing online key went unnamed and the person was told to start Ollama.
**Decision.**
- *The model on this computer is needed for every run.* The finished agent runs on this computer whatever trained and tested it, and training ends by recording which build of the model that is, its name, digest and size, which the agent's package carries and a later test on this computer holds the local model to. So the run's needs (059) no longer skip the model when practice and the final test both run online; the row says why: "The finished agent runs on it, so it has to be here when training ends." The rows for a run that practices or tests here keep naming what runs on it. The other way out was to let freezing put off the pin with a note. That files an agent with a model nobody looked at, a package whose base has no digest for the install checks to compare, and nothing for a later test here to hold the model to; and the person can't use the agent without that model anyway. It is also the larger change, with new state in the agent's record. The needs can still tell only about Ollama at the address they looked at (059), so a runtime they can't see is found out at freezing, where the run pauses with the engine's sentence. `test-targets.test.ts` holds that behavior in place: a run wholly online pauses at freezing without the local model, with no final-test attempt made, and finishes once it is there. The comparisons runner already asks the same thing before it spends (`preflight` in `comparisons/runner.ts`), for the same reason.
- *A run says where its final test runs, and one rule says which student works now.* `runs.get` carries `lockedTestOn` (this computer when absent), the training screen's view of a run keeps it, and `activeTarget` answers for the current phase: where the job trains while the run practices, where the run takes its final test once it is testing, whatever practice used. The paused notice (060) looks at that endpoint. An online final test names the online copy's key and says nothing of Ollama; a final test here names Ollama and the model and says nothing of the online key; the teacher's key is still looked at only while the run teaches. The first step of the testing phase, freezing, still asks this computer's runtime whichever way the final test goes, which the notice for an online final test doesn't diagnose; the engine's sentence says it.
- *A screen that opens reads again what it shows.* A run's detail (Results, the agent's Results tab, Improvement) and a run's mentoring records (Train) are read each time a screen using them opens, and the last visit's copy shows until that read lands (`refreshOnMount` on `useQuery`). The engine speaks only to screens that are open, so what changed while the person was elsewhere is otherwise never heard. Other keys are read once, as before. Between the two there can be a moment of the old state before the new one, such as "Testing" for a test that has ended.
- *A read asked for during a read is made after it.* `fetchQuery` answered an ask for a key that was already being read with that same read, which may have started before whatever made the ask necessary, so an event heard just after a screen opened could be lost and the old answer kept. An ask during a read now waits for one more read that starts after it, any number of asks share that one, the older read's answer is dropped rather than shown as the current one, and whoever asked waits for the newest.
- *A question that isn't in the records is fetched, not waited for.* A round that waits for its answer whose question is missing from the records read so far has them read again, once for each round (`useQuestion`), and the screen waits for that read. If the question is still not there it says so with Try again, in place of a placeholder that waits for a read that isn't coming.
- *Tests.* Unit: `needs` (a run wholly online still needs the model, says Ollama isn't running first, needs nothing once the model is there), `pause` (an online final test names the online key and not Ollama, in either case of practice; a final test here the reverse; the phases before the final test ignore where it will run), `run-state` (`lockedTestOn` carried, `activeTarget` in each phase and when a run moves into its test), `questions` (a missing question, a waiting view, the error once the records were read again), `query` (a read asked for during a read, shared asks, a dropped answer, the newest read's failure or success) and the engine's `test-targets` and `host`. ## 063. What the teacher may change is the person's choice, for each job

**Context.** Each round the mentor picks one intervention from a bounded menu of five: a procedure, retrieval, a helper, weights and a question for the person (042). The engine decided the menu alone: harness changes always, weights when a trainer, a backend and a budget exist, a question when someone is there to answer, and a comparison could fix it (045). A person couldn't say "never write tools for this agent" or "don't stop to ask me, I'm walking away". This adds that choice for each job, and it narrows what the mentor may do and nothing else: the checker, the splits, the weights and the tool permissions stay out of its reach, and the locked test is still never shown to it.
**Decision.**
- *The contract.* `Job.interventions` is optional: the kinds of change the mentor may use. Absent means all five, so every job file, package and saved job reads as before. A list must keep at least one kind that changes the agent (procedure, retrieval, helper or weights), since a mentor that may only ask teaches nothing, names each kind once, and is refused with a sentence a person can read otherwise (`AllowedInterventionsSchema`). A job that allows all five stores no list, so a job nobody changed is left as it was (`storedInterventions`). The types moved to `packages/shared/src/interventions.ts`: `job.ts` holds the choice and `mentor.ts` already imports from `job.ts`, so keeping them in `mentor.ts` would have been an import cycle. Every package still takes them from `@architect/shared`. The plain names a person reads for the five (Instructions and steps, What it reads when, Small tools, Its weights, Questions for you) are there too, so the screen and the engine's sentences say them one way.
- *Where it travels, decided for each place a job crosses a boundary.* Job files travel with it, since it is a setting of the job like the budget and the mentor: `JobSchema` is what a job file is read with (`readJobFile`, `JobLibrary.save`, `get` and `forRun`) and what every job route over IPC is parsed with, so Export the job file writes it, Import reads it, a file from before has none, and a file with a bad list is refused with `not_a_job` naming the field. `applyChoices` spreads the job, so the person's own models go on a new job without touching it. A run reads its own copy of the job from its start, so a change applies to the next run and never to one under way. Contracts and packages don't carry it: a contract is what the agent promises, and its own comment says training settings aren't part of it; `contractTerms` ignores the choice, so changing it makes no new contract version, and the manifest's `.strict()` schemas refuse it (both are tested). It couldn't be used there anyway: an agent installed from a package has no job on that computer to teach it with. A comparison's arms are made from a base job and keep the choice, and the comparison's fixed menu narrows it further; what the person turned off keeps the person's reason.
- *The menu.* `menuOf` refuses each kind the job turned off with "Turned off for this job in the teacher's settings.", ahead of every other reason (a person's choice holds whatever else is set up, so it is the one given, and the backend isn't asked about weights they turned off). The mentor is told which are off and why, its reply format offers only the rest, and `interventionRefusal` rejects a plan outside them, which is the existing path: confirmed by a test for each of the five. The simpler methods of a comparison are held to it too.
- *What a label can't cover.* The kind a change is called is the mentor's word, and a procedure that writes `tools/sum.js` would have slipped a tool past a person who said none. So a change set is held to the choice by the files it writes or deletes (`interventionsForFile`): a tool belongs to small tools, `retrieval.yaml` and `examples/` to what it reads when, `AGENTS.md` to instructions and steps, and a skill to either of those two. Decoding and guardrails belong to no kind and stay open whenever the mentor may change the harness at all. Worked examples are loaded by a retrieval rule the runner adds, so a plan that asks for them is refused when retrieval is off. The sample job and every drafted job start from a blank harness, whose first round is a whole draft that no menu is asked about, so the first draft is told what is off (its list of what to write loses those parts, and a sentence says which files not to write) and goes back with the reason, once, like any change set the runner can't take. A job that allows no harness change has no draft to write, so its rounds start from the starting harness and a weights round is not kept waiting for one.
- *Nothing it can do.* A mentor that may only ask, or whose every other kind is off or can't run here (weights with no trainer, no backend or no budget left), has nothing to try, and its rounds would each cost a mentor call and be refused. The run says so before it spends: `nothingToTry` is asked before the baseline, which is the student on every check task, and before each round, and ends the run with the new stop reason `nothing_to_try` and a sentence that names what is off and what can't run, kept on the run (`error`, as the stop for an unconfirmed rule keeps its). No round is started, no mentor is asked and no attempt is made. With nothing kept, the run ends stopped with no graduate to test, which is how a stop before any change ends; an improvement ends in its own step, which hands the lessons back and gives the sentence as the reason nothing can be promoted; a run that had kept something goes on to its final test, as it does for a spent budget. A comparison's own rounds (an adopted harness, a one-shot adapter) are the runner's plan and aren't asked.
- *Teach this.* When the job turned weights off, an improvement trains none (`trainingApplies`). When it turned questions off, the classification of a correction is not offered the kind that asks one, its instructions say why, and a reply that calls the request unclear anyway is kept as a correction that can't be checked, with no question for the person. A lesson the person applies as an instruction is their own act and isn't held to the choice.
- *The Teacher tab.* Advanced settings, Teacher, has a section, "What Spark may change", with an icon, a name, one short line and a switch for each of the five, the icons the evidence screens already use for them. The last switch that changes the agent is held on and says so on its row, in the line that would have explained it. Weights say on their own row what the app already knows keeps them from being trained here, in the engine's order: the final test runs online, no Hugging Face token comes from anywhere, the job has no training budget. The app can't see the rest, and the engine checks again when a round begins. A switch saves through the job editor like the other tabs, and `validate.ts` marks a list from elsewhere that the engine would refuse, in the Teacher tab.

Nothing is claimed while the token is still being read.

Nothing changed.` Without it, the page would have said of a refused set of weights what it says of a computer that can't train. A run that ended for want of anything to try says so on the Train screen, with the engine's sentence and a way back to the job, and its panels no longer wait for a first round.
- *Tests.* Shared: an old job file parses, any list that keeps a way to change the agent parses and any other is refused with its sentence, the order and the stored form, the choice leaves a contract and its package alone, and every file of the harness surface is placed. ## 066. Teach this keeps a change only when the student learned it and held its check tasks

**Context.** Teach this (042, 048) could end without any sign that the agent learned what the person taught it. Four things stood in the way. The planner ended a run before its first round once dev met the job's target, so Improve agent on an agent already at its target made no rounds and no version (048, Consequences). An improvement round was kept by the ordinary rule, a net dev gain of `minDevGain`, which an agent near its ceiling can't give, so a useful correction there could never be kept. When any change was kept, every lesson the improvement held was marked used, even one nothing showed the agent learned. And "Save as version N" made a candidate with the lesson's instruction added that nothing measured before Promote. The mentor's verified continuation (`teaching/correction.ts`) shows the mentor can do the task, not that the student learned it.

**Decision.**
- *An improvement gets its round.* A run that improves an agent does not end on `target_met` before it has run one round; ordinary training keeps its rule (`plan.ts`).
- *An improvement's keep rule* (`decideLearned` in `keep.ts`; ordinary training keeps `decideKeep`). After the round's change is measured once on dev, the student attempts again, with the change, the round's train tasks of its lessons' task types that it failed at the start of the round: the same batch the mentor diagnosed and drew its worked examples from, so nothing new is generated. The change is kept when the student passes every one of them and `isHarmful` finds no harm on dev (the total doesn't fall and no type loses more than the job's per-type limit), and the hard gates pass. No gain is asked for, so there is no lucky draw to measure again. The reason line says both halves, for example "Learned: passed 2 of 2 tasks it had failed; check tasks held 3/9 → 6/9"; one that failed says "Not learned: …", and a round with no such task says "Not verified: …". The attempts are ordinary train attempts under the candidate's version or adapter, and the experiment records them as `learned`. A weights round in an improvement uses the same rule.
- *Attribution.* A lesson is learned when a round whose change was kept checked tasks of its type; it is marked used in the candidate. A lesson checked only in rounds that weren't kept is not learned; one whose type no round could check, or that names no type, is not verified and never counts as learned. Both go back to the queue with a short note of why, which the flagged answer shows under "Last try" (`lessonOutcomes` in `improvement.ts`; `Correction.note`).
- *One path for teaching.* "Save as version N" is gone, with the engine's `apply`, its route, client call, IPC channel and tests: a rule or a missing fact is saved for Improve like any lesson, and only an improvement that showed the agent learned it makes a version. Removing it was simpler than making Promote refuse an unmeasured candidate: that would have left a button that makes versions nobody may use, and a second kind of candidate to explain. The status `applied` stays in the schema only so lessons applied before this still read.
- *The report* (`/runs/:id/improvement`) says whether the change was kept in its first line, keeps the check-task score before and after for each task type, and gives each lesson Learned, Not learned or Not verified with the line that says why. The Improve dialog now says it saves a version "only if it learns a lesson and does no worse on the check tasks".
- *Tests.* Engine `plan.test.ts` (an improvement at its target gets one round), `keep.test.ts` (`decideLearned`: kept at the ceiling with no gain, not kept when a task still fails whatever dev gained, not verified with nothing to check, refused when `isHarmful` says so), `teach-this.test.ts` (a kept improvement records the student's checks and marks its lesson learned; a change that gains on dev but teaches nothing is reverted and its lesson goes back with its note; a lesson with no task type is never learned while another in the same run is; an agent already at its target gets a round and a version). Desktop unit `teaching.test.ts`; hidden e2e `teaching.spec.ts` against the stand-in engine (a rule is saved for Improve, no Save as button anywhere, saving makes no version, the report's lessons say Learned and Not learned); screenshots `teach-*`, `improve-dialog`, `improve-report`, `improve-report-lessons`.

**Consequences.** A version made by Improve agent now carries evidence that the student, not the mentor, does what it was taught, and that its check tasks held. A lesson only counts when the train set has tasks of its type that the student failed in some round; a correction about something the train tasks never test, such as a preference about wording, can't be verified and stays in the queue, which says so. Checking every failed task of the type is strict: a student that learns most of a lesson but still misses one task doesn't keep the change. The extra attempts cost student calls, not mentor dollars. An improvement no longer measures a kept change a second time on new seeds.

## 067. An approved write is refused when its file changed on disk since it was proposed

An approval in the workspace is for one change to one version of a file. Before, `apply` compared only the store's own copy, so a program that edited the file on disk while the change waited for a yes would have its edit overwritten.
- *The change is bound to the bytes it was planned against.* In a live store, `plan` takes a sha256 of the file's bytes on disk (or notes that there was none), and `apply` reads the file again right before saving. If the hash differs, nothing is written and the change fails with a plain error: the file changed on disk since it was proposed, so read it again and propose the change again.
- *A file that appeared counts as changed.* A new output file is planned against "nothing there", so one that shows up in the meantime refuses the write too.
- *No retry.* The error is not a `SaveError`, so the approver's "try again" is not offered; trying again would only overwrite the other edit or fail the same way. The agent reads the file again and proposes a new change, which the user approves anew.
- *Task mode is unchanged.* A scratch store never touches the disk and has no hash to compare.
- *Tests.* `files.test.ts`: a file edited after planning is refused and left as the other program wrote it, an untouched file saves as before, and an output file that appeared is refused.

## 068. A job can hold several organizations, and the ones it never trains on stay sealed

**Context.** The field plan (`docs/FIELD.md`, its contract and the amendments after the second reading) asks for one specialist that serves several organizations of one field, each with its own files, and is qualified on organizations it never saw, one of them real. The engine knew one `data/` folder per job, split every task the same way, and sealed only tasks.

**Decision.**
- *Schemas (additive).* `job.json` may list `organizations: [{ id, name, synthetic, role }]`, role `train` or `transfer`, ids plain enough to be folder names and unique. `Task.org` names a task's organization; it is required when the job lists organizations, every named one must be listed, and a family never crosses organizations (`organizationProblem`, refused at import as `not_a_job` with the reason). A job without `organizations` is exactly what it was.
- *Files.* Each organization's files sit at `orgs/<id>/data/` beside the job file, under the names the job's `data.files` declare. Importing copies the train organizations' folders into the job folder. A transfer organization's files and every one of its tasks go to the vault (`vault/<job>/transfer/<id>/data/`, each file's sha256 in the fingerprint) and its entry is dropped from the job the library keeps, so nothing in the job folder, the run's copy of the job, an exported job file, the Define screen or a mentor payload names it. A drafted job can't have organizations.
- *Binding per attempt.* A task's `data/` is its organization's folder, for the student's tools and the checker alike, since both use the attempt's one scratch copy; a correction's replay rebuilds from the same folder. A sealed organization's folder exists for the runner only after the mentor is released: `openTransfer` asks for the same proof as `openForLockedTest` and refuses a file that changed since sealing.
- *Splits.* Transfer tasks are taken out before splitting. The train organizations' tasks split as before, stratified by type at each organization, so every split, dev included, holds each organization's share of each type. A harness that hard-codes one organization's facts loses on the other's dev tasks; that measurement, not a text check, is what shows the harness is shared.
- *Invariant 1 covers transfer organizations.* Their name and id count as test content in the fingerprint of their tasks, so the leak gate refuses a payload that names them. The mentor's view lists only the train organizations and marks each data file and train result with its organization. Spark as the reference takes no sealed organization's task.
- *The mentor's prompt* says the agent serves several organizations with one harness, reads every fact from the request's `data/`, and must also serve organizations not listed. `orgFactsProblem` refuses a change set with a file that holds more than two values (ids, labels with a digit, long numbers) found only in one organization's files. It is a heuristic beside the dev measurement and proves nothing on its own.
- *Qualification.* The locked test runs the train organizations' test split and every transfer organization's tasks. The report card keeps `perType` as before and adds `test.perOrg`: each type at each organization, with its name, `seen` and `synthetic`.
- *Graduates.* A graduate's own `data/` is seeded from the first train organization's folder; any other organization is the existing rebinding of `data/` to its folder. The package carries the report card, so it holds each organization's scores, never its files or tasks.
- *A write the task didn't ask for.* An `end_state` task may list `writes`, the files it may change (a data file by name, an output file by path); an attempt that changed or made any other file, a table or a text such as `policy.md`, fails whatever its validator says.
- *After review (GPT-6 Sol).* A locked-test attempt is no longer streamed one by one (`attempt.started`, `attempt.finished`): its task id can name a sealed organization, so the screens get the test's progress and, once it is filed, the report. A transfer organization with no task is refused at import, since nothing would test it. A package's report card names a real organization only as "Real organization" (`real-1`), and the app's own card keeps its name. Organization ids are looked up as own properties, so an id such as `constructor` is a folder like any other.

**Consequences.** An organization's files are copied once more per attempt, as `data/` always was. Task ids must be unique across organizations. The heuristic can refuse a worked example that quotes three ids of one organization; the remedy is an example that reads them from the files.

## 074. Experiments run from the app through the same comparisons runner

**Context.** The platform plan (`docs/PLATFORM.md`, lane "Experiments engine") asks for comparisons the app can plan, preregister, start, pause, stop and read. Until now the comparisons runner (decisions 045 and 051) was a developer script, and the app only read the report it left beside a data folder. A second runner would mean a second set of caps, a second study step and a second release barrier to keep honest, so the app drives the one that exists.

**Decision.**
- *The API.* `experiments.plan(input)`, `revise(id, input)`, `calibrate(id)`, `preregister(id)`, `start(id, options)`, `pause(id)`, `resume(id, options)`, `stop(id)`, `list()`, `get(id)` and `onEvent(listener)`, with their schemas in `packages/shared/src/experiments.ts`. The input names the job folder, the arms (the runner's own, each with an optional Spark and student cap), the mentoring seed and the locked-test seeds (the first for every arm, the rest for the repeat), the rounds, and total caps for the student, Spark, compute and the wall clock. The split seed is the job's own, pinned with its files, and is shown, not set.
- *Where it lives.* `<data>/experiments/<id>/`: `experiment.json` (the record), `preregistration.json` (written once), `runner.log` (the runner's lines), and `comparison/`, which is the runner's output folder with its own `data/`, exactly as the script leaves one.
- *Plan before money.* `plan` reads the job and projects every arm with the runner's own projection at its assumed prices, each labeled assumed, and says what calibration costs: its tasks at the assumed price of an attempt, held to the student cap, and for a job with organizations Spark's study, at most $1 or the Spark cap. `calibrate` is its own call: the runner's `plan` command, run in the background, after which the projection uses the measured price.
- *Preregistration.* Freezing stores the input with the sha256 of the input and the job's pinned files (`pinInputs`, the runner's own pin) and the time, in the record and once more in `preregistration.json`. After it, `revise` and a second `preregister` are refused with `experiment_frozen`. `start` checks the hash and the files again, and refuses a job whose files changed since.
- *Running is the runner.* `start` and `resume` call `runComparison` with the frozen plan, so its caps, its funding order, its request journal, its study-once step and its test-release barrier hold unchanged. `confirm` is `--confirm`; `studyToken` is `--confirm-study`. When the runner waits for either, the experiment is `waiting`, with the reason, and `get` carries Spark's brief and its token for the screen to show. Each arm's Spark and student caps become the runner's `sparkCaps` and `studentCaps`. Nothing from the app runs on this computer's GPU: the GPU window is 0, so the weights arms show as not run, with the runner's reason.
- *Pause and stop.* The runner takes an optional `ComparisonControl`: an abort signal and a view of its engine. Aborting ends the command the way a closed process does: the controller closes, active runs stop where they are and resume the next time it runs, no arm starts and no locked test is released. That is decision 051's restart: an attempt in flight is made again and its requests count at their worst, and a Spark call in flight is paid again. Pause leaves it `paused`; stop leaves it `stopped`, for good, with what it measured kept. Closing the app pauses what was running, and nothing resumes on its own when the app opens again, since going on spends.
- *The wall clock.* The total wall clock counts while the experiment runs, across pauses, and stops it for good when it is used up. Each arm's own wall cap stays the runner's: twice its projection, at least 12 hours.
- *Reading.* `get` returns the runner's report from stored records: while it runs, built from its engine's records as they stand; otherwise the `report.json` it last wrote. Before the release its `backends` are empty, no arm is measured anywhere, no seed lists an arm, and no disclosure that names a sealed organization is shown (invariant 1). The runner holds no locked result before then anyway; this keeps it so if a record is changed by hand. After the release the report has each arm's results per organization (seen, each unseen one, synthetic or real), per skill, and the paired comparisons with Newcombe intervals, all from decision 056's report code.
- *Events.* `experiment.updated` carries the record whenever it changes and whenever one of its arm runs or rounds moves, so a screen reads `get` again. It goes over the engine port as an `experiment.event` message and reaches the renderer as `experiments:onEvent`, the way run events do.
- *The stand-in.* `apps/desktop/e2e/fixtures-experiments.ts` answers every experiments channel with state in the main process: a started experiment runs until `finishExperiments`, which releases it with the recorded dry-run comparison's report. Screens are built against it.

**Consequences.** One runner, one set of guards. The tests run on fakes and call no model: engine `experiments.test.ts` (plan spends nothing; revise, then preregister freezes; the study is made once and the run waits for its token; nothing before the release shows a locked result or names a sealed organization; results per organization, per skill and paired after it; per-arm and total caps held; pause and resume; the wall clock stops it) and the hidden e2e `experiments.spec.ts` through the bridge on the stand-in. Not handled: a pause during calibration or the study waits for them to finish, since the runner checks the signal only between steps; the regression check on a second job and local re-tests are not offered from the app; a per-arm wall cap can't be set.

*Amendment: after review (GPT-6 Sol, Oct 30).* A runner failure is stored and sent with every sealed organization's name and id taken out; the full message goes only to `runner.log`. Calibrating a preregistered experiment checks the frozen hash and job files first, as a run does. Pinning a job refuses a link under `data/` or `orgs/`, since what it points to could change between arm imports. A run's start is kept on the record (`runningSince`), so time cut off by a crash still counts against the wall clock when the app opens again. The abort reaches calibration's sweep, so no attempt starts once the wall clock is up or the person stops it. A stop wins over a pause still pending. Each has a test in `experiments.test.ts` that fails with its fix taken out.

## 077. Certified answers: a calibrated threshold to answer or hand off, with a stated bound

**Context.** A specialist should know when not to answer (`docs/CERTIFY.md`, section 1). The report said how often the graduate was right on the locked test, but not how far a buyer can trust an answer it gives, and the graduate answered every request whatever it knew.

**Decision.**
- *A setting.* `evaluation.certify` (zod, optional): `k` attempts per request (1 to 9, default 5; 1 turns agreement off), the target `epsilon` (default 10%), `delta` (default 0.05), and the calibration size (absent: 15% of the taught organizations' tasks, at least 30, from what the other splits leave). A job without it has no calibration split and no certificate, and runs as before; its splits are the same, since the new bucket takes nothing.
- *A sealed calibration split.* `certify` is a split name. It is drawn by `splitTasks` from the taught organizations' tasks with the others, families whole and disjoint from every other split, and sealed in the vault beside the test (`certify.jsonl`, hashed in the fingerprint). Its tasks' prints join the leak detector, so a request to the mentor that quotes one is refused as a test task is. It opens with `openCalibration` only on the mentor's release proof, after freezing. The existing `calibration` split, which prices attempts and is visible, is unchanged.
- *Agreement.* After the locked test's own attempts, the runner attempts each calibration task and each locked-test task under k seeds (the test's first seed and k - 1 drawn from it), in the frozen configuration. An attempt's canonical answer is its parsed ANSWER (keys sorted) or a refusal, with its file changes (tables as rows in any order, other files by diff without trailing space). The store keeps only a hash of it, salted by the run (`answer_key`, migration 17); sealed attempts still keep no trace or summary and are not streamed. The most common answer wins, ties to the earlier attempt; its votes are the task's agreement, and its check whether it was right.
- *The threshold and the bound.* `certify/stats.ts`: the exact one-sided Clopper-Pearson upper bound (the 1 - δ quantile of Beta(x + 1, n - x), by a continued fraction and bisection), thresholds from k of k down to 1 of k tested in that order, and the loosest one before the first whose bound exceeds ε is certified (Learn-then-Test, fixed sequence). If the strictest fails, no certificate: none answered, the error rate is at or above ε, or too few tasks, with how many would likely do at the observed rate.
- *The card.* `ReportCard.certificate` (additive): n, k, δ, ε, the risk-coverage curve, the assumption in words, and, issued, the threshold point (votes, answered, errors, coverage, bound) and each check where it wasn't calibrated: the taught organizations' locked test together and each never-seen organization, with counts and whether the observed selective error stayed at or under the bound. A packaged card names a real organization anonymously here too. The score, per-type results and repeats are the first seed's, as before.
- *Use.* A version whose card carries an issued certificate with k > 1 answers each chat request with k attempts on private copies of its files, none streamed, each a step that shows its answer and whether it agrees. With enough agreement the reply is the chosen attempt's text and steps, and only its file changes are proposed, one write per file, under the version's write mode. Otherwise it says it isn't sure and asks for the request to go to a person. A guardrail refusal makes no attempts. The CLI shares the host. Nothing reaches the network: the same local student answers.
- *Cost.* k multiplies the test's attempts: `finalTestAttempts` and the final test's time and price on Define say so before a run, the inspector's Evaluation tab shows the tries and the time, and a comparison's projection (and so its student caps) adds the certified attempts (`Field.certifyAttempts`). The locked test stays outside the training wall clock, as before.
- *Where it shows.* The report's Certified answers section: one sentence ("When Phil answers, it is wrong on at most 8% of requests like these, with 95% confidence. It handed 22% to a person."), the basis and the assumption, the risk-coverage plot (`RiskCoveragePlot` in `packages/ui`), and Held or Not held per check. Models has a Certified column, the Lab's Recently finished a Certified figure, a new chat the sentence, and the Evaluation tab the settings. The bound is always rounded up.

**Consequences.** A certified final test costs about k times as much and needs spare tasks: the academy sample now has 252 taught tasks (14 of each skill at each of three academies) and seals 60 of them, so it is certified; its transfer academy keeps 48. In chat, a reply rarely has an ANSWER line, so attempts agree on their file changes alone; replies with neither an answer nor a change agree only when their words are the same once case, spacing, punctuation and the way numbers are written are set aside, and the certificate's assumption says the bound does not cover such replies (the first version keyed them all alike, so five different replies in words counted as five agreeing). Comparison reports list every seed a test was attempted under, the agreement seeds included. Tests: engine `certify-stats.test.ts` (closed forms, the binomial identity, fixed-sequence stops, n needed), `certify-run.test.ts` (a certified run end to end, k attempts after the release, nothing of the calibration split reaching the mentor or the event stream, a job without the setting unchanged, canonical answers), vault and split tests, agent host tests (answer, hand-off, only the chosen writes, uncertified unchanged); renderer `certificate.test.ts`; hidden e2e `certify.spec.ts` with `report-certificate-dark.png` and `chat-handoff-dark.png`.

## 078. A failing helper becomes a minimal counterexample, the repair must pass it, and it stays as a regression test

**Context.** Phil's first field run lost tasks to helpers Spark wrote (`docs/comparisons/phil-1-real-academy-misses.md`): a question lookup that assumed one row per test position threw on "Full" tests, and a history helper compared answers as text and counted 0.125 for 1/8 as wrong. The mentor saw whole traces and whole files, and nothing stopped a later change from breaking a helper again. `docs/CERTIFY.md` section 2 asks for counterexample-guided repair.

**Decision.**
- *Scope.* Helpers only (mentor-written tools), on failed train attempts, in runs with a mentor choosing from the menu (`architect`). Comparison arms keep their declared protocol. Nothing from dev, the calibration split or the locked test is read; the vault is untouched.
- *Detection.* Before the round's mentor call, each helper call in a failed train attempt is replayed faithfully: the attempt's data is opened fresh, checked against the trace's hashes, harness hash, tools version and date, and every call up to and including this one is run again through the same tools and must give the recorded text (`replayToCall`, sharing the checkpoint's replay). The helper is then run in the sandbox on exactly the inputs it was given. The predicate is one of two, recorded with the case: `threw` (the same error message, with the place in the code set aside), or `contradicts` (the output names a field the checker's expected values hold, a fact's last path segment, a validator parameter or an answer key, and gives a value that isn't the expected one, compared as numbers however written or as text with spaces and case set aside). A field the output doesn't name is no evidence. At most one case per helper and three per round.
- *Reduction.* Delta debugging (Zeller and Hildebrandt 2002) over the helper's tables, rows first, then, for a crash, columns; text files are dropped in one step if the failure holds without them. Every candidate is run in the sandbox and kept only if the same predicate holds. Dependency-aware: rows a kept row references by id in another table (a first column named `id` or `<thing>_id` with distinct values) stay with it. The rows the call points at never go: for a crash, the rows that hold the most of the call's values, ties broken by values in the column named like their argument (the two questions at "Practice Test 4", module 2, number 6); for a wrong value, every row that holds any of them (a student's answers on a topic), and every column stays, because the expected value may rest on rows and columns the broken helper never read. Only tables the helper's code names are searched for those rows. A step cap (400 sandbox runs) bounds it; "1-minimal" only when every remaining row (and column, for a crash) was tried on its own, else "reduced".
- *Reproducer.* `CounterexampleSchema` in `packages/shared`: helper name and code hash, arguments, the call id and attempt, the predicate, the reduced tables and kept texts, original and reduced sizes, sha256 of both inputs, the step count, and the repair. Stored per job in the `counterexamples` table with its run and round (migration 17).
- *Repair.* The mentor's request carries this round's cases (the reduced tables, the arguments, the failure in a sentence, the sizes) and how many cases each helper's suite holds, never the attempt's whole tables beyond what it already sees. A change set that writes a helper with counterexamples is held to every one of them in the sandbox, with no model call: each reduced case must run without any error and give no value contradicting the one it records as expected, and this round's own must also pass on the attempt's original inputs, rebuilt by replay, with no error and no value the checker contradicts. A failure refuses the change the way a tool that doesn't load is refused, with the first failing case's reason for the mentor's one fix. Passing it only makes the change a candidate; keep or revert on dev decides as before. Each counterexample records the try, and keeps the first repair that passed.
- *Shown.* The round's drawer: the reduction ("1,212 rows → 1 row"), 1-minimal or Reduced with what that means on hover, the failure in plain words, the call, the reduced tables, and the repair with each case. Fields → Assets: a Counterexamples card with the count and one row per case, repaired or not.

**Consequences.** A real reduction on the academy's Copperfield data takes the "Full"-layout lookup from 2,312 rows to 4 (the two rows of tests.csv at the asked place, both "Full", and their two questions), 1-minimal; the history helper's wrong count keeps 413 rows, since every answer of the student and every row on the topic stays. A reduced case passes only on a clean run (the first version passed it once the recorded failure was gone, so a crash repaired into another crash passed a case with no original to replay); the original case is the stronger one, since it checks every expected field, and only the round that found it has the attempt to rebuild it from. It establishes a reproducible defect in a helper, not why the student reasoned as it did. The anchors are a heuristic of the call's values: a call whose values don't appear in the data keeps no anchors, and its crash can reduce to almost nothing. Tests: engine `counterexamples.test.ts` (the real sandbox on the academy's train data: the lookup crash, the repair passing both cases, the 0.125 case keeping `result`, no case when the helper is right, determinism, the dependency closure, the step cap), `counterexample-loop.test.ts` (the scripted mentor: the reduced case in its request, a repair refused then accepted, the later regression refused, no search for a comparison arm); hidden e2e `counterexamples.spec.ts` with stand-in data, screenshot `counterexample-dark.png`, and `field-assets-dark.png` again (`fields.spec.ts` now sets the Lab edition it needs).

## 081. A comparison pauses instead of dropping an arm it can't fund

**Context.** Before each arm started, the runner priced it at what an attempt had really cost so far. When too little was left under the student cap, it dropped the arm for good and went on to release the other arms' locked tests. That happened twice in real runs. In the second, the bare and draft arms froze at a price about 40% above calibration's, the targeted arm (the one the comparison exists for) no longer fit, and the runner dropped it and released bare's and draft's tests in the same second. Once the tests were released the arm could never run in that comparison, so the money spent on bare and draft answered nothing. Whether a primary arm is worth more money is the person's call, and the runner made it without asking.

**Decision.** This amends decision 051's funding rules.
- *Pause, don't drop.* When an arm can't be paid for at the measured price, the runner starts no more arms, lets the arms already running finish their development, and stops with the outcome `needs_funding`. The plan records the pause (`funding`): the arm, whether it was about to start or its locked test was about to be released, the measured price of an attempt, what the arm needs at that price with the headroom, what is left, and the cap. The log and the experiment say it in one sentence with the two choices. No arm is dropped for money and no locked test is released.
- *Priced before every arm and before the release.* The check runs before each arm starts, so a pause comes before money is spent on an arm that can't finish. It runs once more before the release: every frozen arm's locked test is priced at what that arm's attempts cost, and if the cap can't pay for all of them, the comparison pauses on the first one in 037's order. The release never holds a test for money now; the `held` decision is kept only for records written before this.
- *The person's two answers, only before the release.* Raising the student cap (`--raise-student-usd`, or `studentCapUsd` from the app) is recorded as an amendment: the old cap, the new one, the measured price at the pause, the arm, and that arm's own cap when it had to go up to what the arm needs at that price. The report lists every amendment in its disclosures. Dropping the arm (`--drop-arms`, or `dropArms`) is recorded as a `dropped` decision with `by: "person"` and the numbers it was dropped at. Both are refused once `releasedAt` is set, and the cap can only go up. The runner then prices everything again, and it pauses again if the money still doesn't fit.
- *The release barrier, in full.* The release needs every planned arm frozen, ended, or decided. An arm that never started and has no decision keeps every test held.
- *The app.* An experiment that waits for money has the status `needs_funding`. Its detail carries the pause and the amendments, and `resume` takes the answer; either answer is refused at any other time. The Experiments screen shows the sentence with two buttons, raise the cap to the least that pays for the arm or drop it, each behind the confirm dialog the screen already uses. The spend card shows the raised cap.

**Consequences.** A run can no longer lose its main comparison on its own, and the caps stay hard: every dollar above the first cap is one the person asked for, and the record shows it. A paused comparison spends nothing while it waits. Arms that started in the same wave as the one that paused finish their development first, so they can still spend after the shortfall is known. Tests on fakes, in engine `comparisons-runner.test.ts`: the second halt reproduced (paused, nothing dropped, no locked attempt, and running again changes nothing); a raised cap that goes on to finish within the new cap and is refused after the release; an explicit drop that releases, with the drop recorded as the person's; a final test that waits instead of being held; and an arm the person dropped is never started later. `experiments.test.ts` covers the same pause through the app's API.
